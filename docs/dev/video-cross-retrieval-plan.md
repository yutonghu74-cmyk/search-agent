## 3. 总体架构

```text
对话草稿 → 结构化需求 → 能力与权限校验 → 发起人确认
  → 固定检索计划
  → 多路召回：片段视觉 / 关键帧 / 字幕-ASR / OCR / 可用元数据
  → 授权映射为视频及时间位置
  → 生成片段、聚合证据、融合排序
  → 片段级业务验证（通过 / 不通过 / 未知）
  → 去重与按声明单位计数 → 补数 → 交付
```

维持模块化业务服务、独立 Worker 和现有 DSH 运行边界。不为各模态新建一套业务系统，不引入必装 PostgreSQL，不直接修改 vendored Data-Juicer。ClickHouse/目录、Milvus、业务账本继续通过接口接入。

## 4. 查询契约与确认卡

建议新增 `query-spec@3`，冻结现有 v2 请求和持久化记录的解释规则。以下是设计示例，并非当前可调用接口：

```json
{
  "schema_version": "query-spec@3",
  "media_type": "video",
  "query_input": {"mode": "text", "text": "有人喝水，字幕提到早餐"},
  "count_unit": "clip",
  "target_count": 100,
  "video_options": {
    "clip_duration_ms": {"min": 3000, "max": 15000},
    "allow_multiple_clips_per_video": true
  },
  "video_conditions": {
    "clauses": [
      {"id": "visual_1", "channel": "visual", "predicate": "有人喝水"},
      {"id": "subtitle_1", "channel": "subtitle", "predicate": "提到早餐"}
    ],
    "relation": {"operator": "all", "scope": "same_clip"}
  }
}
```

实际完整请求还须保留现有来源、去重、补数和节点策略等必填字段。视频长度数值仅为示例，不设为隐藏默认值。

- media_type、query_input、count_unit 独立校验。v3 初期只接受视频目标的文字查询；参考图查询视频明确拒绝。
- 不在本轮顺带改写 v2 图片输入字段。旧字段向新内部表示的转换必须显式、有测试、有历史恢复规则。
- clip 必须明确时长范围及是否允许同源多段；distinct_video 不要求片段交付时长，但仍保存命中及验证的证据区间。
- distinct_video 的语义是“原视频中存在满足条件的片段”，不表示整段每一时刻满足。要求全程无水印等条件，须绑定 whole_video 验证范围；无全片验证能力时拒绝承诺。
- 区分召回提示和硬条件。自然语言标准化不能把“不要水印”变成正向召回条件，也不能把“画面有早餐”替换为“字幕有早餐”。
- 首批关系语法仅支持同片段的 all（且）/any（或），clauses 数量受服务端限制；暂不支持任意嵌套布尔表达式和可配置跨片段时间偏移。
- 画面动作本身涉及先后顺序时，使用登记的时序验证能力；缺失则明确不支持，不能拆成两张图片分别通过。
- 用户未要求字幕时，字幕可辅助召回，但不能代替画面条件验证。指定 subtitle 的硬条件不能由 ASR 或 OCR 静默代替。

确认卡展示目标类型、数量单位、片段时长、同源多段策略、完整条件及其作用范围、来源、去重和补数范围。缺失关键字段进入草稿澄清；确认前不创建正式 task/batch/revision/run。修改上述执行语义使旧确认失效。

## 5. 库目录与能力登记

对现有目录和编码能力模型演进，至少登记：

- 目标 video、输入 text、支持的检索通道和结果粒度（whole_video/clip/frame/text_span）。
- 每路 model/encoder/preprocessing/index 版本、向量空间标识；关键词索引不虚构编码器。
- 原视频版本、时长、帧或文本时间定位的可靠性、片段解析与授权读取能力。
- 支持的过滤、分页、快照、候选深度及停止语义。
- 可验证的视觉、字幕、ASR、OCR、时序及全片条件，不将可召回等同于可验证。

先按当前项目与用户权限求授权范围，再做能力路由。各路使用匹配编码器，维度相同不代表空间兼容。缺少定位的字幕只可辅助找到原视频，不能作为同片段联合条件通过的证据。

功能按能力登记与部署开关共同放行；UI、草稿校验、执行端一致拒绝未开放路径，不仅依赖前端隐藏入口。

## 6. 公共模型与稳定身份

在现有公共模型上演进并迁移调用方，不另建一套平行的 SearchRequest/SearchHit/MediaRecord。

| 概念 | 建议字段/约束 |
| --- | --- |
| 素材 | source_namespace、source_asset_id、asset_version、授权引用 |
| 视频单元 | unit_type=whole_video/clip；片段为整数毫秒半开区间 [start_ms,end_ms)，0≤start<end≤duration |
| 检索表示 | binding、representation_kind、类型化索引主键、版本、对应素材/单元、时间定位 |
| 命中证据 | 分支、通道、原始排名/分数、命中区间、映射状态、版本及证据引用 |
| 验证证据 | 条件 ID、作用范围、采样/模型版本、判定、原因及受控证据引用 |

- canonical_unit_key 由可信服务按素材身份、版本、单元类型及区间生成，并有持久化唯一约束。whole_video 与覆盖全片的 clip 仍是不同单元。
- 多帧、多字幕、多索引命中同一单元只增加证据，不增加业务数量。跨库别名需要可信源映射；不能仅靠裸 ID 或 URL 合并。
- 保留原来源及授权关系，内容去重不删除来源，也不让一个授权路径替其他路径授予访问权。
- 字幕/OCR 是视频的表示，不自动生成可交付文本单元。
- 分页与账本继续固定 task/revision/generation/plan/epoch/index 版本；旧回传拒绝发布。

## 7. 多路召回与同片段联合检索

1. 按确认条件选择有能力且有权限的分支。不强制每个视频库具备所有通道。
2. 原有向量请求保持兼容；公共请求用判别式扩展表达向量、关键词等路径，非向量分支不接受伪造向量占位。
3. 各路结果先授权解析为素材版本及时间位置。缺失/冲突映射保留异常证据，不进入可交付集合。
4. 优先复用原库可靠片段边界；帧级结果通过版本化窗口/镜头聚合策略生成候选片段，执行长度约束，保存原始命中血缘。孤立帧不能证明动作持续发生。
5. 对规范化后的候选按分支排名融合，初期采用 RRF；参数固定在计划中，不直接混排不同空间的原始分数。
6. 对联合硬条件，在候选片段范围内读取对应画面与字幕证据，逐条件验证，并计算 all/any。召回命中本身不算条件通过。

“画面有人喝水且字幕提到早餐”须在同一候选片段中获得两种证据。字幕允许与动作在片段内不同时间出现；这不承诺精确同时发生。要求同一时刻或指定秒数偏移时，当前先提示该关系未开放，不能静默放宽成同片段。

召回分支可用并集提高候选覆盖，验收仍按确认的逻辑关系执行。有限 top_k 的交集为空不能证明库中没有联合匹配；继续翻页/扩召回或报告深度限制。必需分支失败保留错误，不能丢弃后报告完整检索；可选分支降级须显式记录。

## 8. 视频验证、去重与补数

- 复用现有清洗计划与 plan_flow，新增视频适配、受控解码和适用算子。图片抽帧结果只证明被观察画面，不能自动证明连续动作或全片条件。
- 内容规则输出 pass/fail/unknown；解码失败、证据缺失、定位不可靠、时序能力不足不得判 pass。未知不计入有效数量。
- distinct_video 按可信来源原视频身份归并，同原视频多个合格片段只计一个，交付保留代表证据。跨来源相同内容按已确认去重策略另行处理。
- clip 先精确身份去重，再做同源时间重叠处理。建议首批同一结果集仅交付同源互不重叠片段；相邻半开区间不算重叠，重叠候选按固定排序选择代表，不擅自合成长片段。
- 若不允许同源多段，再按原视频最多选择一段。跨原视频近重复只有在相应能力和策略已验证后开放，不冒充已实现。
- 有效计数 = 验证通过、授权有效、按声明单位去重后入选的业务单元。DJ 输出文件数、帧数和命中数都不直接用于完成判定。
- 补数沿用确认类型、单位、条件、时长、来源和去重策略；按有效新增量推进。深度上限、预算、源耗尽、失败与真实零命中分别记录，不靠重复区间凑数。

## 9. 预览、交付与运行保护

- 检索卡展示原视频、命中时间、通道和证据；片段预览通过鉴权跳转/读取，不把长期私有地址写入日志或永久清单。
- 清洗页展示每个条件的通过、淘汰和待复核；对全片/片段验证范围作明确区分。
- distinct_video 交付原视频或其授权读取引用；clip 交付实际裁剪文件或平台认可的可消费片段引用。只有时间范围 JSON 不代表已交付可使用片段，具体方式在接入盘点时固定。
- 清单包含素材与版本、单元 ID、时间范围、来源、证据引用、去重/裁剪/模型版本及 QuerySpec revision。
- 裁剪失败不得发布为完整包。持久化保存作业与产物状态，重试幂等，恢复时复核版本和授权，防止重复产物或旧运行覆盖。
- Worker 受控解码，限制时长、帧数、像素、字节数、CPU/GPU、临时盘、并发及重试。使用已有队列与租户公平调度，不因本轮新增媒体解析而引入必装服务。

## 10. 兼容与迁移

1. v2 图片请求、确认摘要、任务恢复及历史导出保持原解释，不原地改写为 v3。
2. 新增 v3 schema、OpenAPI 版本分支及内部规范化；禁止静默忽略视频字段或降级为图片。
3. 公共数据类、端口、各适配器和调用方同批更新。新增数据库字段采用可恢复迁移；旧图片记录不伪造视频区间。
4. 切换开关前先完成图片兼容定向测试。关闭视频开关阻止新执行，已有视频任务的查看、暂停及受控恢复策略单独验证。
5. 存储格式/模型能力不支持时明确报错；内存演示通过不能代替持久化恢复或真实平台验证。

## 12. 定向验收清单

| 用例 | 必须结果 |
| --- | --- |
| 旧文字找图/参考图找图、旧任务恢复 | 请求、身份及结果语义兼容 |
| 文本目标、图片找视频、视频样例输入 | 明确未开放，无静默替代 |
| 未选单位、片段未指定时长、缺关键规则 | 留在草稿，不创建正式任务 |
| 编码器维度相同但空间/版本不同 | 拒绝错误绑定 |
| 同视频 30 帧或多个字幕命中 | 聚合为合法单元，不计 30 个视频 |
| 字幕在前半段、动作在后半段 | all/same_clip 不通过，不能仅按视频 ID 相交 |
| 同片段画面与字幕分别满足 | 可通过；保留两种证据及区间 |
| all/any、字幕硬条件与辅助召回 | 真值逻辑和通道要求正确，不偷换条件 |
| 只有帧图但要求连续动作、全程规则 | 未知或能力拒绝，不算通过 |
| 片段负区间、超时长、源版本变化 | 拒绝映射或使旧证据失效 |
| 同源重叠、多段策略、跨库别名 | 按确认策略选择，计数稳定且有证据 |
| 某分支失败、top_k 深度限制、零命中 | 状态可区分，不假报完整或全库耗尽 |
| 重复点击、重试、并发回传、旧 generation | 幂等；旧结果不覆盖当前版本 |
| 权限撤销与跨租户读取 | 搜索、预览、验证、导出各环节拒绝越权 |
| 裁剪失败、产物缺失、进程中断 | 不发布假完整包，持久化恢复可验证 |
| 补数与资源超限 | 约束不改变，未知/重复不补足目标 |

执行时使用隔离测试账本、端口与显式独立 DSH_HOME。当前连续开发仅运行相关定向回归，不记作完整回归；完整回归在用户明确进入集成/发布验收时执行。

真实试点评测需单列：视觉、字幕、联合条件和时序样例的相关性/误接纳情况、片段边界、有效计数、首批结果与总耗时、解码/模型成本。阈值以真实样例基线和业务确认冻结，本提案不编造准确率或 SLA。

## 13. 审视重点与接入待办

## 19. 手动固定输入的视频流程补齐（2026-11-20）

关闭自动检索/补数时，正式确认只创建视频任务。后台首搜 outbox 保存 manual 回执，不再自动批准检索；视频工作区提供“查看检索来源 → 准备所选检索计划 → 确认计划并开始检索”，每条查询须至少选一个经授权且已核验为整段视频的索引。准备动作不执行检索，修改来源后旧准备失效；正式确认继续复用原批准账本和幂等键。

手动与自动视频计划共用首批 100 命中容量及候选×条件预算限制。固定输入在各已选分支取得首个完整窗口后可验证，不会自动耗尽所有续页。额外显式翻页也不能绕过清洗准备阶段的确认预算。手动模式的自动 intake 回执标为 manual，不反复占据后台待处理队列。

固定输入验证结束且有缺口时，结果发布、INPUT_SCOPE_COMPLETE 停止记录与 AWAITING_INPUT 状态在同一 SQLite 事务中保存，沿用既有停止账本，不新增视频状态机。发起人仍须审视并确认交付；发布后才标记 PARTIAL。合格数量与缺口不改写为目标数量；零合格仍不能打包，未知仍须人工复核。

视频检索进度增加明确的只读浏览路径，清洗或交付推进任务版本后仍可读取同 revision/generation 的已批准页；该路径不放宽 tick/reserve 的运行状态与版本校验。图片原有执行及读取默认行为不变。真实内网、检查器、模型及质量验收仍按第 18 节单独开展。
