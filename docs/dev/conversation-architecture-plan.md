# 对话与执行架构重构

最新增量决定：原 Chat 主角色可以通过可替换 Harness 承担平台中控，原业务服务保留派发和全部确认/版本/预算边界；已确认检索/清洗任务先接入“安排下一步”，不整体替换成熟自然对话。详见 [中控落地](platform-coordinator.md)。下文“不再增加自主主 Agent”保留为历史决策，不能据此禁止此次已授权的中控角色。

## 决策（2026-11-12）

产品围绕持续存在的需求模型、业务命令和执行事实组织，不围绕 DSH 会话组织。
普通需求对话与任务对话默认直接调用已选择的模型。DSH 保留为可替换的规划适配器，
不是理解用户、管理需求或保证作业可靠性的必选底座。不会在 DSH 失败时自动回退。
既有部署的规划引擎默认及已确认模型绑定暂不切换，避免使旧清洗批准失效。

目标边界：Chat/按钮 → 对话应用服务 → 结构化变更与差异预览 → 发起人确认 →
业务协调器/持久化作业 → 检索、DJ/VLM、交付 → 统一执行事实视图。
模型只能提出修改；权限、原文引用、版本、幂等、可执行规则发布和批准仍由业务层负责。

## 第一片已实现

- QuerySpec v2 增加可选 cleaning_conditions；每条含 condition_id、text、source_text、group_id。
  原文用于审计，新增结构中的条件用于编译。add/replace/remove 为有序原子修改；
  替换保留标识，删除必须引用当前条件；新增/替换逐字引用本轮用户消息。
- 历史规格按原有计划只读投影，首次确认修改才持久化新结构；旧发布物及原文不改写。
  结构化清洗草稿能继续修改、显示累计差异，确认前不改变正式版本，不调用图像模型。
- POST /v1/retrieval/tasks/{id}/conversation-turn 统一读取当前条件、待确认草稿和执行上下文，
  一次模型理解后由 TaskConversationCoordinator 保存草稿并返回差异；前端不拼接条件原文，
  不再发起第二次清洗建议模型调用。原 followup-intent 保留兼容诊断读取路径。
- 请求必需 text、llm_id、expected_revision、expected_task_version 和 Idempotency-Key；
  可选 feedback_ref={draft_id,draft_version,proposal_digest} 绑定当前待确认清洗草稿，
  recent_messages 与 draft_preview 沿用原限制。过期任务/草稿拒绝；未经授权不可读写。
- 条件仍受 8 节点上限约束，至少保留一项。适用类别必须属于当前任务；不明确时澄清。
  这一片只支持已有单一语义硬规则的图片清洗任务，其他算子组合明确拒绝，不能静默漏检。
- 新条件参与版本摘要、检测器发布及配方校验，包含仅剩一个条件的情况。
  只修改结构化清洗条件时，复用已确认的检索候选并重新核对权限；重新准备清洗确认卡，
  不自行执行。暂时允许重查所有条件，尚未承诺跨新旧发布物逐规则复用判定。
- 普通提单对话及新任务对话入口经 conversation_runtime 直接调用模型；扩词等规划仍沿用
  已配置运行时。构建信息分别标识 conversation_engine 与 model_engine。

## 尚未完成，不能记作整体现代化或发布验收

1. 总数量、主体、检索词与清洗条件已支持同一原子草稿（第五、六片）；各组配额修改尚未接入
   统一操作。类别专属条件的跨类别迁移需明确新范围；不能声称已覆盖全部需求类型。
2. 清洗完成后的逐规则影响计算及增量重查；阶段版本与运行 generation 的进一步解耦。
3. 正式任务和提单前对话均已支持异步回执及进程内并发预算（第九片）；独立调度、跨进程配额
   和公平性仍未完成，不自动续跑尚未保存提案的模型调用。
4. Chat 对话与侧栏已共享工作区投影（第四片）；生产页其他读取入口仍保留原接口，后续按需要迁移。
5. 相同模型、输入和工具约束下 direct/DSH 的对照样本、P50/P95、成功率及恢复能力。
   不以三次直连成功推断 DSH 的延迟占比，不把换调用方式当作全部性能优化。

后续以完整场景验收：多轮增删改、指代澄清、类别范围、混合修改、重复提交、断网、
服务重启、过期确认、未知判定。保留现有业务不变量。后续按 [双 Agent 方案](retrieval-cleaning-agents-plan.md) 增加检索、清洗两个专业角色的自主规划循环，由业务协调器衔接；普通对话复用现有入口，不再增加自主主 Agent，不拆微服务。DSH 继续是可替换适配器；T01–T03 仅接契约和草稿，执行循环待 T04–T06。

## 第二片：正式任务对话命令与恢复

- 对话账本新增 task_conversation_commands，按租户/用户/任务/命令键保存请求指纹、阶段、
  冻结写入、结果及失败。相同键和正文只产生一个执行轮次；正文变更返回冲突。
- 模型提案校验通过后，先持久化 prepare_feedback 产生的完整写入，再提交业务账本；
  完成回执与 task_dialogue_turns 聊天记录在对话数据库的同一事务提交。
  跨两个账本的间隙通过原业务幂等回执处理，不能在恢复时重新解析旧消息或重算草稿。
- 服务启动使旧持有者失效：保存了提案的命令可重放原写入；尚未保存提案的命令标为 interrupted。
  已知失败和 interrupted 需用户明确重试，使用同一个命令键、原正文和 X-Conversation-Retry:true。
  完成命令始终重放结果；不再调用模型。历史任务或草稿已变化时标记 is_current=false。
- GET /tasks/{id}/conversation-turns/{command_key} 只查询，不调用模型或触发执行。
  浏览器发送前在当前会话保存原请求及命令键，网络中断先查询；刷新后恢复查询/明确重试。
  未确定结果时显示“结果待核对”，不声称业务一定没有保存。恢复的状态回答标注为当时回复。
- 本片继续使用同步 HTTP 处理线程；浏览器断连不撤销已接收的处理。进程退出前未保存的
  模型响应无法恢复；重试这类命令会再次调用模型，但不存在已提交的业务写入。
  提单前的 DialogueCoordinator 已于第三片迁入此回执协议；扩词后续作业仍沿用现有作业幂等机制。
- 验证包括独立进程在任务 SQLite 提交后 os._exit、重开任务仓库、恢复同一个草稿版本，
  以及并发重试、旧持有者栅栏、不同正文键冲突、越权读取和浏览器丢响应/刷新。

## 第三片：提单前回执与快速接收

- 新增 POST /projects/{id}/dialogue-command 与 GET /projects/{id}/dialogue-commands/{key}，
  复用 ConversationCommandStore；TaskCommandStore 为旧名称兼容别名，旧日志表保留。
  项目命名空间只是命令寻址，不创建正式 Task、Batch、Revision 或 Run。
  原 dialogue-turn 入口继续兼容旧调用方。
- 模型完成后先持久化会话写入检查点；会话状态、递增版本、双方消息和完成回执在同一
  SQLite 事务里提交。写到会话但尚未写回执时进程退出会整体回滚，恢复只重放检查点，
  不再次理解该消息。并发修改仍有会话版本栅栏，已删除会话不能通过旧回执重放复活。
- Prefer:respond-async 请求先持久化接收，返回 202 和回执，再启动继承身份上下文的后台线程。
  浏览器短查询读取结果；仅停止等待不会撤销已接收处理。进程重启后已有检查点可恢复，
  没有检查点则需明确重试。此实现不是独立生产任务队列，尚未迁入统一 Worker 调度和并发预算。
- 浏览器为尚未获得 session_id 的 Chat 保存本地容器标识；收到结果后先保存 session/version，
  再清除命令恢复标识。首次回复丢失、刷新或新建另一个 Chat 时，不重复创建会话，
  不将旧响应盖到新 Chat。恢复已展示的回复不重复插入聊天，词表作业继续使用现有幂等接口。
- 隔离真实模型三轮对话保留主体和数量，首轮约 17.421 秒、数量补充约 0.004 秒、后续条件修改
  约 2.434 秒；每轮回执重放不调用模型。另一次完整异步 HTTP 样本约 0.023 秒拿到 202，
  约 4.606 秒完成。接收快不等于模型生成更快，不能据此声称首轮长延迟或 P95 已解决。
- 定向验证覆盖首次消息/后续修改、HTTP 接收先于模型完成、并发去重、上下文身份继承、
  中途退出回滚、越权/过期/删除保护、浏览器响应丢失/刷新/停止等待。未运行完整回归。


## 第四片：统一工作区状态

- 新增只读 GET /tasks/{id}/workspace，组合当前任务投影、检索分支计数、已确认候选清单引用和清洗调度状态。
  纯函数 workflow_state 统一给出节点、摘要、业务计数、阻塞与下一步动作；Chat 侧栏直接消费这些字段。
  不调用候选预览/映射，不保存提案，不触发确认或运行。完整词表在展开时才读当前绑定。
- 每个输入按 task/revision/generation/version 校验；读取中任务版本或写入时钟变化时最多重读一次，
  持续变化返回冲突。已替代、失败或未知的作业不能作为成功；目标数量/原始命中不作为入选数。
  下游清洗已推进时不再读取旧检索作业，避免历史检索绑定反过来覆盖当前状态。
- 普通进度/下一步问题无需模型直接读工作区；其他表达允许模型只返回 status 意图，回答前重新读取。
  模型不决定运行事实、不猜测网络或数据量。恢复的旧回执明确标注当时状态；当前回答以刷新后的
  侧栏工作区为准。模型提出的普通需求修改仍走既有草稿协议。
- 下一步动作来自服务端固定集合，浏览器校验当前任务及版本/generation；查看动作不会自动确认。
  清洗、候选确认与启动检索仍须用户点击，权限在服务端复核。失败刷新标记为上次读取状态。
- 本片覆盖 Chat 和其侧栏，不代表全部生产页统一、完整业务场景验收或延迟 P95 已达标。


## 第五片：总数量与清洗条件的原子草稿

- 新增 requirement 意图，复用 count_edits（images 的 set/add/scale）和 cleaning_changes。
  服务端 apply_requirement_changes 在副本上统一校验和生成 QuerySpec；数量、补数目标、
  条件共同写进一份草稿。任一操作失败均不保存，其后确认只推进一个正式版本。
- 待确认草稿就是后续相对修改的基数；20 张再多 5 张得到 25 张，已有筛选条件继续保留。
  原始消息不作为可变状态覆盖，差异预览同时显示总数量和检测条件的累计变化。
- 总数改变使用已有新版本检索调度，保守要求重新检索，不把旧候选或旧清洗批准当作新版本批准。
  只改条件继续走既有候选复用边界。目标数字不是已入选数量。
- 已有各组配额时，单独修改总数要求明确各组新数量，不自动平分或比例分配；当前仍未接入配额操作。
  同时改主体/检索词及清洗条件暂须澄清，不能静默只保存其中一项。
- 普通对话限制单个提案工具调用。结构化清洗提案含数量操作时按统一修改归一化，解释字段不参与执行。
  兼容模型在 count_edits 外重复回传相同的计算后总数，
  仅两者一致才接受并归一化；冲突拒绝，不能执行两次数量操作。


## 第六片：主体、词表与清洗条件混合修改

- requirement 增加可选 retrieval_changes 有序列表；复用公开 grouped-expansion 模型，
  不引入第二套词表。每项 op=upsert|remove，引用已有 group_id 或用 null 新增；upsert
  提交 primary_label 和完整 auxiliary_terms，remove 两者为 null。source_text 逐字引用本轮消息，
  新主体标签必须在引用中；类别/词数/重复词/词长/来源/引用共同校验，不写半份草稿。
- 未改类别、既有配额和模型绑定保留。词表从当前绑定草稿读取，后续“再改这个词”针对已修改主体，
  不回到旧正式版本。累计预览显示旧/新主体、总数和条件变化，完整词表按需展开。
- 改主体不能留下要求旧主体的清洗条件；模型需同时提出明确替换/删除。删除或重命名类别后，
  原类别专属条件不得变成全局条件或套到另一类别，缺少新范围时要求澄清。
  跨类别迁移暂不猜测或自动映射。独立的无水印、清晰等条件在未修改时保留。
- 提案有效后沿用命令检查点、幂等和一次版本确认；改主体/词表确认后走原新版本检索调度。
  旧候选和清洗批准不复用为新版本批准。单独扩词的既有作业入口仍兼容。
- 隔离真实模型样本完成“狗→猫、指定两个检索词、增加清晰并保留无水印”，约 9.484 秒，
  包含一次格式修复。首轮试跑曾因不合法清洗操作失败；没有现场业务写入。
  该样本不代表长期成功率、P95 或完整混合修改验收。


## 第七片：耗时分段与同轮状态复用

- 任务对话以 current_read_binding 直接读取当前版本，不遍历历史版本；用轻量 task_read_summary
  做模型返回后的版本栅栏。草稿绑定、权限校验和持久化命令协议保留。
- 新 conversation-timing@1 返回纯数字耗时，分开 requirement_read、draft_read、history_read、
  workspace_read/refresh、model_initial/repair、proposal_validation、version_check、draft_prepare/save。
  model_http_attempts 记录实际请求数，model_retry_wait 单列重试等待。日志不包含原文、回复、
  模型参数、URL或凭据；并发请求用 ContextVar 隔离。Server-Timing 提供本次处理总耗时。
- timings.scope=original_processing；完成回执重放保留原耗时，以 command_replayed 标识，不当作新请求耗时或新状态快照。总数不含最后
  命令回执提交/网络传输/页面渲染，嵌套阶段不能直接相加。浏览器另记 sidebar_update。
- 常见状态问题无需模型，写入时钟存在且未变化时复用本轮工作区；时钟变化/不可用则重读。
  模型分流出来的状态问题始终在模型结束后重读。没有新增跨请求缓存。
- 回答携带的工作区可供侧栏直接采用，避免再次请求 workspace；任务绑定或写入时钟落后则重新读取。
  普通轮询持续读最新状态；恢复的旧回执仍按历史回复展示，不作为当前快照套用。
- 隔离 SQLite、相同场景各7次，改前中位数17.251毫秒，中间版本10.417毫秒、最终版本9.309毫秒，进度读取14→7，
  历史版本读取7→0。另用同版代码仅关闭/开启复用作受控对照：15.781→11.092毫秒，进度14→7。
  样本和账本很小，不代表现场3秒级读取、真实模型等待或P95已改善。


## 第八片：明确修改直达草稿与模型输入去重

- 明确整句的总数量设值/增减、逐字引用的单组检索词替换，直接生成同一 requirement 草稿，
  不调用模型、不读聊天历史/执行状态；仍经过条件、配额、权限、版本、幂等和确认校验。
  多条件消息、逐图对象数、模糊指代、各组数量和未绑定的扩词预览不走快捷路径。
- 模型首轮只保留一份词表、条件与审计原文；字段映射沿用 current_groups 和 cleaning_conditions，
  类别ID/配额留在有效规格元数据。保留全部近期双方消息、独立限制、节点实际原因和模型绑定。
  格式失败时原有唯一修复轮恢复完整事实，不增加模型调用次数上限，不切换模型。
- 规范化只消除等价表达：完整词表与重复词数必须一致；已有类别的 replace 可映射为 upsert，
  不允许凭别名新增类别。单一类别、原条件仅为其字面主体、明确删除该条件且改名时，业务层
  将该主体条件联动替换为已引用的新主体，差异仍须确认。复合条件、类别专属范围不猜测。
- 示例上下文 JSON 3379→2244 字符，约减少34%，未删除历史消息；这是上下文片段大小，
  不是整个模型请求/token或延迟降幅。计时新增明确路径命中和模型输入字符/请求体字节计数。
- 前期真实试跑发现重复词数、替换别名和遗漏新主体检测；修正后的最终隔离复杂样本一次模型调用
  完成，约5.727秒，保留猫、无水印和清晰三个条件。单样本不能代表P95或整体成功率。


## 第九片：正式任务异步接收与有界后台工作

- 正式任务 POST conversation-turn 支持 Prefer:respond-async；先持久化原命令，返回202回执，
  模型理解/草稿写入在后台处理。查询仍用同一个 GET conversation-turns/{key}。
  旧同步客户端兼容；状态问答、明确数量及逐字换词直接返回，不排在模型工作后面。
- 复用 ConversationCommandStore。异步入口默认2个执行槽、最多8个执行中/等待命令，
  提单前与正式任务共用该服务实例的预算；满时保留失败回执并返回可重试503，用原键明确重试。
  同键运行中查询原回执，不消耗新槽或重复执行。它不是跨进程队列或所有模型接口的全局配额。
- 捕获身份 ContextVars 和独立请求头快照；原HTTP处理结束或后续请求不能更改后台命令键。
  后台仍检查任务/草稿版本，旧回执标记过期。关闭服务时先等待该线程池，再关闭业务依赖。
  启动恢复依旧只恢复已保存提案，未保存的模型响应不自动续跑。
- 网页先显示已接收，再短轮询同一回执；正常等待不重复POST。失败/断网/等待到期保留原消息键，
  可核对或明确重试。接受阶段与 queue_wait_ms 分开计时，排队不计入模型执行耗时。
- 隔离HTTP测试用阻塞闸门证明模型未结束时约12.818毫秒返回202；重复接受约1.978毫秒，
  同时队列占满时明确数量仍能直接保存草稿。该测量没有调用真实模型，不是端到端提速证据。


## 第十片：精简模型提案与本轮短引用

  待确认草稿及有效规格。工具枚举精确列出当前可用引用和scope，未知、跨类别改作用域、过期引用拒绝。
  同一次有界修复沿用原映射；任务/草稿在等待期间变化仍由既有版本栅栏拒绝。
- 提案解码后恢复原稳定 condition_id/group_id，业务模型、命令检查点和回执没有改成短ID。
  已保存的v1命令及明确选择DSH规划适配器的旧调用仍兼容，不修改DSH Skill批准摘要。
- 模型重复声明的“保留”条件仅在文本和作用域完全相同、原条件未被本轮修改时省去；显式删除/替换
  后再添加仍保留有序语义。单一类别的纯字面主体检查由明确改名联动更新，审核差异中可见；
  复合/专属范围不自动迁移。
- 提示词4886→1700字符，工具定义示例2169→1823字符。早期真实试跑拦截了虚构g2、错误范围和重复条件，

- 当前架构保持：普通/任务对话直连LLM；DSH保留扩词等规划适配；权限、草稿、执行与恢复归业务层，
  没有新增自主Agent循环。


## 第十一片：缩小状态恢复范围

- 当前检索计划、分页进度与当前候选清单在一个 SQLite 读事务内选择当前任务记录，再解码业务对象。
  复用同快照任务绑定投影；投影脏/缺失时回退原账本。每次重新授权，不跨请求保存权限或结果。
- 分页链、计划与版本/generation、清单发布关联、候选来源及媒体权限仍复验。写侧序列化和接口契约不变。
- 350 条无关历史分页的隔离计划+进度样本中位约39.5→15.9ms；8096同一任务工作区前后各3次
  中位约1.70→1.30秒。样本数量有限且有波动，不能推导模型耗时、端到端检索耗时或P95。
- 尚存限制：整块账本仍会读取并解析成JSON；当前任务自身历史仍有成本。进一步优化需要按任务/计划
  拆分存储或带事务一致性的持久读投影，并另做迁移与恢复验证，不用无效期状态缓存掩盖问题。


## 第十二片：按任务持久读视图

- 增加按 task_id 索引的检索派生快照；正常的计划、进度、当前候选清单读取不再选择整个 plan_set_ledger。
  任务绑定与派生快照处于同一 SQLite 读事务；权限与业务版本校验继续实时执行。
- 写原账本与同步快照同事务提交。原账本触发器使旧写入路径自动将快照标为失效，失效或缺行时
  回退原账本；载荷校验和损坏明确报错。启动从原账本重建，迁移失败可重试；级联删除同步清理快照。
- 同代码350条无关历史分页的隔离样本，强制回退与读视图各9次中位15.853→1.370ms；8096既有任务
  工作区前后各3次中位约1.70→0.38秒。实页波动较大，不能当作稳定延迟或模型生成提速。
- 此片完成读取侧按任务分区；原账本写入仍为全量序列化，快照同步有额外写入成本，当前任务自身历史
  尚未按计划拆分。保留原账本作为恢复来源，不将派生快照当作独立业务真相。


## 第十三片：分页写入与重放减负

- 预留/提交分页只在事务开始时读视图干净的前提下，按当前任务同步派生视图；源账本已被旧写入者改动时
  仍全量修复后才清除失效标记。其他确认写入保留原全量同步策略。
- 相同键预留和相同内容页回传在现有授权、计划/版本及内容一致性校验后返回只读重放结果，不再重复写账本。
  新幂等键仍保存映射；未知、冲突、撤权和旧 generation 不走成功重放。普通写入跳过字节未变的任务账本 UPDATE。
- 隔离350条无关历史分页、不启用分析器、每类7次，中位：预留135.0→96.7ms，提交136.5→92.6ms，
  相同页回传128.7→30.6ms。这是存储路径测量，不是模型或完整检索耗时。
- 剩余开销：全量源账本恢复/序列化、全量任务/Chat摘要同步与写锁；尚未完成源账本按任务/计划拆分。


## 第十四片：摘要增量、分页源分区、短写锁与对话总预算

1. 检索写入的任务摘要和Chat摘要只更新关联任务；相同Chat载荷不再删后重插。
   原摘要或源分区已失效时保留全量恢复路径，不把其他任务的旧状态误标为最新。
2. 新增任务头和批准计划页的独立持久分区；热分页只恢复当前任务/当前批准计划，不恢复其他计划的历史页。
   原JSON仍是同步兼容镜像，供尚未迁出的清洗/补数/历史读取及分区重建使用；没有删除历史源数据。
   分区、镜像、候选投影和摘要同事务提交；旧写入使分区失效，下次回退镜像并重建。启动迁移可回滚/重试。
3. 短读快照后，在事务外恢复业务账本、校验新页和编码兼容镜像；获取写锁后以同连接data_version检查任何并发提交，
   有界重做并在发布前再查外部权限。发生新generation时拒绝旧回传，无关写入可重试且不重复预留。
4. 单条对话默认30秒单调时钟预算，覆盖接受、排队、直连模型HTTP重试、退避和单次修复；链路内DSH进程也受剩余时间约束。
   过期队列不发模型请求，晚到响应不生成新检查点；已保存检查点仍可完成原有幂等恢复。独立非对话规划/VLM调用保留原配置。

同一隔离环境、350条无关历史分页、每类7次，对照原分页提交路径：预留89.439→24.128ms，提交92.329→24.562ms，
重复回传35.170→3.350ms；写锁持有中位分别88.218→4.414ms、91.237→4.674ms、34.345→0.018ms。
这是本地存储测量，不是模型或向量库端到端耗时，也不是P95。

剩余：兼容镜像仍有全量原始JSON读取/编码成本，但已移出分页写锁；业务local_ledger仍整块恢复。
非分页写入和失效重建仍可能全量同步；外部权限复核仍可能占用写事务时间。后续迁移其他模块后才能停止镜像双写。


## 第十五片：单一行存储与非分页准备/提交分离

- 五类业务JSON物理表（任务、计划集、旧检索、候选、清洗）迁移到共享registry/section/item行存储。
  原表名是按需聚合的兼容视图，旧读取、清洗、补数、历史恢复和维护UPDATE均访问同一份记录，
  不再常驻完整JSON镜像。计划分页按键追加，常规非分页写入直接编码记录差异；派生缓存仍是可重建投影。
- 布局版本1；每个账本在事务内先校验、复制、替换视图并再次校验。失败回滚，未知版本拒绝覆盖；
  兼容触发器保留损坏载荷以便报错，不把缺失/错误容器或未知标签修复成空状态。旧哈希、版本、计数不变。
- 任务创建/反馈确认、计划确认、清洗/候选/检索写入，以及摘要重建与级联删除，先在私有SQLite快照中
  完成验证、编码、派生页与事件准备；获取原库写锁后验证提交水位、重新核验外部权限，只回放记录变更。
  SQL回调的嵌套连接使用保存点，失败一起回滚。三次竞争后用串行回退，避免并发确认饥饿。
- 私有快照不启动Worker、不调用外部写操作；参考图BLOB非空时走原库只读延迟视图，避免复制全部媒体字节。
  当前未把所有聚合读取和快照准备成本消除；外部权限复核及竞争回退仍可能延长写锁。
- 同环境350条历史分页、7次新计划确认：旧物理JSON路径中位总耗时158.866ms/写锁157.774ms；
  新路径约171.889ms/2.585ms。主要收益是缩短阻塞，不能宣称单次总耗时也改善。未测P95或真实内网依赖。
- 现场历史副本五类账本语义对照一致；切换前停稳备份到仓库外0600私有文件。降级旧程序需停服、核对切换后
  写入并按备份恢复，不能让旧代码直接打开新布局。新增布局不要求PostgreSQL或改动vendored DJ。


## 第十六片：非分页计划写入按任务准备源分区

- 在同一准备快照内、修改源记录之前观察plan_source_meta。原分区干净且调用提供task_id时，仅编码并同步目标任务头及其计划页，保留无关任务记录；失效、迁移和无范围维护仍完整重建，不能把其他任务的旧分区直接标为干净。
- 任务/Chat摘要复用本次事务已经校验的current映射，不再另读完整计划兼容视图。权限复核、提交水位检查、原子发布与重试沿用第十五片。
- 派生分区是否相同同时比较载荷与校验和，确保脏源重建能够修复载荷损坏但旧校验和未变的情况。
- 隔离350条无关历史分页、各7次，确认中位总耗时193.558→83.860ms，写锁1.917→1.732ms。对照是关闭本片优化的上一轮行存储路径；并非LLM、真实向量查询或P95测量。完整源恢复、差异准备及当前任务自身历史成本仍在。

- 通过请求/后台激活级pipeline trace串起需求理解、扩词批次、查询编码、向量调用、页提交、候选校验及响应编码；原对话计时向父trace合并，异步复制上下文不共享已结束请求的计数。

## 第十八片：当前计划和进度使用同一读快照

- 可选get_progress_snapshot在一次SQLite读事务内选择当前批准计划并校验page heads；HTTP进度与检索调度复用同一校验器，原get_progress接口保留，无该可选能力的适配器仍走原双读路径。
- 不缓存业务状态或授权，不减少结束前的库权限复核；同快照内计划/分页一致，快照之后的改版由下一读取和原写侧generation/version栅栏处理，不能把旧快照当作最新写入授权。
- 独立隔离样本351条旧计划历史页、每路径17次，中位41.820→32.659ms，读事务2→1；只证明局部进度读取减负，不等同端到端提速。workspace_projection/retrieval_progress_read子阶段继续提供定位依据。


## 第十九片：当前计划页裁剪及本地分类迁移切换

- current/进度优先读取任务头中的当前指针及其plan_digest页分区；只解码当前计划的页和游标，不读取旧计划分页。候选历史清单校验仍用完整任务视图，权限及版本/generation栅栏不变。
- 源分区失效或缺头时保留同快照回退；存在但损坏的当前分区不能借旧视图绕过。任务头仍需解析，因此不宣称所有任务历史成本归零。
- 迁移源指纹和节点语义校验纳入兼容视图，防止行存储账本被忽略。私有现场副本演练后，停服备份、从停稳源库重建并校验、核对提交水位/持有者/WAL、原子替换同一路径并沿原配置重启8096；源业务内容保持，新增六分类为派生重建。
- 切换后两份结果共12个分类API、工作区和健康接口通过只读验证；原库备份保留在仓库外。隔离351条旧计划历史页、各17次，中位32.939→1.867ms，为局部读路径证据；未运行完整回归或真实内网模型验收。

## 第二十片：Chat 在途状态读取合并

- workspace/progress 相同路径与身份请求头仅在传输重叠时共享，完成即释放；每个消费者获得独立数据并继承性能 trace。
- 写请求前后、新事件及切换任务时清空共享入口；带 signal 的请求独立取消，fresh 版本复核不参与共享。沿用业务授权、UI token 与版本/generation 栅栏，不缓存已完成授权或状态。
- Node 实际并发边界与既有 Chat/计时定向测试共85项通过；非跨客户端缓存、全量回归或端到端延迟验收。

## 第二十一片：检索执行治理

- LOCAL_EXACT/LOCAL_CLIP/PLATFORM及组合CLIP首轮共用有界公平队列实现：按租户/用户轮转，同用户任务FIFO，每页让出；默认2线程、128执行/待执行项。恢复从持久批准/作业补入，容量不足时等待空位；重复通知不会并行执行同一任务。可重试故障退避，异常任务不阻断其他用户，有限保留错误码供状态展示。
- 同服务实例首轮、手动与补数共用执行槽和用户互斥，锁覆盖读取至页提交；手动冲突返回可重试SEARCH_BUSY，不重复请求、扣额度或提交。
- SQLite预算按租户/用户/项目/任务/revision/generation原子预留检索调用与原始命中名额；默认128/1000，task_version推进/同代次重批/重启不重置，既有scope不因调高服务配置静默扩额。失败或中断保守消耗预留，历史启用前未知，不将预留当作供应商计费、候选数或有效素材数。
- 耗尽持久停止，匹配当前代次才发同事务事件；补数结束dispatch并落EXECUTION_LIMIT_REACHED，不创建虚假清洗intake。Chat展示队列、预算及停止状态，已有结果保持可读。新增表纳入迁移源指纹和任务/Chat清理。
- 配置、语义和限制见contracts/search-execution-controls.md。并发/公平仍为单服务实例，未实现跨进程租约或全平台模型费用配额；真实W3多人/内网容量仍待配置及联测。


## 双 Agent Harness 接入补充（设计）

后续检索/清洗角色通过统一运行端口和共享工具网关接入，Harness 产品、版本与模型配置分开，按角色路由。普通对话直连与旧批准绑定保持现有行为，先适配再逐步迁移；不直接在 DshModelRuntime 上追加双角色业务分支。SDK/事件/工具前缀/原生 Team 只属于适配器；最新 DSH 先以精确候选发布物隔离验证，再决定切换。参见 [审视及 T04 子项](harness-portability-review.md)。这是待实现约束，不是多 Harness 已接通声明。
