# 需求理解核心回归

本轮覆盖建数据需求的多轮理解、草稿保存和恢复，不覆盖视觉清洗质量或真实内网验收。核心原则是：模型提出结构化修改，后台核对证据、作用范围、数量与状态后保存；完整需求直接进入待确认检索词，不重复询问数量。

## 场景与检查

场景集：[core-24.json](../../../tools/requirement_scenarios/core-24.json)。24个场景、74轮，六组各4个场景：

| 组 | 覆盖内容 |
| --- | --- |
| A 首轮完整需求 | 多类各配额、不同配额、仅总数、画面对象数量 |
| B 补充缺失信息 | 每类补数量、只补未定类别、先条件后数量 |
| C 局部修改 | 单类数量、画面、增加类别、删除后恢复 |
| D 条件作用域 | 类别条件、共同条件、撤销、单类豁免 |
| E 指代与冲突 | 换主体、按动作指代、模糊指代、配额与总数冲突 |
| F 另起与普通问答 | 独立新需求、完全替换、解释原因、询问执行状态 |

每轮读取后台实际草稿，再重开SQLite账本核对恢复。六项检查为类别完整、画面保留、数量、修改范围、追问必要性、状态与副作用。未进入用户确认的正式执行；测试使用合成需求及隔离账本。

失败分为服务失败、协议失败、保存拒绝、语义失败；通过分首次通过、协议修复后通过、显式重试后通过。前置轮失败后的轮次记为未执行，不计通过。自动归因只是线索，后台回复缺陷也可能先落在“模型或上下文”分组，需结合保存状态和提案人工定位。

## 从真实失败修复的契约

- 明确数量不能丢失：新需求的逐类配额、明确总数与类别配额冲突在保存前校验，失败交模型进行一次协议修复；不替模型猜测各组如何分配。
- 已知内容不重复问：部分类别有配额时，追问只列缺数量的类别；单个已分配类别修改总数时同步配额。
- 模糊指代不猜测：多类别下“那个改成30张”必须先问类别；用户随后只回答“狗”时，数量证据可引用尚未解决的scope追问。解决或放弃追问后不能继续复用旧数量。
- 场景修改保持一致：类别ID稳定；名称本身包含旧画面时，与新画面同步更新，避免旧动作再次拼入有效需求。重组名称/画面只允许当前原话及原画面已有内容。
- 条件迁移保留依据：某类解除共同条件时，可逐字把原共同条件保留给其余类别，并记录来自原共同条件的证据；不能借此增加新条件或把别的类别条件扩散。
- 冲突必须真正解决：用户明确“按每类20张算”时，应保存对应类别配额并解除冲突，口头回答或摘要确认不算完成修改。
- 独立新需求不追加旧类别：明确要求与之前分开的新一批，应替换当前草稿，新需求不继承旧配额。

这些校验只覆盖证据明确的边界。模型仍负责开放语义理解；24个场景通过不代表任意表达都能正确理解。

```sh

  --fixture --output var/requirement-evaluation/fixture.json
```
