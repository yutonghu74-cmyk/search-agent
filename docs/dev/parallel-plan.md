# 多窗口协作实施方案

状态：已有独立角色 worktree 和本地开发记录；远端必需检查未配置。A 总控门禁补齐实现待审查发布，不能用候选代码自认证为可信基线。

## 阶段与停止条件

1. **准备基线（A）**：筛选首次提交内容，审查凭据/大文件/数据/嵌套仓库；禁止无审查 `git add .`。提交代码、规格、契约及本套规则后记录提交 SHA。范围与契约缺口见 `baseline-readiness.md`；首次提交不等于公共契约冻结。
2. **冻结契约（A）**：对齐 v1.9 第 4、14、16、17 节，补足草稿确认、版本/generation、检索分页、逐素材清洗结果、事件/错误及存储一致性契约。用固定请求/响应样例和契约测试表达。现有 `ports.py` 仅覆盖 P0，不视为全量契约已冻结。
3. **分派（A）**：每个窗口填写任务卡中的基线 SHA、具体切片和验收项；从同一已提交基线建立独立 worktree 和角色分支。不允许直接在同一个 checkout 并行编辑。
4. **开发（B/C/D）**：只做任务卡范围；接口缺口提交变更请求；职责内自动修复、测试、检查。每次完成切片写交接文件。未获授权不自动提交/推送。
5. **集成（A）**：用可信基线中的检查器检查每个工作分支，审查 diff 和测试证据；按契约→适配器/业务→装配顺序逐个集成。合并前后均跑测试。冲突由对应负责人处理，不整文件覆盖。需要共享契约变更时，先发布新基线，各窗口同步后再继续。
6. **第二轮**：第一轮后端闭环稳定后，A 再分配 UI、验收和内网联调工作包及文件范围；不能借第一轮角色自行扩展 UI。

## 进度汇报节奏

- A 在 `docs/dev/progress.md` 维护单一当前快照；B/C/D 在本角色 handoff 追加带时间的明细，避免多个工作区同时编辑总看板。A 审查或集成角色更新后，在同一周期同步总看板。
- 活跃任务按 30 分钟为最长间隔；开工、完成契约、完成实现、获得测试结果、阻塞/恢复、READY_FOR_REVIEW、ACCEPTED 等状态变化不等待定时点。任务在 30 分钟内完成时仍记录开工和交付。
- 每次汇报使用事实状态：`IN_PROGRESS`、`BLOCKED`、`READY_FOR_REVIEW`、`ACCEPTED`；只有 A 审查后可写 `ACCEPTED`。命令尚未结束写 `RUNNING`，未执行写 `NOT_RUN`，不得预填成功结果。
- 全局快照回答“现在做到哪、卡在哪里、下一步是什么”；角色 handoff 回答“具体改了什么、为何这样改、怎样验证”。两者引用相同基线和任务卡，但不复制整段日志。
- 会话暂停、等待外部输入或没有变化时，记录原因和恢复条件；定期更新是工作会话内的协作规则，不代表仓库自身具备后台定时器。

## 角色及文件边界

| 角色 | 工作包 | 交付重点 |
| --- | --- | --- |
| A 总控 | WP01/公共契约/集成/WP07 协调 | 规格与公共模型一致、契约样例、任务卡、装配和端到端证据 |
| B core | WP05、WP04c、补数协调 | 草稿确认/任务状态/版本、结果去重计数、补数、账本接口实现 |
| C retrieval | WP02、WP03 | 数据目录、元数据/Milvus/Embedding、受限 DSH、可替换的模拟数据源 |
| D cleaning | WP04a | 复用 plan_flow、提交/取消、逐素材结果及执行证据 |

机器可检查的修改范围以 `ownership.json` 为准；目录项以 `/` 结尾，其他项只匹配单个文件。未列出的文件均由 A 负责，包括 `ports.py`、`models.py`、`integration_models.py`、`query_spec.py`、`api.py`、`errors.py`、包入口、`contracts/`、`config/`、`db/`、依赖和规格书。A 也不能未经审查接管 B/C/D 的进行中修改。

角色专属测试目录必须有 `__init__.py`，以便标准库 unittest 递归发现。新增目录不会自动成为可导入包，开发者应按需要添加包入口。

## 第一轮目标与验收

最小闭环：草稿→发起人确认→模拟检索→真实 DJ 清洗→去重计数→不足补数→版本化结果/导出。

- 重复确认仅创建一次；变更载荷冲突；非发起人拒绝。
- 新 generation 后旧回传拒收；失败/未知/重复不计入有效数量。
- 历史批次排除基线固定；补数达到目标或明确给出停止原因。
- 真正调用 DJ 才标记清洗联测 PASS；只用 fake 时标记 SIMULATED。
- 持久化重启恢复、真实 ClickHouse/Milvus/W3 测试分别登记；外部无环境记 NOT_RUN，不得算通过。

上述为待实现门禁，不是本次新增脚本已经实现的业务测试。A 按 v1.9 第 16 节建立验收项→测试→结果映射，不能用测试总数替代业务验收。

## 一键本地检查

Python 3.11+，无额外依赖。在本 worktree 根目录执行：

```bash
# 基础检查：适用于初始提交前；不能证明角色边界通过
python3 tools/collab_gate.py baseline

# 开发窗口交付：把占位符替换为 A 分派的真实完整提交 SHA
python3 tools/collab_gate.py check --role core --base <BASE_SHA>
python3 tools/collab_gate.py check --role retrieval --base <BASE_SHA>
python3 tools/collab_gate.py check --role cleaning --base <BASE_SHA>
# A：基线中必须已经存在审核发布的 JSON 任务卡
python3 tools/collab_gate.py check --role integration --base <BASE_SHA> --task docs/dev/tasks/intent-model.json
```

`check` 会验证基线为 HEAD 祖先、角色分支、基线责任表、已提交/暂存/未暂存/未跟踪文件的修改范围、交接文件存在，并执行基础测试。重命名按删除旧路径和添加新路径一起检查。失败返回非零退出码；没有提交或漏传基线直接失败，不假装通过。

A 附加约束：必须为独立 linked worktree、codex/integration 分支；JSON 任务卡与责任表均从 `--base` 读取，当前任务不能修改自身任务卡。文件范围是 A 允许范围与任务卡精确清单的交集，并排除 core/retrieval/cleaning 所有负责路径；不允许目录通配、路径穿越、符号链接或子模块。任务卡 source_base 为任务起始提交，须为发布基线的祖先；acceptance 为非空验收说明，files 必须包含 integration 交接文件。这些字段检查不替代人工审查验收证据。

发布顺序：人工审查门禁变更与隔离 Git 测试 → 授权发布门禁/任务卡可信基线 → 候选工作区同步该基线 → 由受信检查器执行角色门禁与全部回归。旧基线缺少 integration 配置时必须失败，不回退到 baseline 模式，不把新门禁认证自身当作信任来源。角色、基线、任务卡都应由受信总控/CI 指定；本地通过不自动授权提交、合并或推送。根 AGENTS.md 原三角色命令继续有效，A 使用本节新增命令。

测试会执行仓库 Python 代码，首次接收不可信代码时先审查；本地脚本不是沙箱。检查不扫描 Git 忽略文件，不是凭据扫描器，不自动确认网络安全或业务完备性。

## 从“自觉执行”到“不能绕过”

本地 AGENTS.md 和脚本可被人为绕过。正式协作仓库应由仓库管理员配置受保护集成分支、禁止直接推送、必需检查和总控审查。当前未连接/配置此类保护。

CI 应从受保护的目标分支取得检查器，不执行开发分支自改的检查器；角色和基线由 A/受信 CI 配置指定，不能接受开发者任意自选。CI checkout 实际工作分支（保留角色分支名），下载完整基线历史，在候选目录执行该可信脚本的 `check`；通过后仍需审查测试有效性。可使用公司现有 CI，无需为了协作先引入新的托管平台。

## 运行资源隔离

分别使用 worktree 下的 `var/<角色>/` 作为运行输出与测试账本目录，显式配置独立 DSH_HOME 和端口。当前 HTTP 示例固定 8080：可同时跑单测，启动多个 HTTP 服务前由 A 增加端口配置；不要假设写进任务说明就已支持。环境按冻结依赖准备，不共享可变 DJ/DSH workspace，不向仓库提交环境和真实数据。

AGENTS.md 是仓库持久开发指引；任务计划、任务提示和交接文件是本项目约定，不是产品自动调度机制。官方参考：[Iterating Development Workflows with Codex](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)。本方案不会自动启动窗口、监听其他会话或自动合并。
