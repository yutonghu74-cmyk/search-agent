## 1. 总体建议：评测系统与业务系统分开

采用“固定评测数据 + 测试驱动器 + 业务证据采集 + 评分器 + MLflow 记录与对比 + 发布门禁”。

MLflow 用于管理评测数据、运行记录、Trace、评分和反馈，不替代业务任务数据库、任务队列或权限服务；也不是负载测试和故障注入工具。

官方 GenAI 评测以数据、预测函数和评分器组成评估流程，可使用 `mlflow.genai.evaluate()` 组织评测。本项目需要在业务系统外封装评测入口，而不是把 DSH 对话文本直接当作检索效果。[MLflow 评测概览](https://mlflow.org/docs/latest/genai/eval-monitor/)

```text
冻结的评测集 + 语料/索引快照 + 版本清单
                  │
                  ▼
             测试驱动器
      创建任务 / 执行反馈 / 等待终态 / 注入故障
                  │
                  ▼
DSH → 检索业务服务 → 向量库 → Data-Juicer → 结果集服务
                  │
                  ▼
       真实输出、事件、清洗证据、成本和 Trace
                  │
        ┌─────────┼──────────┐
        ▼         ▼          ▼
     程序评分   人工标注   经人工校准的模型辅助评分
        └─────────┼──────────┘
                  ▼
     MLflow Run / 逐案例结果 / 对照报告
                  │
                  ▼
     CI 门禁 + 业务签字：通过 / 不通过 / 证据不足
```

最重要的三个区分：

1. 系统自报合格数，不等于独立评测确认的合格数。
2. 功能测试通过，不等于业务效果达标。
3. 模型评分较高，不等于权限、计数和状态一致性正确。

## 2. MLflow 的借鉴范围与接入前提

### 2.1 能力映射

| MLflow 概念/能力 | 本项目映射 | 需要自行建设的部分 |
| --- | --- | --- |
| Evaluation Dataset | 用户诉求、标准条件、目标库、反馈场景 | 多模态素材标注、语料快照、授权测试身份 |
| Evaluation Run | 一个版本/配置在一套固定数据上的评测 | 版本清单、预算和对照实验设计 |
| Trace / Span | 解析、选库、检索、清洗、去重与补数阶段 | DSH/业务服务/Worker 的采集适配与关联 |
| Code-based Scorer | 计数、规则一致性、重复、越权、版本检查 | 本文定义的业务评分逻辑 |
| LLM Judge | 解释质量、扩词语义漂移等辅助判断 | 业务 rubric、人工校准、多模态证据适配 |
| Feedback / Expectation | 人工评语、正确答案、争议复核 | 标注权限、复核流程、来源与版本治理 |
| CI 回归集成 | 已知失败场景的发布检查 | 故障注入、并发驱动、门槛和审批策略 |

MLflow 提供代码评分器与模型裁判；建议本项目优先使用代码评分处理客观约束，模型裁判只补充不能简单程序化的部分。[Scorers 文档](https://mlflow.org/docs/latest/genai/eval-monitor/scorers/)

### 2.2 必须核实的运行前提

- 冻结 MLflow 客户端和服务端版本，先验证数据集、评分、Trace 和反馈功能。本文引用 `latest` 文档，不代表团队现有环境已支持全部接口。
- 官方 Evaluation Datasets 要求 SQL 后端，不支持仅使用 FileStore。团队环境建议使用受管理的 SQL 数据库；单机试点可用 SQLite，但不据此推导多人生产容量。[数据集要求](https://mlflow.org/docs/latest/genai/datasets/)
- 素材、结果清单等大对象放在受控对象存储；MLflow 记录摘要、引用和必要的脱敏证据，不默认上传全部私有图片/视频。
- 不假设 DSH 或内部 Data-Juicer 插件可以直接自动埋点。业务边界采集优先，框架内部细节在有支持且经验证时补充。
- 开源自托管和托管平台的能力、权限配置可能不同；不将某个平台特有功能当成本方案前提。
- 普通 pytest、压测和故障注入仍保留；即使 MLflow 暂时不可用，也要保存本地受控测试产物和失败退出状态，不能把记录失败视为测试成功。

## 3. 评测对象与分层测试

| 层级 | 测试对象 | 输入 | 主要输出 |
| --- | --- | --- | --- |
| L0 契约与确定性单测 | schema、授权、幂等、计数、参数校验 | 人工构造边界 | 明确 pass/fail |
| L1 单组件效果 | 解析、扩词、路由、各清洗算子、去重 | 标注样本和需求 | 准确率、误杀、漏检、成本 |
| L2 静态流水线 | 固定候选经过清洗去重 | 相同候选清单与规则 | 组合后质量、损耗、证据完整性 |
| L3 端到端任务 | 从诉求到结果及补数 | 真实库快照与固定需求 | 合格唯一产出、达标率、时间、费用 |
| L4 多轮与多人 | 反馈、规则放宽、隔离、取消恢复 | 固定交互脚本 | 版本正确、无串用户、无重复计数 |
| L5 压测与故障 | 排队、依赖故障、进程重启 | 固定负载与故障时间表 | 吞吐、尾延迟、恢复、账本一致性 |

顺序：先证明组件输出可信，再测组合效果；先在受控数据上证明状态一致，再接真实业务试用。不能只用端到端“结果看起来不错”替代基础测试。

## 4. 测试数据设计与标注规范

### 4.1 推荐测试集

| 数据集 | 初期建设建议 | 必须覆盖 |
| --- | --- | --- |
| intent_routing | 200 条需求起步 | 实体、否定、数量、来源/风格、歧义、库选择 |
| image_operator | 1000 张图片起步 | 合格/不合格、边界、各类水印/文字/模糊；不能只收集容易样本 |
| video_operator | 100 个片段起步 | 时长、重复片段、时序、镜头切换、抽帧盲区 |
| dedup_pairs_clusters | 300 对样本及若干小簇起步 | 精确重复、变体、相似非重复、视频重叠、链式误合并 |
| end_to_end | 50 个任务起步 | 可满足、不可满足、未知可满足性，图片和视频分组 |
| multi_turn | 20 个脚本起步 | 收紧、放宽、数量变化、等待确认、暂停/取消 |
| isolation_recovery | 覆盖规格书相关全部验收项 | 两用户相反反馈、晚到、重复事件、崩溃、撤权 |

这些数量是建设起点，不是统计充分性保证。实际样本量取决于目标误差率、业务分组和置信要求；不能认为“1000 张总样本”就等于每种水印都有足够证据。

### 4.2 数据分组和冻结

数据至少分为开发集、验证集、锁定验收集。可从 60%/20%/20% 的比例开始，但小样本业务需专门补充，不能机械切分后导致关键场景只有几例。

- 相同原视频、同一素材的裁剪/压缩变体、近重复簇尽量按组划分，防止跨集合泄漏。
- 人工设置的去重用例本身可以包含同簇样本，但不能让其近重复副本泄漏到调参集作为“未知验收样本”。
- 锁定需求文本、标签、素材版本、库目录、索引快照和权限夹具；生成数据摘要。
- MLflow 数据集可以更新，因此发布评测不能只记录一个可变名称。额外保存不可变导出清单、摘要和冻结日期。
- 修改标签或新增生产坏例后生成新基线；不得覆盖旧评测的标准答案。
- 真实失败样本可经审批加入开发/回归集，但不能无节制地把所有已见失败加入保密验收集再反复调优。

MLflow 支持以人工样例和历史 Trace 构建评测数据集，并关联 expectations；本项目在此基础上补充素材快照和防泄漏规则。[Evaluation Datasets](https://mlflow.org/docs/latest/genai/datasets/)

### 4.3 标注规则

每个需求标注：硬条件、禁止项、偏好、来源/风格解释、计数单位、允许的澄清、相关库集合和可满足性类型。

每个素材标注：规则级 pass/fail/unknown、证据、媒体版本、视频时间区间、重复簇及许可范围。主观风格需先定义 rubric，例如“明显符合/部分符合/不符合/无法判断”，再由业务确定如何映射验收结果。

建议关键样本双人独立标注并仲裁分歧；记录标注者、标准版本和修订原因。用户“喜欢/不喜欢”可作为体验反馈，但不能直接等同于所有硬条件的标准答案。

验收人员尽量不知道被测版本名称。测试输入中不暴露标准标签、正确素材列表或期望库给 Agent；这些仅由测试驱动器和评分器读取。

### 4.4 用例数据结构示例

以下为业务侧用例契约，不是要求原样提交给 MLflow SDK。适配器将允许的字段映射至 `inputs`、`expectations` 和元数据。

  "suite_version": "golden-2026-10-v1",

  },

  },
  "expectations": {
    "source_constraint": null,
    "style_intent": "小红书风格",
    "must": ["室内家居", "无水印"],

## 5. 测试驱动器与真实输出契约

### 5.1 评测入口不直接读取 Agent 自述

一条端到端用例应完成：

1. 初始化隔离的测试命名空间、数据快照、身份和预算。
2. 通过正常业务 API 创建检索任务，不跳过权限层。
3. 按脚本回答确认、提交反馈、触发允许的故障。
4. 在受限期限内等待业务终态；超时记录为失败/超时，不能从平均分中消失。
5. 获取数据库或正式结果 API 的快照、候选判定和执行账本。
6. 生成统一评测输出，交给评分器，与 MLflow Run/Trace 关联。
7. 仅清理本次隔离测试资源，保留报告和必要失败证据。

可封装成 `predict_fn`，也可先批量运行长任务，再将预生成输出与 Trace 交给评测流程。不要让“每行评测”默认创建无上限在线长任务。

### 5.2 评测输出最低字段

| 字段 | 用途 |
| --- | --- |
| case_id、task_id、revision、generation | 精确对应测试案例和业务版本 |
| final_state、stop_reason、timeout | 区分完成、部分结果、故障和超时 |
| parsed_spec、selected_libraries | 评估理解、路由和未经批准的条件变化 |
| result_manifest_ref/digest | 独立复核实际交付内容 |
| reported_accepted_count | 系统自报值，用于核对而非直接当质量答案 |
| validation_manifest、dedup_manifest | 每条规则证据、重复关系与代表选择 |
| rounds、queries、candidate_counts | 还原补数过程和无效重复检索 |
| task_event_ref、permission_audit_ref | 验证晚到、撤权、幂等和跨用户行为 |
| latency、token_usage、compute_usage、cost | 性能和单位有效结果成本 |
| version_manifest、trace_ids | 可复现与定位 |

任何缺失的关键字段应返回“证据不完整”，而不是默认正确。系统自报 100、实际清单 98 条应立即被计数一致性评分器发现。

## 6. MLflow Experiment、Run 与 Trace 组织

### 6.1 建议组织方式

推荐按稳定用途建立 Experiment，例如 `retrieval/offline-quality`、`retrieval/online-canary`、`retrieval/reliability`；不要每次发布都新建一个无法对比的 Experiment。

一次 Run 对应“一个被测版本 + 一个测试集快照 + 一个配置/预算 + 一个重复批次”。case、模块和媒体类型作为记录或标签维度。若执行器产生多个子 Run，需用统一的 comparison_id 关联，不假定所有并行执行天然汇总为一个 Run。

版本清单至少包含：应用提交/构建摘要、DSH、Data-Juicer、内部算子包、模型、提示词/Skill、清洗配方、去重策略、MLflow、评分器、Judge、目录/索引快照、数据集和硬件/执行环境。

### 6.2 Trace 采集建议

MLflow Tracing 支持记录步骤的输入、输出和元数据，并提供 OpenTelemetry 相关能力。业务系统仍需完成适配和上下文传播，不能假设记录最终答案就有全链路证据。[Tracing 文档](https://mlflow.org/docs/latest/genai/tracing/)

建议记录逻辑步骤：需求解析、Skill 加载、扩词、授权选库、查询编码、各库检索、清洗批次、规则判定、历史去重、计数、补数决策、人工确认和快照发布。

- 每个异步操作有 operation_id、attempt_id、task/revision/generation；多个 Trace 用这些键及 parent_operation_id 关联。
- 单次模型调用/Worker 操作可形成独立有界 Trace；不要求暂停数小时的任务保持一个未结束 Span。
- 能正确传播追踪上下文时再建立父子关系；否则保留明确关联表，不伪造一个完整同步调用树。
- Span 记录时间、状态、参数摘要、输入输出引用和错误码；全量媒体与逐条清单存为受控产物。
- LLM token/cost 若无可靠采集则标记缺失或估算，不能记为零。GPU、向量库和算子成本由业务另行上报。
- 不采集隐藏思考过程；简短决策理由和实际动作足够用于审计。

### 6.3 安全和可观测性覆盖

Trace、标签和产物引用可能泄露私有需求或数据来源。脱敏租户/用户标识，限制实验和产物访问，不记录密钥、长效下载链接或未授权素材内容。Experiment 名称和标签不是权限控制。

离线门禁集要求关键阶段证据完整；线上可采样，但安全事件、失败和高费用任务应优先留证。若采样丢失关键证据，应标记不可评分，不能让未观测到的错误算成通过。

## 7. 指标字典：先定义分母再看分数

本文所有指标名是拟建业务指标，不声称 MLflow 自动提供。

### 7.1 需求、选库和检索

| 指标 | 定义/口径 | 注意事项 |
| --- | --- | --- |
| spec_exact_match | 关键字段全部与标准一致的需求数 / 可明确判断需求数 | 把歧义需求另组评测，别奖励乱猜 |
| hard_constraint_preservation | 被正确保留的硬条件数 / 标注硬条件数 | 否定、来源和计数单位单独切片 |
| clarification_correctness | 应澄清且正确澄清的案例比例，并另报不必要澄清率 | 防止系统靠不停提问刷正确率 |
| library_recall_at_k | 选中相关授权库数 / 标注相关授权库数 | 多库需求不能只统计“命中任一库” |
| irrelevant_library_rate | 调用的不相关库数 / 实际调用库数 | 与召回、成本一起看 |
| retrieval_precision_at_k | 前 k 个候选中相关数量 / k | 返回不足 k 时同时报告返回数和 precision@returned |
| retrieval_recall_at_k | 前 k 个候选命中的相关素材数 / 全部相关素材数 | 仅用于标注充分的封闭语料，不在未知大库假报完整召回率 |
| expansion_gain | 同预算下扩词版与原始查询版的合格唯一产出差 | 不用扩词数量或总召回量替代 |

查询未返回素材时，precision@returned 为未定义；recall 在标准相关集非空时为 0。相关集为空的案例独立评价正确空结果/停止行为，不混入普通 recall。

### 7.2 清洗算子

定义正类为“确实违反该规则的素材”，例如有水印。分别报告：

| 指标 | 定义 |
| --- | --- |
| violation_detection_recall | 被正确判 fail 的违规样本 / 全部人工标注违规样本 |
| violation_escape_rate | 被错误判 pass 的违规样本 / 全部人工标注违规样本 |
| valid_false_reject_rate | 被错误判 fail 的合格样本 / 全部人工标注合格样本 |
| unknown_rate | 输出 unknown 的样本 / 全部评测样本 |
| execution_error_rate | 执行错误样本 / 全部执行样本 |
| evidence_coverage | 有完整规定证据的条目 / 应提供证据条目 |

unknown 不能默认为合格，也不能为了提高准确率直接从总报告剔除。违规样本的 fail/pass/unknown 分布都需展示；执行错误另设标记，说明其与 unknown 的映射，避免重复相加。

### 7.3 去重

- pair_precision：判为重复的已标注样本对中，真实重复的比例。
- pair_recall：真实重复的已标注样本对中，被识别出的比例。
- false_merge_cases：不同内容被错误归入同簇的案例与数量。
- delivered_duplicate_rate：按固定人工/规则标准聚类后，交付条目数减去唯一代表数，再除以交付条目数。
- representative_validity：每簇最终代表满足当前规则与授权的比例。

样本对集必须固定正负比例，并包含困难负例；不能用海量明显不同的图片对稀释误合并。单对正确不保证聚类正确，另测 A≈B、B≈C、A不≈C 的链式案例。

### 7.4 交付质量与闭环

设 N 为用户目标；D 为实际交付条目数；V 为独立评测确认“满足全部硬条件且去重后”的有效数。

```text
真实有效交付率 = V / D                      （D > 0）
真实目标完成度 = min(V, N) / N              （N > 0）
单轮边际有效产出率 = 本轮新增有效唯一数 / 本轮返回候选数
单位有效结果成本 = 全任务实际成本 / V        （V > 0）
```

D=0 或 V=0 时单独标记空交付/零产出，保留任务成本与失败状态，不能从汇总中删除。

严格任务成功要求：真实有效数达到目标、必需配额满足、没有未经批准的硬条件放宽，且未违反权限/预算等门禁。人工仅抽检时不能声称已证明每条有效或严格任务成功，只能报告抽检质量估计及不确定性。

对已知可满足任务计算真实达标率；对已知不可满足任务计算正确部分交付/停止率；未知大库任务报告质量、有效产出和成本，不以缺少全库标注为由推断系统已找全。

### 7.5 性能与可靠性

分别记录创建响应、排队时间、首批结果、活跃执行、用户等待、最终完成的 p50/p95；图片/视频、冷/热缓存、目标数量与并发等级分组。

同时记录错误率、超时率、重试率、恢复时间、过期代次提交拦截和证据缺失。只统计成功任务时长会美化系统，应同时展示全体任务终态分布及超时截断情况。

成本至少拆 Agent 推理、清洗模型、CPU/GPU、检索和评测裁判。Judge 成本属于测试成本，不混入被测系统线上成本；未知价格的资源用用量表示并注明，不能伪造精确总金额。

## 8. 评分器设计：程序为主，人工兜底，模型辅助

### 8.1 评分器清单

| 拟建 Scorer | 输入证据 | 判定方式 | 发布作用 |
| --- | --- | --- | --- |
| spec_contract | QuerySpec、标准字段 | 代码校验，歧义语义可人工复核 | 理解效果 |
| authorized_access | 身份夹具、目录/素材访问日志 | 程序断言 | 硬阻断 |
| count_consistency | 当前版本清单、数据库计数、重复关系 | 程序重算 | 硬阻断 |
| revision_isolation | 反馈时间线、generation、结果成员 | 程序断言 | 硬阻断 |
| constraint_fidelity | 初始/确认后规则、实际执行参数 | 结构化比较 + 歧义复核 | 擅自放宽则阻断 |
| operator_quality | 检测输出、人工标签 | 混淆统计、unknown 和证据覆盖 | 分算子门槛 |
| dedup_quality | 固定样本对、小簇和代表标签 | 程序比较 | 漏检/误合并门槛 |
| delivery_quality | 实际交付内容、独立人工标注 | 全量或分层抽检 | 业务质量 |
| refill_effectiveness | 每轮新增素材、判定与成本 | 程序统计 | 对照实验收益 |
| stop_reason_correctness | 可满足性、预算、策略与终态 | 程序判断 + 原因复核 | 不伪报完成 |
| explanation_quality | 最终说明、权威任务摘要 | 模型辅助/人工 | 非核心辅助项 |
| evidence_completeness | 必需日志、清单和版本 | 程序校验 | 证据不足不能通过 |

MLflow 评分器可承载这些业务指标，但逻辑名称不对应现成内置类。不要直接使用通用问答 Correctness 或 groundedness 分数代替图片相关性、视频动作正确性和去重质量。

### 8.2 多模态 Judge 的限制

- 判断图片是否有水印，需要实际图片或可信检测证据；不能仅凭 Agent 的 caption。
- 判断视频动作顺序，需要可访问的片段和时间覆盖证据；单张关键帧不能证明全过程。
- 模型及评测适配器必须明确支持相应媒体输入。媒体只以路径文本传入并不代表 Judge 真正看到了内容。
- 被测模型与 Judge 不宜完全共用同一判断链；即使换了模型，也不能视作天然独立或正确。
- Judge 只读必要、已授权数据；OCR、库描述和用户文本中的指令不得变成裁判规则。
- 媒体不可访问或证据不足时返回不可评分/unknown，不能依据系统自述补猜。

### 8.3 Judge 校准与版本化

从独立人工标注中抽取校准集，记录 Judge 与人工一致率、误判方向及业务分组表现。提示词调优只用校准集，最终验收用独立数据；改变 Judge 后需要重新评估基线与候选版本，不能比较不同裁判体系下的两个分数。

冻结 Judge 模型、提示词、评分 rubric、媒体预处理和版本。固定随机种子只能在支持的组件中减少波动，不能保证外部模型完全确定。

人工作为标准答案、复核意见和真实用户反馈应分别保存，避免“用户不满意”自动覆盖事实标签。MLflow 支持记录反馈；具体标注页面和权限方案按部署版本验证。[反馈文档](https://mlflow.org/docs/latest/genai/assessments/feedback/)

## 9. 对照实验与归因方法

### 9.1 必做的四组对照

| 组别 | 配置 | 主要验证 |
| --- | --- | --- |
| A | 原始查询、固定路由、相同清洗、不补数 | 基线能力 |
| B | A + 业务 Skill 扩词 | 扩词是否提高有效唯一产出 |
| C | B + 固定规则补数 | 简单循环的收益 |
| D | B + Agent 根据损耗原因动态补数 | Agent 决策相对规则策略的增量价值 |

控制相同语料/索引、权限、算子、质量阈值、目标、总预算上限和硬件条件。A/B 的额外调用成本同样计入；除共同上限外，可按相同实际费用区间或产出—成本曲线比较，避免把“多花钱多拿数据”当作智能提升。

初次比较尽量只改变一个因素；动态路由、模型替换和新去重策略另建消融组。不能同时换模型、索引和清洗阈值后把提升全部归因于 Agent。

### 9.2 执行与统计

- 同一个 case 在所有版本上配对执行，使用新的隔离任务状态。
- 随机化版本执行顺序，避免某版本独占热缓存或低负载时间段。
- 明确区分冷缓存质量/性能与热缓存性能；除专门测试复用的场景外，不能共享先前结果绕过本次执行。
- 核心随机场景建议先做 3 次重复，记录均值、波动及最差关键行为；样本不足时继续补充，3 次不是稳定性保证。
- 汇总同时展示整体、业务域、图片/视频、可满足性、难例和目标数量切片，避免平均值掩盖弱项。
- 模型与算子成本不完整的 Run 不参与精确成本排名，标记证据不足。

### 9.3 如何定位失败

1. 使用人工正确 QuerySpec 替换解析输出，判断问题是否来自理解。
2. 固定正确目标库，观察有效产出变化，判断路由损失。
3. 将人工合格素材混入固定候选集，测清洗误杀。
4. 固定清洗标签，单测跨轮去重和数量账本。
5. 固定每轮检索返回，重放规则/Agent 补数决策。

这些诊断实验是“理想输入下的局部测试”，不得当作真实端到端线上效果。其价值在于定位改哪一层，而非美化总指标。

## 10. 多轮、多人、故障与性能测试

### 10.1 固定多轮脚本

示例：初检 100 张室内家居图 → 排除文字 → 允许少量文字 → 只要横图 → 增加到 150 → 暂停 → 恢复。

每个步骤检查需求版本、规则差异、有效集、备选池、复用特征、补数预算及晚到处理。固定脚本用于回归；可选的模型模拟用户用于探索新场景，但模拟输出需审核后才纳入正式标准，不代替固定门禁。

### 10.2 多用户对照

同时运行两个用户：A 排除人物，B 需要人物；同一素材可以得到不同判定。

检查会话、拒绝列表、规则阈值、个人偏好、临时目录、预览链接、缓存和 Trace 访问。还需测试同用户不同任务、同租户无任务权限者、跨租户用户和显式协作用户。

共享检测事实只能在授权范围内发生；不共享用户判定。不能只检查返回内容，还要检查目录描述、计数、错误消息和产物引用是否泄露。

### 10.3 故障注入矩阵

| 故障 | 注入位置 | 必须保持的行为 |
| --- | --- | --- |
| DSH 退出 | 计划前/工具返回后 | 业务账本保留，新会话按摘要恢复 |
| 清洗 Worker 崩溃 | 部分条目完成后 | 已提交条目不重复，缺失条目恢复或明确失败 |
| 协调器接管 | 租约到期 | 旧 fencing token 不再有写权限 |
| 重复完成事件 | 计数前后 | 不重复增加数量或派生补数 |
| 旧 revision 晚到 | 用户更新规则后 | 不污染新版本有效集 |
| 向量库超时 | 指定来源/可选来源 | 有限重试，不偷偷改变来源条件 |
| 权限撤销 | 检索中/导出前 | 后续读取和交付重新授权 |
| MLflow 写入失败 | 评测结束前 | 本地保存产物，报告记录不完整，不伪造绿灯 |

这些场景需要驱动器或专用测试框架实现；MLflow 负责承接结果，不能代替故障注入。

### 10.4 负载模型

先定义用户峰值、到达率、活跃任务数、图片/视频比例、目标数量分布和外部 API 限流。可用低负载 → 目标负载 → 超额负载阶梯测试，具体并发数在容量规划后确定。

区分固定并发用户测试和固定到达率测试：仅在请求完成后再发下一次会隐藏排队问题。报告排队、资源占用、尾延迟、错误率及公平性；单个大任务不能使其他用户长期饥饿。

## 11. 达标门禁与统计判定

### 11.1 三类结论

每项输出 PASS、FAIL 或 INCONCLUSIVE（证据不足）。对生产发布而言，关键项 INCONCLUSIVE 不等于 PASS。

| 门禁 | 初始建议 | 判定方式 |
| --- | --- | --- |
| G0 评测有效性 | 快照、版本、关键证据和标签完整 | 缺失则不可给出最终达标结论 |
| G1 安全/状态 | 规定用例全部通过 | 任一越权、串用户、重复计数、旧版本覆盖即阻断 |
| G2 明确需求理解 | 关键字段完全正确率目标 ≥95% | 独立需求集；歧义另评，不以反复澄清刷分 |
| G3 交付质量 | 一般业务样本级合格率目标 ≥95% | 人工标准及置信区间；高风险条件另设零容忍门禁 |
| G4 清洗/去重 | 每项漏检、误杀、unknown 上限由业务冻结 | 未冻结不能宣布整体达标；不只看平均准确率 |
| G5 补数价值 | 可满足任务的真实达标率不低于批准基线 | 并评价成本、完成时间与人工干预；不可满足任务另组 |
| G6 性能/成本 | 在目标负载下满足已批准 p95 与预算 | 缺少负载和费用依据时仅提供基线，不虚构 SLA |
| G7 版本回归 | 关键难例不回退、整体满足非劣效边界 | 安全/状态不允许用总体分数补偿 |

上述门槛不是已实现指标。若本稿与主规格书门槛不同，以研发评审批准的门槛清单为唯一发布依据，并同步修订两份文档。

### 11.2 置信区间与样本量

比例指标报告分子、分母、点估计和区间。严格验收可预先约定“单侧 95% 置信下界达到门槛”；若点估计达标但区间未达到，结论为证据不足或按预定规则不通过，不能事后换统计方法。

独立样本比例可采用预先选定的二项比例区间；同任务、同视频、同近重复簇样本相关时，按任务/原视频/簇重采样，不把所有帧当作独立样本。版本比较采用案例级配对分析，避免把大任务的素材数当成更多独立需求。

精确计数、授权和版本等规定回归用例必须零失败；这只能说明已覆盖用例通过，不是数学证明系统永远零漏洞。

对未知大库的人工抽检，保留随机/分层采样方法和权重；重点抽查坏例用于诊断，不直接当总体质量估计。新增子分组时须报告样本不足，不用总样本量掩盖。

### 11.3 基线提升与非劣效

先冻结业务可接受的质量下降界限和成本/时延上限，再看结果。Agent 方案即使数量增加，也不能以未经批准的质量下降换取“提升”。

建议发布顺序：先满足绝对质量与安全门槛 → 再证明相对基线不显著退化 → 最后判断新增能力是否值得其成本。若 D 组相对 C 组没有可复现收益，可继续使用规则补数，不必为 Agent 化本身放宽门禁。

## 12. CI/CD 与发布执行建议

MLflow 官方提供将 GenAI 回归评测接入 pytest/CI 的方法；当前文档包含 `@mlflow.test`。采用前需验证冻结版本与插件支持。未支持时保留普通 pytest 断言并记录评测 Run，不强依赖某个新装饰器。[回归测试与 CI/CD](https://mlflow.org/docs/latest/genai/eval-monitor/regression-testing/)

| 触发时机 | 测试内容 | 失败处理 |
| --- | --- | --- |
| 每次代码变更 | L0 契约、关键规则、白名单、幂等和小型固定回归 | 阻止合并 |
| 每次 Skill/模型/配方变更 | 受影响组件 + 关键端到端样例 | 阻止发布，保留失败证据 |
| 每日或定期完整回归 | 固定质量集、多轮、随机核心案例重复 | 报告趋势与新增失败 |
| 候选版本发布前 | 锁定验收集、全部安全/恢复用例、目标负载、人工复核 | 业务与技术联合签字 |
| 小范围灰度 | 真实接受率、质量抽检、成本、异常、权限事件 | 触发门槛后回滚新流量 |

发布流水线的逻辑顺序：冻结版本 → 校验数据 → 运行 → 完整性检查 → 评分 → 切片/区间与基线对比 → 门禁 → 报告 → 审批。

模型评测失败不能无限重跑直到变绿。重试仅按预先批准策略处理基础设施故障；所有原始失败、重试原因和结果都保留。随机性明显的 Judge 分数应由预先定义的重复/聚合和人工复核流程处理。

### 14.3 必须附带的材料

- 逐案例结果、失败清单和已知限制。

## 15. 最小落地步骤与责任分工

| 步骤 | 交付物 | 主责 |
| --- | --- | --- |
| 1. 冻结评价口径 | 指标字典、硬条件、判定规则和门槛草案 | 产品 + 业务 + 测试 |
| 2. 建立首批标注集 | 需求、素材、重复样本、交互脚本及独立验收集 | 业务标注 + 算法 |
| 3. 建立证据接口 | 统一输出、版本清单、Trace 关联、成本字段 | 后端 + Agent/数据工程 |
| 4. 接入 MLflow | SQL Tracking、Experiment、数据集与 Run 组织、访问控制 | 平台/测试工程 |
| 5. 跑基础组件和基线 | 算子报告、固定流水线、A/B/C/D 对照 | 算法 + 测试 |
| 6. 建立发布门禁 | 35 项场景执行、性能/恢复、置信与切片报告 | 测试 + 后端 + SRE |
| 7. 内部试用与迭代 | 人工盲评、失败归因、坏例进入受控回归集 | 产品 + 业务 + 研发 |

首期不必搭建复杂评测 Agent。优先交付可用的测试数据、程序评分器、业务证据和报告，再按价值补充模型裁判与更丰富的标注界面。

建议首个评审会明确五件事：哪些条件零容忍、允许多少误杀、视频计数单位、成本/时延预算、谁有权批准最终发布。没有这些决定，即使接入 MLflow 也只能得到分数，不能判断是否达标。
