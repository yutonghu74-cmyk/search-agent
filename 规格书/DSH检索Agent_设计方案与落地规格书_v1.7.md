> 核心决策：建设一个以 DSH 为推理与工具调用底座的检索 Agent，对外作为独立检索产品提供服务。Agent 负责理解和决策，业务服务负责权限、状态、计数、执行及恢复。过滤和去重发生在候选检索之后；不足时继续检索，并对新旧结果统一清洗、去重和计数。通用算子优先复用 Data-Juicer，业务算子独立维护并按需接入，用户状态和补数控制不放进算子库。

## 1. 设计结论与范围

### 1.1 推荐形态

采用“一个逻辑检索 Agent + 一套持久化业务状态机 + 受控工具与版本化算子”（模型型算子不承诺绝对确定性），不把扩词、选库、清洗、去重、补数各自拆成独立 Agent。

这里的“一个”是一个业务角色与一套能力定义，不是所有用户共享同一个会话。每个任务有自己的会话、需求版本、候选池和执行状态，可由多个运行实例并发承载。

DSH 是本方案必选的 Agent 运行底座；LangGraph 不是必选依赖，不再增加第二套 Agent 循环。长任务可靠性由外部业务状态机、数据库和任务队列保证，这并不意味着重新实现 DSH 的模型推理循环。

| 决策 | 规格 |
| --- | --- |
| 产品边界 | 独立前端、业务 API 和数据库；通过适配层调用 DSH |
| Agent 边界 | 理解诉求、选择业务 Skill、提出检索计划、分析损耗、提出下一步动作 |
| 执行边界 | 后端校验计划、调用向量库、执行清洗、维护去重关系、计算数量，管理任务执行限制 |
| 算子边界 | Data-Juicer 执行已批准的检测/过滤配方；内部扩展包承载业务算法，不以长期修改上游核心为默认方案 |
| 结果边界 | 检测事实与任务判定分离；跨轮去重、代表样本选择和计数由结果集服务负责 |
| 数据权威 | PostgreSQL 是任务、权限策略及交付关系的事实来源；Milvus 保存检索向量；DSH 对话不是唯一任务账本 |
| 用户隔离 | 身份认证、资源授权、会话隔离、缓存隔离、反馈作用域共同实现 |
| 版本策略 | 固定验证过的 DSH 发布物，隔离适配层，禁止生产自动跟随最新版本 |
| 缺口处理 | 先在授权库内补检索；不能满足时交付部分结果并解释，或申请离线补数 |
| 人工参与 | 可确认需求、修改条件、拒绝样本、批准扩范围、暂停及恢复；额外费用仅在适用时确认 |

### 1.2 目标范围与阶段承诺

以下八项为完整目标范围，按 P0—P4 分期交付；不表示 P1 已包含全部能力。首个多人生产版本为 P1+P2，默认仅开放图片与一个已验证业务域。视频、配额及跨任务特征共享在 P3 开放；训练平台正式发布与缺口单闭环在 P4 开放。若业务要求首个生产版本支持视频，应显式将视频工作包及对应验收整体前移，重新评审资源和排期。

完整目标范围：

1. 自然语言需求解析、歧义处理及结构化确认。
2. 库目录检索，即“先找适合检索的库，再检索库中的素材”。
3. 按业务加载扩词 Skill，保留原始语义和否定条件。
4. 图片、视频各自的向量检索适配，以及不同 embedding 空间的正确使用。
5. 检索后的多轮清洗、精确去重、近重复处理和结果计数。
6. 数量不足时按损耗原因补数，跨轮次、跨库去重。
7. 多人并发、用户反馈隔离、版本化、失败恢复、审计和可观测性。
8. 导出可复现的数据集清单，预留数据生产与训练评测平台接口。

各阶段均不默认提供：自动抓取外部网站、自动改变素材授权、在线修改共享 Skill、自动训练模型、将所有平台模块改成 Agent、让模型自由执行脚本。上述能力未来均需独立权限和验收，不因存在 Agent 而默认开放。

### 1.3 关于全链路的衔接

历史诉求中的“问题分析 → 数据生产 → 训练 → 评测”保留为平台级闭环；本规格书详细落地其中的检索与数据筛选子闭环。

- 上游：人工需求或评测问题单，可携带失败类型、目标分布和示例。
- 当前模块：发现与选择已有数据，输出带版本的数据集清单和缺口报告。
- 下游：多个检索任务、生产管道的数据由数据集组装服务合并，再做全局去重与训练/评测集合隔离。
- 训练服务：只消费已批准的不可变数据集版本；检索任务更新不直接改变运行中的训练任务。
- 评测服务：问题分析可以创建新的检索需求，不直接授权无限补数和训练。

检索 Agent 对“当前任务交付的数据”负责，不对“所有训练管道的数据已经完成全局去重”作保证。

## 2. 需求追踪与业务不变量

| 编号 | 历史需求 | 本方案落点 |
| --- | --- | --- |
| R01 | 用户任意自然语言检索 | 结构化需求、明确硬约束、必要时澄清 |
| R02 | 图片和视频分别已有 embedding | 媒体适配器、匹配的查询编码器、模型版本校验 |
| R03 | 每个库有简介、关键词、业务属性 | 可检索 Library Catalog，授权后路由 |
| R04 | 不同业务使用不同扩词 Skill | 版本化 Skill 与受约束的扩词方案 |
| R05 | 检索词自动清理 | 分离原文、标准化词、扩展词、排除条件及来源 |
| R06 | 过滤去重放在检索之后 | 候选落库后执行，安全授权不属于清洗 |
| R07 | 按反馈多次清洗 | 不可变需求 revision，重算当前有效集 |
| R08 | 清洗后不足继续补数 | 边际有效产出率驱动补检索，跨轮统一去重 |
| R09 | 多人同时使用、反馈不同 | 租户/用户/任务/版本隔离，禁止共享隐式记忆 |
| R10 | DSH 版本不稳定，避免大改 | 独立业务服务 + 薄适配层 + 契约测试 |
| R11 | 可穿插人工，也能自动子闭环 | 受控动作集、人工确认点、任务执行限制和停止条件 |
| R12 | 未来进入训练评测闭环 | 数据集快照、血缘、缺口单与下游事件契约 |
| R13 | 清洗能力复用 Data-Juicer | 独立清洗执行服务、外部业务算子包、在线/离线共用算法与配方 |

必须长期保持的业务不变量：

1. 未授权的库、素材、描述、缩略图和统计信息不进入用户会话或模型上下文。
2. `accepted_count` 只统计当前需求版本下，通过所有硬约束、已处理重复关系、仍有访问权的结果。
3. 新反馈不会静默修改旧版本；旧任务结果不能冒充新版本验收结果。
4. 模型不能直接修改有效数量、放宽硬约束、更改服务端执行限制或指定其他用户身份。
5. 检索与清洗只生成结果视图及判定记录，不删除源库素材。
6. 不同 embedding 空间不能直接混用查询向量；不同库的原始相似度不能无校准直接比较。
7. 自动结束必须携带明确原因，不能把执行限制已达到表述成“所有库都没有数据”。

## 3. DSH 能力依据与使用边界

### 3.1 已确认的公开能力

DSH 官方将项目定位为插件化 Agent Harness，并明确标注 developer preview、可能出现兼容性破坏。因此，本方案将它放在可替换的运行时边界内，而非让业务表结构依赖其内部会话格式。[官方项目说明](https://github.com/deepseek-ai/deepseek-harness)

| DSH 能力 | 本方案如何使用 | 不应据此推断的能力 |
| --- | --- | --- |
| 插件与工具扩展 | 注册受限的检索业务工具 | 不代表工具自动获得业务授权与事务保障 |
| 进程外 SDK、会话和事件 | 业务适配层启动运行时、投递需求、接收事件 | 不代表生产级多租户网关已经具备 |
| Skill 发现与按需加载 | 加载已发布的业务扩词和筛选指导 | 不代表 Skill 是安全策略引擎 |
| 会话所属的后台 jobs | 可辅助展示当前会话工作 | 不代替持久化业务队列和跨进程恢复 |

SDK 文档说明其通过换行分隔的 JSON-RPC 驱动运行时，TypeScript 客户端支持以命名 profile 和配置补丁启动；Python SDK 使用同一协议。[SDK 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/README.md)

Skill 文档说明可通过 provider 合并目录并按需加载指令；本方案在其上增加租户授权、版本发布和任务绑定。[Skill 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/skill/README.md)

Jobs 文档中的 `jobs-local` 为进程本地存储。本方案的检索批次、清洗作业及恢复记录必须持久化在业务侧。[Jobs 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/jobs/README.md)

### 3.2 版本基线说明

前序只读核对发现，本地源码目录的 CLI 包清单标记为 `0.2.0-rc.2`。这不是实际部署版本或已通过验收的证明，也未确认对应上游提交。按照用户要求，本次继续编制不再查看 DSH 源码。

本文所有 `retrieval.*` 工具名、业务 API、表名、适配层方法名均为拟建契约，不是声称 DSH 已有这些接口。正式开发前需冻结运行时发布物、依赖锁文件和构建摘要，并在选定版本上验证启动、工具注册、Skill 加载、取消和事件订阅。

### 3.3 Data-Juicer 能力依据与版本边界

Data-Juicer 官方提供多模态算子目录、可组合处理流程和外部自定义算子接入。开发指南提供 `custom_operator_paths` 方式；v1.5.5 发布说明引入通过 Python entry points 加载独立算子包的能力。正式开发按实际锁定版本验证其中一种，不假设旧版本拥有所有接口。[开发指南](https://github.com/datajuicer/data-juicer/blob/main/docs/DeveloperGuide.md)、[v1.5.5 发布说明](https://github.com/datajuicer/data-juicer/releases/tag/v1.5.5)

官方 Filter 示例将统计计算与过滤处理分开，本方案借鉴该结构，但“跨用户安全缓存、三态业务判定、跨轮结果账本”需要自行补建。官方图片/视频 deduplicator 的精确匹配能力不能直接等同于视觉近重复或视频片段重叠去重。[开发指南](https://github.com/datajuicer/data-juicer/blob/main/docs/DeveloperGuide.md)、[算子目录](https://github.com/datajuicer/data-juicer/blob/main/docs/Operators.md)

本稿未确认团队已安装的 Data-Juicer 版本，也未实际验证任何算子效果。本文中的内部算子名称和服务接口是设计契约；上线前冻结框架、扩展包、模型权重、执行环境和配方版本。

## 4. 总体架构与模块职责

### 4.1 主链路

主链路按已批准计划连续执行，Agent 在规划与策略变化时参与。箭头表示调用或数据流，所有访问仍由业务服务授权。

```text
用户 / 上游需求
    ↓
独立检索界面 → 认证与业务 API → 任务库 / 需求版本 / 审计
    ↓
需求解析与确认（DSH 适配层 → 检索 Agent / 业务 Skill）
    ↓
授权目录发现 → 库能力匹配 → Agent 计划提案 → 后端校验与计划冻结
    ↓
任务协调器 / 业务状态机
    ↓
持久化执行队列 → Retrieval Worker → 计划绑定的向量库
    ↓
命中映射 / 当前授权校验 / 候选与来源入库
    ↓
已见媒体单元识别 → 兼容检测事实查询 → 低成本检查
    ↓
必要的模型检测（清洗执行服务：Data-Juicer / 内部算子）
    ↓
结果集服务：当前规则判定 → 跨轮去重 → 排序/配额 → 计数
    ├→ 发布版本化预览 → 用户反馈 / 人工复核 → 重验与新预览
    ↓
协调器根据已完成统计及损耗执行已批准策略
    ├→ 不足且可继续：补批 / 翻页 / 合法重试 → 执行队列
    ├→ 策略需调整：受控摘要 → Agent 新提案 → 后端校验
    ├→ 需用户批准：持久化确认请求 → 等待确认
    ↓ 达标或明确停止
最终校验 → 完整/部分交付快照 → 不足说明 / 缺口报告
                                         ↓ 另行申请与批准
                                    离线数据生产

素材服务向 Worker 提供授权读取。
P1 可串行小批执行；P2 验证通过后允许检索与清洗有界重叠。
```

目录发现发生在规划或批准的重新规划阶段。检索 Worker 执行固定物理绑定、查询编码器、查询参数及过滤模板；每批重新核查权限，但不在执行中自行重新选库。预览发布不等于任务完成；最终交付经第 13.5.1 节发布流程后才可导出。

### 4.1.1 用户流程与后端执行关系

```text
检索词扩词 → 检索 → 清洗（DJ） → 补数 → 打包
              ↑                    │
              └── 补数计划批准后 ──┘
                 再检索仍需再清洗
```

任务详情页以五主节点为入口，每个节点可点击查看输入、实时输出、执行记录及推进门禁。扩词节点同时展示授权目录选择与查询分支；检索 Worker 使用后端批准绑定。清洗计算由 DJ 和内部算子执行；规则判定、跨轮去重、选样、计数及节点审批仍由业务服务负责。

每次补数产生新的 iteration 和检索/清洗节点实例，主图保持五节点，展开可看各轮。补数节点输出缺口分析和下一步计划，批准后启动新一轮检索，或进入打包；无需补数时仍显示节点及其门禁。节点运行中实时查看和完成后批准相互独立，查看结果不代表允许继续执行。

### 4.2 组件划分

| 组件 | 职责 | 禁止承担的职责 |
| --- | --- | --- |
| 检索 UI | 提交诉求、条件卡片、样本预览、反馈、进度、导出 | 直接连接向量库或暴露 DSH 管理端 |
| 业务 API | 身份认证、授权、幂等、输入校验、任务查询 | 信任模型提供的用户 ID |
| 任务协调器 | 状态转换、批准策略执行、损耗统计、补数、背压、租约及恢复；按触发条件唤醒 Agent | 自行改写用户明确约束 |
| DSH 适配层 | 隔离 SDK 差异、会话映射、事件规范化、工具上下文 | 存放唯一一份任务进度 |
| 检索 Agent | 理解意图、选择 Skill、规划及异常策略调整、分析反馈；常规批次完成不必调用模型 | 自行执行任意代码、直接操作业务表 |
| Library Catalog | 库元信息、权限、检索能力、模型版本、健康状态 | 把未经授权的库介绍送入 LLM |
| Retrieval Gateway / Worker | 按已批准物理绑定检索、权限复核、游标、限流、统一返回；不自行发现或切换库 | 以统一向量查询不兼容的模型空间 |
| 清洗执行服务 | 通过 Data-Juicer 适配器运行算子，返回检测事实、逐条判定和错误 | 管理用户任务状态、决定补数或直接发布最终结果 |
| 内部业务算子包 | 可复用算法核心、Data-Juicer 包装、业务语义验证、特征计算 | 保存用户历史、修改权限、运行时安装未批准依赖 |
| 清洗策略编译器 | 将已批准规则映射为白名单配方，校验参数、成本和依赖 | 直接执行模型生成的任意 YAML、脚本或模块路径 |
| 结果集服务 | 判定记录、重复簇、计数、快照、导出 | 用 LLM 输出的数量覆盖数据库统计 |
| 配置与 Skill 注册表 | 已发布版本、适用业务、审批与回滚 | 自动把一个用户反馈推广为全局规则 |

建议初期采用模块化单体业务服务 + 独立 Worker + 独立 DSH 运行进程。业务数据库采用 PostgreSQL；队列使用团队已有可靠方案；图片/视频 embedding 保留在现有 Milvus，素材继续使用现有媒体存储。无需为每个模块新建微服务，也无需迁移已有向量库。清洗执行服务是独立逻辑边界，可先采用队列驱动的 Python Worker 部署；不必为每个算子建服务，也不必额外引入清洗 Agent。

### 4.3 存储架构决策

本期采用“PostgreSQL 管业务、Milvus 管向量、现有媒体存储管文件”。这是结合已有 Milvus 的设计选择，不是断言 PostgreSQL 无法检索向量，也不构成容量或性能已达标的承诺。

| 存储 | 权威职责 | 不承担的职责 |
| --- | --- | --- |
| PostgreSQL | 业务库目录与授权策略、媒体映射、任务/需求版本、检索命中、判定、去重关系、结果清单、事件和用量账本 | 默认不复制全量 embedding，不保存大体积视频/图片二进制 |
| 现有 Milvus | 图片/视频/帧/片段的 embedding、检索索引及必要的标量过滤副本 | 不作为任务状态、用户反馈或最终交付数量的权威账本 |
| 现有媒体/对象存储 | 原始媒体、缩略图、大型特征或证据、导出清单文件 | 不代替关系约束与任务事务 |
| Redis（可选） | 可丢弃缓存、加速和限流辅助 | 不作为唯一任务状态、结果清单或持久化恢复依据 |

已有身份系统、素材主数据和授权系统继续作为各自领域的权威来源；PostgreSQL 保存业务关联及可追溯版本，不另建一份人工独立维护的账号/素材主库。业务权限撤销须即时阻断访问，不能只等待检索字段同步。

PostgreSQL 可借助 pgvector 存储和检索向量，但本期不要求安装。若库介绍将来需要向量化，优先评估现有 Milvus 的独立目录 collection；只有经验证确有收益才引入 pgvector，不为少量库介绍增加第二套必需的向量检索基础设施。[pgvector 官方文档](https://github.com/pgvector/pgvector)

Milvus 可保存并索引标量字段用于缩小检索范围；这些字段的更新来源、可见水位和授权语义必须登记，不能让 Milvus 与业务服务各自维护一套冲突规则。[Milvus 标量索引文档](https://milvus.io/docs/scalar_index.md)

## 5. 需求解析与检索词处理规格

### 5.1 结构化需求 QuerySpec

LLM 负责从原文提出结构化需求；后端进行 schema、权限、取值和矛盾校验。高风险歧义须经用户确认。原始文本不可被标准化结果覆盖。

下列为业务契约示例，不是 DSH 配置：

```json
{
  "schema_version": "query-spec@1",
  "raw_request": "找100张小红书风格的室内家居图，不要水印，横图优先",
  "media_type": "image",
  "count_unit": "image",
  "target_count": 100,
  "quotas": [],
  "business_domain": "home_lifestyle",
  "source_constraints": [],
  "rules": [
    {"rule_id": "r1", "predicate_ref": "scene.indoor@1", "operator": "eq", "value": true, "hardness": "hard", "origin": "user_explicit"},
    {"rule_id": "r2", "predicate_ref": "subject.home@1", "operator": "eq", "value": true, "hardness": "hard", "origin": "user_explicit"},
    {"rule_id": "r3", "predicate_ref": "watermark.present@1", "operator": "eq", "value": false, "hardness": "hard", "origin": "user_explicit"},
    {"rule_id": "r4", "predicate_ref": "style.home_lifestyle@1", "operator": "eq", "value": true, "hardness": "hard", "origin": "user_explicit"}
  ],
  "preferences": [{"field": "orientation", "value": "landscape"}],
  "query_seeds": ["室内家居"],
  "dedup_policy": "visual-near-duplicate-v1",
  "unknown_policy": "hold_for_review",
  "allow_auto_refill": true
}
```

身份、任务、revision、revision_status、授权上下文和 execution_policy_ref 位于服务端 RequestEnvelope，不属于模型可提交的 QuerySpec。Skill、模型、配方及排序版本位于服务端 ExecutionBinding。模型只能提出 QuerySpec 草案，不能决定版本已生效。上述 predicate_ref 为拟建规则注册项，须在 P0 绑定经过验证的检测/人工证据要求；不表示已有算子或已达到风格识别质量。用户无需填写执行额度或内部策略名称。

空 quotas 表示只要求总量。P1/P2 不支持分组配额时，对含配额诉求返回 QUOTA_NOT_SUPPORTED 并说明能力范围，不能静默丢弃；P3 启用后按第 8.6 节的结构与规则执行。

### 5.1.1 规则与版本契约

QuerySpec 使用严格 JSON Schema；P0 冻结 schema 文件并作为模型输出、API 和配方编译器的共同输入。结构约束和业务校验分层执行：

| 字段 | 约束与处理 |
| --- | --- |
| schema_version | 必填；未知主版本拒绝，不尝试猜测兼容 |
| raw_request | 保留原文；非空，长度上限由输入能力配置确定 |
| media_type / count_unit | P1/P2 仅 image/image；P3 支持 video/clip 或 video/distinct_video；不接受不兼容组合 |
| target_count | 大于零的整数；超出已验证服务能力时返回能力说明，不静默截断 |
| rules | 每项有唯一 rule_id、注册 predicate_ref、operator、类型匹配的 value、hardness、origin；否定用显式布尔值或注册否定操作表达 |
| preferences | 只影响排序；field/value 须注册。不能靠偏好补偿硬规则失败 |
| source_constraints | 类型化来源命名空间、来源值及证据要求；与素材授权分开校验 |
| quotas | P1/P2 必须为空；P3 的互斥维度及目标和按第 8.6 节校验 |
| query_seeds | 检索提示，不能作为硬规则通过证据 |
| dedup_policy / unknown_policy | 只能引用当前业务已批准策略；unknown_policy 初期仅 hold_for_review |
| allow_auto_refill | false 时完成已批准首批后按真实数量完整或部分交付；后续补数须显式继续 |

规则注册表保存 predicate_ref、类型、合法操作、单位、证据覆盖要求、可用验证器、支持阶段及负责人。规则的硬/软属性在确认卡片上显示；本示例将风格作为硬要求，业务若允许其仅为偏好须经需求确认。无法执行的硬规则返回 UNSUPPORTED_RULE 或等待明确人工验证路径，禁止编译时丢弃。未提供的可选字段以 schema 声明的默认值归一化；未知字段拒绝并指出位置。

版本确认前生成 normalized_spec，明确填入默认值；对象键稳定排序、UTF-8 编码、禁止 NaN/Infinity，数组保持顺序，单位在规范化时统一；P0 固定规范化实现和测试向量，再对规范化字节生成 SHA-256。原文保留在需求记录，spec_digest 覆盖完整规范化 QuerySpec；单规则缓存使用 rule_digest，并加入证据及验证器策略摘要，不能只按 rule_id 复用。confirmation 的 proposal_digest 还覆盖 base_revision、请求批准的范围/用途/费用以及当前提案版本。

同一 schema 主版本只允许已声明的兼容演进；旧需求按原 schema 读取，升级通过显式迁移产生新草案，保留迁移映射和旧摘要。原自然语言 must/must_not 只作为 UI 表达，不再作为执行器输入。

### 5.2 必须区分的语义

| 用户表述 | 解析策略 |
| --- | --- |
| “小红书来源的图片” | 来源硬约束；只能使用有明确来源证据且被授权的素材 |
| “小红书风格的图片” | 风格需求；可以在其他授权库寻找，不能擅自变成来源约束 |
| “专业摄影作品” | 先区分拍摄来源/作者资质与视觉质量诉求；前者需来源证据，后者形成质量规则。库名称只作路由提示 |
| “不要文字” | 排除条件，不得在关键词清理时丢失“不要” |
| “横图优先” | 排序偏好，不等于禁止竖图 |
| “只要横图” | 硬约束 |
| “给我100段视频” | 明确计数是片段还是不同原始视频；不明时询问 |
| “和这些相似，但不要同一张” | 相似检索与近重复排除同时成立，不可只看相似度 |

缺失的数量可使用界面明示的默认值；涉及来源、授权、视频计数单位、矛盾硬条件时不能靠隐式默认绕过。

### 5.3 扩词、关键词清理与查询组合

处理顺序：原文留存 → 抽取实体/否定/数量/条件 → 词语标准化 → 业务 Skill 扩展 → 硬条件一致性校验 → 生成多路查询。

- 标准化：修正明确错别字、统一同义词、合并重复表达；保留产品编号、专名、时间范围和否定。
- 扩词：区分同义词、视觉属性、场景、构图、业务关联词；每个扩展词记录来源、类型和权重。
- 原始语义保留：保留一条原始核心查询路径，不只依赖扩词结果。
- 多查询：原始主题、场景变体和属性变体分别检索，不能把所有词拼成一条超长文本。
- 排除条件：写入后置验证规则，不假设 embedding 相似度能够可靠表达否定。
- 查询去重：对标准化后的查询形成指纹，避免补数时重复发出等价查询。
- 可追溯：记录某个扩词带来的候选量、通过量、去重后新增量，用于后续评估。

输出至少包含 `query_text`、`query_role`、`source_term`、`skill_version`、`intended_libraries`、`constraint_refs`。模型置信度只作诊断，不作为自动通过硬约束的证据。

## 6. 库目录与多模态检索规格

### 6.1 Library Catalog：索引的索引

不让 Agent 记住所有库。建设授权可过滤的库目录，每个库至少包含：

| 字段组 | 必填内容 |
| --- | --- |
| 标识与版本 | library_id、catalog_version、负责人、更新状态 |
| 物理绑定 | milvus_connection_ref、database/collection、业务范围过滤模板、index_version；凭证存密钥服务，不写入目录或模型上下文 |
| 业务描述 | 名称、简介、适用业务、别名、正反例、来源属性、风格标签 |
| 权限 | tenant_scope、项目/角色访问规则、素材授权用途 |
| 媒体 | image/video、视频粒度是整段/片段/帧、计数映射 |
| Embedding | model_id、model_version、query_encoder_id、维度、距离度量、预处理版本 |
| 检索能力 | 支持的过滤字段、top_k 上限、游标/翻页能力、混合检索能力 |
| 数据状态 | 可用性、更新水位、索引版本、快照读取能力、游标所属版本、粗略规模、费用类别 |
| 验证能力 | 元数据完整性、OCR/水印等预计算特征可用性 |

库目录首先保存于 PostgreSQL，初期使用授权过滤、标签/别名/关键词匹配和必要的 LLM 路由；目录语义召回为可选增强，不是 P1 必需条件。若启用，库介绍 embedding 与库内媒体 embedding 是两套独立用途，须独立管理并使用匹配的编码器。

### 6.2 路由步骤

1. 业务服务先计算用户有权访问的库集合。
2. 在该集合内执行别名/关键词召回；启用目录语义检索时再融合其结果。没有可靠授权过滤能力时，采用授权分区或仅对已授权目录做匹配；不把越权目录交给模型后再删除。
3. 合并结果，按明确来源约束、媒体类型、模型能力、业务匹配度和健康情况筛选。
4. Agent 可在候选库内提出选择及理由；后端再次检查权限和可执行性。
5. 初次选择少量库；不足时扩展到其他相关且已授权的库。

“用户提到小红书，就只查名字里有小红书的库”不是完整路由规则：可能存在别名、混合来源库，也可能用户只是表达风格。系统须保留选库证据和排除原因，便于纠错。

### 6.3 图片和视频的查询适配

每个库必须明确文本查询如何进入其向量空间。已完成媒体 embedding 不等于天然支持文本检索：只有配置了匹配的文本编码器或经过验证的跨模态检索链路，才能执行文本到媒体搜索。缺少这一条件的库需补齐能力或采用已有的 caption/OCR 文本索引，不能把任意文本向量直接用于检索。

- 不同模型或版本分别编码；查询缓存也必须带模型与预处理版本。
- 多库融合优先采用排名融合或经过验证的分数校准；不直接排序不同空间的原始相似度。
- 图片候选包含原素材 ID、库 ID、缩略图引用、原始尺寸和检索证据。
- 视频候选包含原视频 ID、片段起止时间、命中帧/片段、媒体版本和可访问引用。
- 帧级命中要先聚合为合法片段再计数；不能把 30 个命中帧算成 30 个视频。
- 涉及时序动作，例如“先拿起杯子再喝水”，须按片段验证；单帧相似不能证明时序要求。

### 6.4 关于“过滤在检索后”的准确边界

业务内容过滤、质量清洗和去重，均放在候选检索之后。权限、租户边界、合法资源范围是检索的前置安全条件，不能等到检索后才处理。

用户明确指定的库、媒体类型和时间范围可作为查询边界下推，但后端仍需验证返回素材满足条件。这不等于在检索前对用户结果做清洗。

### 6.5 任务内索引版本与游标一致性

每个检索计划绑定各参与库的 index_version，批次记录实际读取版本。catalog_version、embedding/model_version 与 index_version 分别表示目录、向量空间和数据索引的变化，不能互相替代。

| 库能力 | 执行规则 |
| --- | --- |
| 支持快照读取 | 计划固定 snapshot_id/index_version，后续轮次在同一快照翻页 |
| 仅支持稳定版本游标 | 游标与库、索引版本、查询指纹及排序参数绑定；版本不同禁止复用 |
| 不支持版本固定 | 标记 live 模式；保存每批读取时间、可获得的版本/水位及原始命中，明确可复现性受限 |

执行前发现索引变化且原读取契约已失效，或已批准切换新版本：停止使用旧游标，为受影响分支建立新的计划 epoch，重新检索并与任务已见候选及历史重复关系合并。保留旧批次证据，不清空任务进度，也不将重复返回计为新增。

如果快照已过期且原版本不可读取，返回 INDEX_SNAPSHOT_EXPIRED；默认暂停受影响分支，由既定自动策略或用户选择切换新版本。向量空间模型变化时必须重新验证查询编码器，不能只重置游标。

live 模式下禁止声称已穷尽全库；同一任务中的多版本读取在结果清单里可追溯。索引频繁变化导致反复重启时，采用后台排队/退避或报告暂时无法稳定检索，不无限重置搜索进度。

### 6.6 业务库与 Milvus 的物理绑定

“库”是业务检索入口，不强制与 Milvus collection 一一对应。同一 collection 的不同授权业务范围可以注册为不同 library；一个 library 也可通过显式绑定访问多个经过验证的物理目标。初期优先采用最简单的既有映射，不为每个用户复制 collection 或 embedding。

- 同一 collection 内以过滤条件区分业务范围时，过滤模板由后端白名单编译，不接受模型传来的任意过滤表达式。
- 不兼容向量空间必须隔离到明确的 collection 或向量字段等物理目标；每个目标登记维度、距离度量、模型/预处理及查询编码器，不因为同属一个业务库就共享查询向量。
- 物理绑定记录具体 collection 及字段，别名切换也要记录实际目标。index_version 是业务版本契约，不假设 Milvus 原生提供任意历史快照或稳定分页；按部署版本实测能力执行第 6.5 节。
- 同一素材来自多个索引时，统一映射后记录多个 candidate_hit，不重复增加候选与有效数量。
- 用户/租户权限先确定可检索范围，召回后再校验候选可见性；无法安全限定的分支关闭，不用“稍后清洗掉”作为越权兜底。

### 6.7 检索连接器能力与分支进度

P0 对每个物理绑定交付 RetrievalConnectorCapability 和契约测试证据。版本信息来自实际部署；缺失能力必须显式登记，不能用通用参数名假设已经实现。

| 能力 | 必须登记 |
| --- | --- |
| 查询空间 | 查询编码器、模型摘要、预处理、维度、距离、支持文本/例图的方式 |
| 范围限定 | 可下推字段、授权过滤生成方式、过滤表达式/已见 ID 集合大小限制 |
| 读取深度 | single_topk / offset / iterator / snapshot_cursor 中实际验证的方式、单页与总深度上限 |
| 一致性 | snapshot / stable_cursor / live、读取水位、游标寿命及断线恢复能力 |
| ANN 参数 | 允许参数、固定策略版本、近似检索的漏检及重复返回基线 |
| 失败语义 | 超时、限流、部分失败、游标过期、依赖不可用；是否安全重试及退避策略 |

批次返回 hits、next_cursor、has_more（true/false/unknown）、read_watermark、read_mode、actual_target、stop_reason 和原始命中证据。has_more=false 只表示当前查询及连接器可访问深度已耗尽，不证明全库不存在合格素材；live 或无法证明时使用 unknown。

分支进度绑定 plan_epoch、物理目标、查询指纹、参数摘要和已读位置。达到 top_k/读取深度限制应标记 DEPTH_LIMIT，不标记语料耗尽；新查询或参数变更生成新分支。快照仍可读时固定快照继续，只有读取契约失效或显式切换时才新建 epoch，不能因线上新增数据就无条件重置固定快照分支。

P0 用固定测试库检验重复第一页、深度上限、索引切换、迭代器失效和权限过滤。P1 只启用验证通过的连接器；批次去重后无新增的原因须区分命中重复、清洗损耗、深度限制和权限/依赖故障。

## 7. 检索后清洗、去重与结果集

### 7.1 推荐执行顺序

```text
候选检索 → 命中映射/授权校验 → 候选入库与来源记录
         → 已见媒体单元识别 → 兼容检测事实查询
         → 必要的授权下载/解码/内容哈希 → 精确重复识别
         → 低成本元数据与质量筛选 → 缺失事实的模型检测
         → 当前规则下的内容、排除条件与视频时序判定
         → 近重复聚类与代表样本选择
         → 偏好排序/配额选择 → 当前版本有效集 → 数量检查
```

精确去重提前是为避免重复支付后续算子成本，但它仍发生在候选检索后。Data-Juicer 可参与哈希/特征计算及批内重复识别；结果集服务维护跨轮历史关系，不能只把每一批独立去重后相加。来源不同的同内容素材保留各自血缘与授权，不因内容相同就把无授权副本替换进结果。

同 unit_id 再次命中仅补 candidate_hit，若当前规则所需事实完整则不再派发相同检测。候选尚在清洗时合并等待已有 operation；唯一计算键至少含任务作用域、素材版本、片段区间、特征及算法/参数摘要。租约过期可接管，但逻辑作业与真实尝试仍分别记账。

复用检测事实须满足第 7.10 节的授权及版本条件；当前访问与来源用途不能靠旧缓存证明。缓存中存在通过判定也必须重建当前 revision 的规则解释及结果关系。只有读取内容才能计算的哈希放在受控下载后执行；不同来源的同内容素材保留独立来源校验，不直接丢弃来源记录。P1 只要求任务内复用，跨任务共享按 P3 门禁开放。

### 7.2 算子定义

| 类型 | 典型检查 | 输出与限制 |
| --- | --- | --- |
| 资源有效性 | 可访问、可解码、图片尺寸、视频时长 | 明确错误码，临时失败可重试 |
| 质量 | 模糊、曝光、损坏、水印、字幕比例 | 算法版本、阈值、证据 |
| 语义 | 主体、场景、风格、用户指定对象 | pass/fail/unknown，禁止仅以缺标签判断不存在 |
| 排除条件 | 不要文字、不要人物、不要某品牌 | 检测证据与覆盖范围，必要时人工复核 |
| 视频时序 | 动作顺序、片段完整、时间跨度 | 时间段证据，不能只记录一个总分 |
| 去重 | 二进制一致、视觉近重复、重叠片段 | 重复簇、保留理由、阈值版本 |

业务 Skill 可以建议算子组合，但可用算子及参数范围来自后端白名单。清洗策略编译器将已确认规则映射为经版本化的 Data-Juicer 配方；不接受模型指定任意算子模块路径、依赖或可执行代码。“不要水印”默认检测后筛除，不调用去水印算子改变素材。裁剪、修复、重编码等素材转换属于另一类授权操作，不是本期筛选模式的默认能力。

### 7.3 三态判定与质量承诺

每条硬规则输出 `pass / fail / unknown`。当前版本的素材只有全部硬规则为 `pass` 才可进入自动有效集；`unknown` 进入复核池，不计入达标数量。规则变更必须产生新需求版本；原规则下的人工复核按第 7.15 节新增带证据的判定，禁止无证据直接改写 unknown。

“pass”表示通过约定验证器，不意味着识别模型绝无误判。因此交付需同时记录验证器版本、证据和抽检指标；水印、版权来源等高风险条件需要更严格证据或人工门槛。

### 7.4 去重层级

1. 精确重复：原始内容哈希等确定性证据；同一 ID 重复返回只新增命中记录，不新增候选。
2. 近重复：同一图裁剪、压缩、加边框等变体；通过感知特征和经过校准的阈值识别。
3. 相似但不同：相同风格、不同主体或不同镜头，不能仅凭语义 embedding 接近就删除。
4. 视频片段重复：同源时间区间重叠及视觉证据共同判断；保留任务需要的独立动作或场景。

每个任务在所有已授权参与库、所有轮次中统一去重。跨任务是否排除曾交付素材是显式业务选项，默认关闭，不能让用户甲的检索消耗用户乙的候选。

去重代表样本按“当前条件通过状态 → 授权可用性 → 质量 → 用户偏好”选择。后来发现更好副本可以替换代表样本，但不增加数量。近重复算法要避免简单传递闭包导致相似链条错误合并，需保留代表样本校验或簇内一致性限制。

### 7.5 多轮清洗语义

“再去掉有文字的”“保留暖色调”“重新允许竖图”均生成新需求版本。原始候选和历史判定不删除：

- 新增条件：复用可复用检测结果，对受影响候选补做验证。
- 放宽条件：允许此前因相应条件淘汰的候选重新进入评估，不能只在上轮剩余集上筛选。
- 用户拒绝样本：区分“只删除这一条”“排除这一近重复簇”“把该理由升级为全任务规则”。
- 用户例图：作为当前任务证据；若要保存为长期个人偏好，必须单独确认。
- 扩词或模型变化：不影响的确定性结果可复用；语义判定按规则、模型和素材版本决定是否失效。

对用户显示的是“合格数、待复核数、重复数、未通过原因”，而不是把召回数量称为最终结果数量。

### 7.6 清洗能力采用 Data-Juicer 的边界

采用“独立清洗执行服务 + Data-Juicer 适配器 + company-data-operators 内部扩展包”。包名为建议命名，不表示已存在。Data-Juicer 不管理租户身份、用户反馈或补数，不新增与 DSH 竞争的自动决策循环。

| 能力 | 落地方式 | 验收关注点 |
| --- | --- | --- |
| 尺寸、宽高比、时长、资源格式 | 优先复用已验证通用算子；无适配算子时提供轻量扩展 | 输入单位、缺失字段、视频片段口径 |
| OCR、清晰度、水印、质量特征 | 评估现有算子，不足时接入内部模型或服务 | 证据、误判、依赖、成本，不以算子存在代替效果验收 |
| 图片/视频精确重复 | 复用内容哈希或对应算子能力 | 核实哈希覆盖对象及规范化语义；不能冒充视觉近重复 |
| 视觉近重复、重叠片段 | 特征计算可在算子层；任务级匹配和簇管理在结果集服务 | 跨批次和跨库比较，避免误合并 |
| 业务风格、复杂主体、视频动作顺序 | 自定义版本化模型算子，按需包装为 Data-Juicer OP | 业务评测集、提示词版本、unknown 和时间证据 |
| 用户阈值、规则组合、配额 | 业务规则层执行，必要时编译为批准的过滤配方 | 不写入共享模型状态，不跨用户复用最终判定 |
| 用户反馈、数量统计、补数与终止 | 业务服务 + DSH Agent | 不放进 Data-Juicer recipe 或算子内部 |

“算子融入库”不等于必须提交上游 PR：内部扩展包先独立维护；适合公开、无业务秘密的通用算子可后续贡献社区，但上线不依赖 PR 被合并。

### 7.7 检测事实与用户规则分离

数据流拆为两步：

1. 检测：得到文字区域占比、模糊评分、主体标签、视频时间段证据等事实及其不确定性。
2. 判定：用当前任务规则解释这些事实，得到 pass/fail/unknown。

示例：同一图片检测得到文字区域占比 0.02。A 要求“完全没有文字”，B 的已确认规则允许占比不超过 0.05。若检测覆盖充分且满足各自证据要求，A 与 B 可以得到不同判定；不能把 A 的 fail 缓存成素材的永久属性。数值仅示例，不是 OCR 通用阈值。

若模型直接回答“是否符合这条需求”，它属于规则相关检测，缓存键必须包含完整规则、提示词及相关上下文，不能冒充独立于用户的通用特征。

Data-Juicer 适配器必须捕获统计、证据及被筛除条目。可通过明确的检测步骤、适配包装或已验证的追踪机制实现，不能只读取最终保留数据集。若现有算子只能给出保留/丢弃而无法提供必要证据，应补包装或替换；输入输出差集只能说明条目被移除，不能杜撰移除原因。

执行错误与内容不合格分开：解码失败、模型超时、依赖缺失返回执行错误；按策略重试或进入 unknown，不能伪造成“有水印”等 fail。

### 7.8 算子注册与配方编译

建立业务算子注册表，使用稳定逻辑 ID 映射到内部或 Data-Juicer 实现。前端和 DSH 不依赖第三方 Python 类名。

每个版本至少登记：

- 逻辑 ID、版本、负责人、许可证及发布状态。
- 输入媒体、输出特征 schema、参数类型/上下限、可处理的计数单位。
- 后端映射、模型/权重/预处理/提示词版本、环境镜像摘要。
- 支持的执行模式、CPU/GPU/外部 API 资源、batch 限制、超时和重试规则。
- 是否依赖任务上下文、是否可缓存、是否有状态、是否产生新素材。
- 质量评测、失败语义、证据能力和已批准使用场景。

编译链路：QuerySpec + 已批准 Skill 建议 → 规则归一化 → 白名单算子映射 → 依赖/参数/资源校验 → 不可变 CleaningRecipe → Worker 执行。

配方记录规则到检测步骤的映射、步骤依赖及顺序、资源限制、失败处理和版本摘要。同一检测供多条规则使用时只运行一次；明确规定前置失败后下游状态为“未执行”，不能按 pass 处理。

不得接受 Agent 指定任意模块路径、安装地址、输出目录或解释器命令。注册与发布权限属于管理员或发布流水线，不属于普通检索用户。

### 7.9 内部扩展包与开发规范

建议结构：

```text
company-data-operators/
  core/            算法核心与模型调用，不读用户会话或任务数据库
  dj_adapters/     Data-Juicer OP 包装与字段转换
  schemas/         输入输出及检测特征版本
  tests/           单测、契约、质量回归、异常与多用户隔离
  recipe_templates/ 已批准的配方模板，不含密钥
```

接入时采用冻结版本支持的外部注册方式，不长期修改上游核心。不要求所有现有内部模型服务改写：可通过算子包装调用，但必须由服务端注入凭证、限流和超时。

算法核心禁止持有可变的“当前用户规则”全局变量。常驻模型可以在安全范围内复用权重，但每次请求的阈值、提示词、样本和临时文件须隔离。模型推理完成要释放请求相关引用，防止后续任务读到缓存中的用户内容。

筛选模式下禁止覆盖源素材。抽帧等检测用中间产物保存到受控临时位置并设置保留期；正式生成裁剪图/新片段等衍生数据须另行批准，并保存父素材、转换版本和新内容摘要。

### 7.10 缓存与增量重算

特征缓存键至少包含：授权范围、素材内容/版本、片段区间、特征 schema、算法/模型版本、预处理与检测参数摘要。对任务相关推理再加入规则、提示词和上下文摘要。

- 默认在租户及素材授权范围内复用。跨用户命中只返回获授权素材的检测事实，不暴露其他用户任务和使用记录。
- 缓存读取也需授权；内容相同不代表调用者有权知道其他库存在该内容。
- 阈值改变但检测定义不变：复用事实，重算用户判定。
- 模型、抽帧策略、提示词或素材内容改变：失效对应特征，重跑受影响部分。
- 模型超时等暂态错误不作为长期有效检测缓存。
- 条件放宽时，从任务原始候选池重新评估，而不是只读取 Data-Juicer 上次导出的保留集。

批次返回前再次校验 revision/generation；旧代次事实可按素材权限和版本保存，但旧判定不能进入新版本有效集。

### 7.11 跨轮去重的执行职责

Data-Juicer/扩展算子产出哈希、感知特征及可解释的批内重复关系；结果集服务维护任务级历史索引，包括之前轮次和其他库的候选。

每轮至少执行“新增对新增”和“新增对历史”比较。历史不只包含已交付样本，还需保留必要的原始候选关系，支持放宽规则后的重新评估。用户拒绝项按单条、重复簇或任务规则分别生效。

纯内容相等关系可以复用；近重复阈值、规则有效性和代表样本选择按版本维护。清洗服务无权把“一个批次留下 20 条”直接加到任务有效数量上，由结果集服务提交后重新计算。

### 7.12 在线与离线执行

| 维度 | 在线检索清洗 | 离线数据生产 |
| --- | --- | --- |
| 输入 | 每轮少量候选 ID/清单 | 大规模数据集清单 |
| 重点 | 首批延迟、可取消、用户隔离、增量处理 | 吞吐、分区、成本、批处理恢复 |
| 执行建议 | 常驻 Worker、模型预热、受限小批量 | 按规模采用批处理或经过验证的 Ray 执行 |
| 共享内容 | 算法、schema、模型版本、配方与规则含义 | 同左 |
| 不强求共享 | 进程、批大小、队列优先级、任务状态 | 同左 |

不因为引入 Data-Juicer 就强制在线任务启动 Ray 集群或完整离线 CLI。采用库级或执行器封装的可行性、模型复用和取消粒度，需要在冻结版本上做最小验证；不能假设所有 OP 能任意切换执行后端。官方分布式文档对去重算子的执行适配有特别说明。[分布式执行文档](https://github.com/datajuicer/data-juicer/blob/main/docs/Distributed.md)

线上先采用清晰的受控执行顺序。若启用算子融合、重排或并行优化，必须确认不改变业务筛选语义、逐条证据、取消和版本检查，且通过在线/离线等价性回归。

### 7.12.1 小批次流水线与背压

P1 使用独立可恢复的小批次，允许串行完成端到端闭环。P2 在串行基线通过后，验证“检索批次 n+1 与清洗批次 n 重叠”；流水线开关可回退串行，不改变规则、计数及结果版本契约。

协调器按租户及任务限制预取候选数、在途批次数、待清洗队列长度、媒体字节量和 CPU/GPU 并发。超过高水位停止派发新检索，降到低水位且权限/预算仍有效才恢复；高低水位与资源预留量在 P0/P2 对应验证前冻结。不能只限制任务数而放任单个视频占满临时盘。

每个完整小批次提交结果后可构建预览，无需等待同一逻辑轮所有检索分支结束；未完成候选不计通过。批次内部部分成功可保存用于恢复，仍遵守第 14.6 节的完整性协议。并行批次发布以任务级提交串行化或 CAS 重建，保证每次发布都比较“新增对新增”和“新增对所有已提交历史”，不能把并行结果各自的新增数相加。

接近目标时按已完成有效数、在途候选和固定预取余量缩小下一批；在途数量仅用于调度估算，不提前算作 accepted。达标后停止新派发并尽力取消多余计算，走 FINALIZING 发布；晚到事实可留存、真实费用仍入账，不改变 delivery。暂时变慢不触发 NO_PROGRESS。

阶段对照使用相同语料、规则、版本、负载及缓存条件，报告串行/流水线的首批延迟、任务完成时长、峰值队列/内存/临时盘、额外预取量和取消后浪费；资源峰值和质量一致性与延迟一起作为放行依据。

以下为内部逻辑能力名，不是 Data-Juicer 已存在的类名：

| 逻辑能力 | 初期范围 | 交付要求 |

### 7.14 排序与最终选样

P1 固定 SelectionPolicy 版本，执行顺序为硬规则通过 → 授权复核 → 去重代表选择 → 偏好排序 → 截取目标数量。P3 加入配额分配。策略记录融合方法、特征定义、参数、缺失值处理、稳定排序键和代表选择规则，随结果版本保存。

多路召回采用按媒体单元合并的排名融合：P1 可选固定等权 RRF，公式为各命中分支的 1/(k+rank) 之和；k、参与分支数及截断深度在 P0 固定，rank 从 1 开始。等价查询指纹只贡献一次；保留分支数与命中血缘，防止重复扩词虚增得分。跨空间原始距离不直接相加。该策略是 P1 待验证实现选择，不构成效果承诺。

P1 的排序采用确定的字典序：已确认偏好匹配序列 → 融合相关性 → 已定义且同量纲的质量等级 → canonical_unit_key。无质量等级时跳过该维度；偏好无法判断按不匹配处理并解释，不能提升为硬拒绝。偏好顺序在需求卡片确认；相同输入及版本必须得到相同排序。P3 如引入学习排序、多样性或来源分布，单独评测并发布新策略；来源比例若为硬要求必须进入配额/规则。

代表样本优先选择满足当前全部硬条件且当前授权有效的副本，再按上述排序取代表。P3 分组与近重复簇发生冲突时，选择须同时满足簇最多一个代表及组配额，不能先固定错误组代表再声称无可行结果；初期可要求簇内分组一致，冲突簇进入复核，未解决不计配额。

工作集可随新候选更新排序；已发布 preview/result 的成员与顺序不可原地修改。替换产生新 result_set_id，记录 replaced_candidate 和原因。已完成任务不会因后台晚到的更优样本自动改写交付。

### 7.15 人工复核

人工复核在原规则下补充判定证据，允许 unknown 经授权复核后产生新的 pass/fail 判定记录，不修改模型原始判定。修改条件仍创建新 revision；二者不能共用一个“接受”按钮。

复核记录绑定 tenant/task/revision、candidate_id、素材版本、rule_digest、原判定、复核者、证据、结论与时间。只有规则注册表允许的人工证据可覆盖机器不确定性；授权和来源等确定性门禁不能被普通用户点击通过。存在审查冲突或证据不足时保持 unknown。

P1 可由受控试点人员复核；P2 定义 owner/editor/reviewer/viewer 的权限矩阵。复核完成后重算相关判定、去重、排序和计数，发布新预览版本；已完成快照保持不变，需要用户显式发起重新评估。重复提交幂等，旧 revision 的复核不得计入当前版本。

## 8. 数量不足自动补数：受控闭环

### 8.1 计数口径

设目标数量为 `N`，当前版本经验证且去重后的有效数量为 `A`，缺口 `G = max(0, N - A)`。

- 图片任务：按合格图片的最终代表样本计数。
- 视频片段任务：按合法片段和去重策略计数；起止时间必须在素材范围内。
- 不同视频任务：同一原视频即使有多个合格片段，只计一份。
- 启用配额时：总缺口 G 只用于无配额任务；有配额任务还须计算每组缺口 G_j，分组不足时即使 G=0 仍需补检索，详见第 8.6 节。
- 未完成当前 revision 验证、待人工复核、权限失效或重复的素材均不计入 `A`。

### 8.2 协调器执行与策略调整

完整小批次提交后，后端生成真实统计；协调器直接执行计划中已批准的补批、翻页、受限重试和达标终结。持续高重复、低相关性、需要新库/新查询或用户反馈触发策略调整时，才唤醒 Agent 提出受限动作。以下动作若已在批准策略内，由协调器执行；超出计划则经提案与后端校验，涉及硬条件、授权或费用变化仍须相应用户批准。

| 观测原因 | 可选动作 | 禁止动作 |
| --- | --- | --- |
| 当前查询还有未读取结果 | 深翻页或增加合法检索深度 | 把已返回同一页当成新增候选 |
| 重复比例高 | 调整查询分支、扩展相关库、排除已见 ID（若支持） | 降低去重要求凑数量 |
| 内容不相关 | 删除低效扩词、提高主体约束、重选库 | 擅自改换主题 |
| 清晰度/水印大量不通过 | 优先高质量库或更合适查询 | 自动接受有水印、模糊素材 |
| 某个分组不足 | 针对该分组补检索 | 用其他分组填平缺口 |
| 大量 unknown | 追加验证或请求人工复核 | 将 unknown 按比例计为合格 |
| 已授权策略增益很低 | 请求扩范围或交付部分结果 | 静默使用无权限库或抓取外部数据 |

ADD_ELIGIBLE_LIBRARY_TO_PLAN 仅从当前已授权、用途相符的库中增加计划分支，不授予新权限。

动作枚举固定为：`SEARCH_MORE`、`TRY_QUERY_VARIANT`、`ADD_ELIGIBLE_LIBRARY_TO_PLAN`、`RECHECK`、`ASK_USER`、`FINALIZE`、`REPORT_GAP`。不开放模型任意跳转任务状态。

### 8.2.1 已批准执行计划

search_plan 绑定 plan_version/plan_epoch、QuerySpec 摘要、授权范围引用、目录与物理目标版本、查询编码器、查询分支、配方、选样策略和 execution_policy_revision。附 ExecutionRules，至少包含：

- allowed_actions：可自动执行的动作、固定查询/库集合、单批及共享资源限制。
- triggers：翻页、补批、有限重试、Agent 重规划、人工确认及停止的条件。
- progress_policy：已完成批次观察窗口、低产出/重复判定口径、可执行替代策略集合。
- dispatch_policy：调度并发、预取与背压参数，pipeline_enabled。
- binding_digest：所有执行绑定的规范化摘要，提交时核验。

阈值由服务端已批准配置提供，模型只能引用或提出待审批建议。P1 采用固定触发规则，P3 再启用产出率/耗时/成本自适应分配。无规则匹配时暂停相应分支并重规划，不能自行放宽条件。允许自动补数仍受 allow_auto_refill 约束。

同一任务同一代次最多一个有效重规划决策。协调器汇总触发摘要并生成 decision_id，合并重复唤醒；提案绑定其读取的 plan_version 和统计水位。新计划提交采用版本校验，旧计划已派发作业显式取消或登记兼容承接关系，不因更新计划重复派发同一位置。普通批次完成可以继续已批准动作；同一分支需要重规划时暂缓该分支新增派发。故障可用性与业务无进展分开判定。

### 8.2.2 损耗归因与补数依据

每个库/查询分支及任务汇总记录原始命中数、已见单元数、首次发现候选数、映射/权限隔离数、执行错误数、硬规则通过数、unknown 数、精确/近重复数、新增唯一合格数、选中及备选数，以及耗时/实际用量。统计附 revision、plan_version、批次集合和截止水位；不同阶段的通过率不能混用分母。

淘汰主原因按固定顺序归类，分母为已完成判定候选；同时保留全部规则失败原因供诊断，多原因计数不能直接相加解释总损耗。分支成本/吞吐以实际运行记录计算，免费或无计费系数时报告 CPU/GPU 时间和调用量，不虚构费用。

| 主因 | P1 固定处理 | 需重新规划的情形 |
| --- | --- | --- |
| 已见命中/重复比例高 | 读取允许的更深位置，使用已验证的排除已见方式 | 深度受限或持续重复，需要新查询/参与库 |
| 语义不相关 | 按批准策略停用低效分支、切换已批准变体 | 需要生成新扩词或改变分支集合 |
| 水印/质量失败多 | 使用计划内质量更合适的分支 | 需要添加合适库或新查询，不能降低质量要求 |
| unknown 多 | 按策略补证据/有限重评，或进入人工复核 | 现有证据路径不足，需用户确认后续方式 |
| 映射/权限/依赖异常 | 隔离命中、告警、有限重试或暂停分支 | 必需来源不可用；不得解释成内容不足 |

多分支命中同一候选时保存全部血缘；任务级新增唯一数只计算一次。P1 分支产出使用稳定首次命中归因（按服务端批次顺序、分支 ID 决定同批并列），另报重复覆盖；此指标具有执行顺序偏差，P3 策略评估需固定归因方法并通过对照测试判断收益。代表替换不记新增数量。

### 8.3 补检索量估算

补数不能简单设为“缺 40 张就检索 40 张”。使用新增合格且唯一的产出率估算：

```text
本轮边际产出率 = 本轮新增有效唯一数量 / 本轮返回候选数量
估算批量 = ceil(缺口 / max(平滑后的边际产出率, 最小估算率) × 安全系数)
实际批量 = min(估算批量, 当前调度允许的批量, 库允许上限)
若配置了任务候选总上限，再受该上限的剩余额度约束
```

平滑产出率按查询策略/库和任务汇总同时记录；新策略采用经离线评估确定的先验值。安全系数只是数量估算参数，不能改变合格标准。实际批量由调度器分配，不是每个并行查询分支各自取得整份任务额度；有配额时按组估算后再分配共享资源。

例如缺 40 张，近期新增有效产出率约 20%，不加安全系数时预计需检索 200 个候选。最终是否足够以实际判定为准，不能承诺一定补满。

### 8.4 避免无效循环

- 保存每个“库版本 + 查询指纹 + 参数”的已读游标、检索深度和已见候选。
- 不支持分页的库，使用受限扩大 top_k 或更换有效查询；不能假装拥有游标。
- 一个策略无新增不代表所有策略耗尽；先检查是否有尚未使用的合法策略。
- 连续无新增且已尝试适当替代策略、达到已配置的任务执行限制，或没有可执行策略时结束本次自动执行；低产出但仍有稳定增益可降低调度优先级并继续，不能仅因某轮低于固定比例就判定无数据。
- 新需求版本不清零任务累计资源用量；恢复和继续也保留历史用量。后台策略可批准继续执行；涉及额外付费、授权范围或用户已指定截止时间的变化时，再按对应规则确认。
- 达标后仍需完成本次交付集的最终权限校验与快照，不必等待全部预取任务结束。
- 多余合格候选进入备选池，不挤占已确认结果；后续替换应更新快照版本。

### 8.5 停止条件和输出

| 原因码 | 含义 | 用户可见结果 |
| --- | --- | --- |
| TARGET_MET | 数量、硬约束和配额全部满足 | 交付完整结果 |
| EXECUTION_LIMIT_REACHED | 到达已配置的任务时间、处理量或模型调用限制 | 部分结果、剩余缺口，可选择继续或转后台 |
| COST_LIMIT_REACHED | 适用的付费/内部成本上限已达到 | 费用与用量说明，按规则批准后继续 |
| NO_PROGRESS | 在配置的观察窗口内无新增有效结果，且可行替代策略已尝试 | 部分结果、已尝试策略与主要损耗 |
| SEARCH_STRATEGIES_EXHAUSTED | 当前可用策略均已执行 | 说明检索范围与限制，不声称穷尽整个语料库 |
| NEED_USER_INPUT | 来源、条件冲突或扩范围需确认 | 暂停并保留已有结果 |
| DEPENDENCY_UNAVAILABLE | 依赖故障无法继续 | 可恢复状态或明确失败原因 |
| USER_CANCELLED | 用户取消 | 停止新增提交，保留审计及已有结果 |

“自动补数”默认指已有授权库中的再检索。触发数据生产应生成独立缺口单，描述缺少的样本分布及证据；只有另行批准后才进入生产流程。

### 8.6 分组配额与补数分配（P3 启用）

配额与目标数量分别表达。初版配额仅支持单一互斥分组维度，且各组 target_count 之和等于总目标；重叠分组或多维交叉配额须另行设计分配算法，暂不接受。

```json
{
  "target_count": 100,
  "quota_mode": "exclusive_groups",
  "quota_dimension": "scene_type",
  "quotas": [
    {"group_id": "indoor", "predicate_ref": "scene.indoor@1", "target_count": 50},
    {"group_id": "outdoor", "predicate_ref": "scene.outdoor@1", "target_count": 50}
  ]
}
```

以上是业务契约示例。素材通过分组判定后至多分配一个组；无法确定组别的样本不计入配额。去重簇只贡献一个代表样本，先完成规则验证及全局去重，再做分组分配，不得在多个组重复计数。

每组缺口 G_j = max(0, N_j - A_j)。当室内 80、室外 20，而配额各 50 时，交付可用数为 50 + 20 = 70，室外缺口为 30；室内多出的 30 条进入备选池。补数优先生成面向室外的查询，而不是用总数量 100 判断完成。

按每组近期“新增合格唯一且可分配”产出率估算候选量，再由调度器在允许的资源内统一分配。每轮重算分组缺口、代表样本与总交付数；仅在全部 G_j=0 且其他硬条件成立时完成。用户修改配额须创建需求草案并确认生效。

### 8.6.1 停止判定的实施约定

P1 使用固定策略集和可配置分支预算实现补数；第 8.3 节的分支自适应产出率优化在 P3 启用。即使采用固定批量，仍保存返回量、首次出现候选量、规则通过量和新增唯一有效量，供后续比较。

NO_PROGRESS 的观察窗口由协调器按已完成批次推进，不能因排队或慢作业暂时未返回就触发。RECHECK 的重试次数、查询变体数和重评范围必须受已批准策略约束，模型持续生成改写不能无限扩展“尚未尝试策略”。已尝试策略集合可穷尽时才用 SEARCH_STRATEGIES_EXHAUSTED；深度受限和 live 查询的限制需进入报告。

同轮/流水线完成事件按 decision watermark 汇总并幂等消费，常规补批无需等待整轮屏障；策略变化按第 8.2.1 节合并决策。允许提前达标时，终结准备关闭检索/清洗提交资格并停止未派发批次，仅保留快照发布资格；在途结果仅可保存历史事实和用量。模型重复提案由 decision_id + action_digest 幂等处理，不能每收到一次完成通知就再发一轮。

### 8.7 任务执行限制与用户交互

用户表达目标数量和质量要求，服务端管理执行限制。执行限制解决长任务、低产出和多人资源竞争问题，不保证任何目标都能在有限时间内满足，也不把固定轮数当作用户需求限制。

- 交互模式：在配置的响应窗口内优先返回首批及部分结果；窗口届满可按用户偏好转后台，或形成部分结果等待继续。
- 后台模式：可以不设固定检索轮数或候选总数，持续到达标、取消、无进展或不可恢复依赖故障。用户指定的截止时间和适用成本上限仍有效。
- 所有模式：保留每用户/租户并发、单批大小、模型/API 限流和公平排队；依赖暂时故障进行有限重试与退避。
- 执行额度由协调器原子预留，完成后按实际用量结算并释放剩余额度；防止多个并行作业各自检查后一起超额。
- 达到任务限制时保留当前候选、检测结果和快照，显示“已找到多少、还缺多少、为什么停止”，提供继续或转后台操作。只有确有费用影响时才显示费用确认。
- 继续执行保留需求 revision，增加 run_generation，并写入独立 execution_policy_revision/批准记录；若同时修改用户需求，则另走需求确认流程。

## 9. DSH 接入与业务 Skill 规格

### 9.1 运行模式

推荐由服务端 DSH 适配层使用进程外 SDK 管理检索运行时。选定受支持的命名 profile，并通过其允许的配置扩展加载业务插件；最终 profile 和配置键在冻结版本时验证。

生产入口是独立检索业务 API，不直接把通用 DSH Web UI 当成多用户业务后台。无需修改 DSH 核心推理循环；检索插件主要承担“注册工具、加载已批准 Skill、转换输入输出”。

运行时只保留完成本任务需要的工具：不开放任意 shell、通用文件读写、任意网络请求、动态安装插件、修改自身指令或创建任意子 Agent。若选定 profile 默认携带这些能力，必须在上线前移除或禁用，并验证最终实际工具清单。

### 9.2 适配层内部契约

下列是业务侧抽象，不代表 DSH 官方函数名：

| 抽象操作 | 作用 |
| --- | --- |
| create_runtime_context | 绑定运行配置、隔离目录、模型与工具允许列表 |
| open_task_session | 将 tenant/user/task/revision 映射到独立会话 |
| submit_turn | 发送用户需求或经过验证的执行摘要 |
| observe_events | 将模型输出、工具状态和会话异常转成业务事件 |
| cancel_turn | 请求终止当前推理，并由业务侧禁止后续结果提交 |
| close_context | 释放运行资源；业务状态仍保留在数据库 |

迁移 DSH 版本时，优先只修改该适配层和工具注册封装，不修改 QuerySpec、候选表、用户 API 和结果快照格式。

### 9.3 检索工具契约

| 拟建工具 | 模型可提供的参数 | 后端职责 |
| --- | --- | --- |
| retrieval.get_task_summary | 摘要类型、分页位置 | 注入当前任务身份，返回当前版本及真实计数 |
| retrieval.find_libraries | 主题、媒体类型、业务标签 | 先授权再搜索目录，隐藏敏感连接信息 |
| retrieval.propose_plan | 查询分支、库引用、规则引用、理由 | 校验语义、权限、执行限制和参数边界，保存计划及索引绑定 |
| retrieval.start_batch | 已批准的 plan_id/version、动作与批次建议 | 作为请求交给协调器统一派发；与自动调度共用幂等及资源预留，返回 operation_id；非每批必经模型工具 |
| retrieval.get_operation | 当前任务的 operation_id | 授权校验并返回统计，不暴露其他任务 |
| retrieval.sample_candidates | 状态、采样上限 | 返回少量已授权预览及证据，不导出全量原始数据 |
| retrieval.propose_next_action | 动作枚举、原因、建议参数 | 状态机验证并决定执行或请求用户批准 |
| retrieval.request_confirmation | 问题、选项、影响 | 持久化确认请求并暂停相关调度 |
| retrieval.propose_finalize | 完整/部分交付、停止原因、目标快照建议 | 重验规则、权限和计数；仅全部达标可 COMPLETED，合法停止且不足时 PARTIAL |

所有工具调用自动附加可信的任务上下文、请求 ID 和当前运行代次。即使模型参数中包含其他 task_id，服务端也必须拒绝或忽略，不能发生上下文切换。

耗时检索/清洗由持久化作业执行。工具返回作业 ID 后结束当前模型轮次；协调器收到完成事件后更新账本并执行已批准动作，仅在策略触发条件满足时唤醒 Agent。正常翻页、补批、重试和最终校验不要求额外模型调用。重复完成事件不得触发重复业务执行；Agent 不可用时允许继续当前有效计划中的确定性动作，需重规划的分支暂停。

### 9.4 Skill 包规格

每个业务 Skill 包由以下部分组成：

| 内容 | 规格 |
| --- | --- |
| 元信息 | skill_id、版本、业务域、所有者、审批状态、适用媒体 |
| 指令 | 术语解释、扩词规则、禁止语义漂移规则、正反例 |
| 词表 | 同义词、场景词、属性词、歧义词，不携带生产密钥 |
| 策略引用 | 允许使用的算子模板、目录标签和参数建议 |
| 测试集 | 扩词一致性、否定保留、来源/风格区分、业务典型案例 |

发布流程：草稿 → 离线评测 → 业务审批 → 发布不可变版本 → 新任务使用 → 观察与回滚。运行中的任务固定 Skill 版本，升级需显式产生新的计划或需求版本并记录影响。

共享 Skill 是经过审批的业务知识；个人偏好单独存储，不通过修改共享 Skill 实现。不同租户的同名 Skill 在业务注册表中使用完整命名空间，避免加载来源优先级引发串用。

### 9.5 Skill 选择与回退

P1 固定已支持的试点业务范围；未支持的业务直接说明能力范围，可使用经过验证的通用检索路径，但不得声称具备未实现的业务质量规则。

后续开放多业务时，按用户明确业务域、已授权业务配置和需求分类选择 Skill。无匹配时使用通用检索基线，保留原始查询并限制扩词；多个匹配时使用已定义的兼容组合，存在实质歧义时澄清。

用户当前明确条件优先于个人偏好和 Skill 建议。Skill 之间冲突时不自动合并互斥规则；所选版本不可用时可继续使用任务已绑定的有效版本，无法读取则暂停相关能力并说明原因，不静默升级或替换。

### 9.6 模型输入与输出规范

模型输入仅包含当前任务需求、授权目录摘要、Skill、统计和少量样本。全量候选、素材二进制及全部历史对话不反复塞进上下文。

模型结构化输出要经过 schema 校验、枚举校验、约束一致性校验和执行策略校验。格式错误允许有限次数修复；连续失败进入可恢复错误状态。内容、库介绍、OCR 文本和用户上传样例均视为数据，不能提升为系统指令。

若执行条件允许但模型不可用，可继续执行已经批准的确定性批次；不能未经批准自行换主题或采用更宽松规则。最终用户界面的数量与状态取自业务服务，而不是直接展示模型自报的完成情况。

## 10. 多用户隔离与安全规格

### 10.1 五级标识

采用 `tenant_id → user_id → conversation_id → task_id → revision`，再附加 `run_generation` 识别当前执行代次。

- tenant：组织/数据授权边界。
- user：个人所有权、偏好、配额和审计身份。
- conversation：交互容器；一个会话可关联多个任务，但不自动合并候选。
- task：目标、候选池、去重和资源用量的业务单元。
- revision：已保存的需求版本，包含 proposed/confirmed/superseded/rejected 生命周期；只有 confirmed 且被 confirmed_revision 指向的版本可以执行。
- run_generation：暂停、取消、改需求或故障接管后阻止旧执行继续写入的栅栏。

### 10.2 隔离矩阵

| 对象 | 默认作用域 | 允许共享的条件 |
| --- | --- | --- |
| DSH 会话与对话历史 | 任务及需求版本 | 仅显式协作任务内授权参与者 |
| 候选池、拒绝项、去重簇 | 单任务 | 另建共享数据集，不直接互串任务状态 |
| 用户反馈 | 当前任务 | 用户选择保存个人偏好或提交公共规则评审 |
| 个人偏好 | 单用户 | 不自动分享 |
| 业务 Skill | 已授权业务/租户 | 版本发布与授权后共享 |
| 素材内容特征 | 有权访问该素材的范围 | 服务端缓存复用，不泄露其他任务存在性 |
| 检索结果缓存 | 权限指纹与查询空间 | 访问权限、索引版本和查询语义完全匹配 |
| 导出与预览链接 | 授权用户、有效期 | 受控分享并可撤销 |

用户 A 说“以后不要人物”，默认只改变 A 当前任务；只有显式保存才成为 A 的个人偏好，不影响 B，更不能修改整个业务的扩词规则。

### 10.3 身份与授权

身份提供方确定为内部 W3 登录系统（2026-10-20 用户确认）。产品接入 W3，
不另建独立密码库。W3 协议、应用注册及网关/应用直连方式尚待内部文档确认；
当前代码仍为开发用身份头，未完成真实认证。接入步骤、所需字段及验收见
[W3 登录对接约定](../docs/p0/w3-integration.md)。
W3 验证身份后由服务端映射稳定 user_id/tenant_id；资源权限仍由权威授权服务决定，
不能把登录成功等同于所有库可访问。

1. 网关验证登录身份，服务端取得 tenant/user/role，模型不参与身份认定。
2. 业务 API 检查任务所有权或显式协作者权限；只检查 tenant_id 不够。
3. 目录查询前、向量检索前、素材读取及导出前分别进行授权。
4. Worker 使用限作用域服务凭证；执行时仍检查任务权限版本。
5. 数据库查询强制资源范围；可采用行级安全作为纵深防御，但不能代替应用层授权。
6. 列表、错误消息、统计、缓存命中和相似内容哈希查询同样不能泄露跨用户数据。

权限撤销后，中止相关新读取，失效预览和导出能力，并从可交付集移除不再有权访问的素材。历史审计可按合规要求保留最小引用，但不能继续提供素材访问。

### 10.4 DSH 运行环境隔离

初期建议按租户和用户建立隔离的运行身份/工作目录，按任务创建独立 DSH 会话；任务需求发生实质变化时开启新 revision 会话，只携带后端生成的受控摘要。运行进程可按需创建和回收，不要求每个用户永久占用一个进程。

不得让所有用户共用一个可写 DSH home、同一个项目指令目录或统一的可变记忆。共享只读的已发布 Skill 可以复用；个人文件与日志按身份隔离。进程隔离不是完整安全边界，还需容器/操作系统权限、网络白名单和最小凭证。

高并发阶段可优化运行池，但必须先证明会话、目录、事件、凭证、缓存和插件状态没有跨用户泄漏；不能为节省进程直接退回共享会话。

### 10.5 数据保护

- 向量库密码、对象存储密钥不进入提示词、工具描述或普通日志。
- 素材 URL 只能由可信素材服务生成；禁止模型提供任意 URL 让 Worker 抓取，防止 SSRF。
- 外部模型处理私有素材前必须符合组织的数据出域规则；必要时采用内网模型或脱敏特征。
- 提示词、工具日志可能包含用户业务信息，需权限控制和敏感字段脱敏。
- 短期签名链接到期后重新授权生成；不可把永久下载链接写入公开会话。
- 保留期按组织策略配置；任务删除应覆盖业务数据、会话、缓存与导出引用，源库素材不随任务删除。

## 11. 任务状态机、版本和故障恢复

### 11.1 运行状态定义

下表统一命名为 run_status。task_lifecycle 仅为 active/archived/deleted；完成、部分交付、失败和取消均为一次运行的终态，不结束任务容器。query_revision.status 继续使用 proposed/confirmed/superseded/rejected。API 分别返回 task_lifecycle、revision_status、run_status 和 stage；不以一个 state 同时表达三者。初次解析可以有 confirmed_revision=null 的 run，确认后创建绑定生效 revision 的新 run，旧解析 run 保存结束原因。


| 状态 | 含义 | 允许的后续状态 |
| --- | --- | --- |
| CREATED | 已创建、等待解析 | PARSING、CANCELLED |
| PARSING | 解析需求和歧义 | AWAITING_INPUT、PLANNING、FAILED、CANCELLED |
| AWAITING_INPUT | 等待草案确认或其他明确输入 | 确认后 PARSING/PLANNING；拒绝后恢复原确认版本视图或按规则继续；CANCELLED |
| PLANNING | 选库、扩词、生成检索计划 | RUNNING、AWAITING_INPUT、FAILED、CANCELLED |
| RUNNING | 检索/清洗/去重/统计循环 | RUNNING、AWAITING_INPUT、PAUSED、COMPLETED、PARTIAL、FAILED、CANCELLED |
| PAUSED | 用户或系统安全暂停，保留可恢复位置 | CANCELLED；恢复创建新 run，旧 run 不转回运行 |
| COMPLETED | 本次运行已达标并生成快照 | 终态；新需求建立新 revision，既有快照不可改写 |
| PARTIAL | 本次执行停止并交付不足数量 | 本次运行终态；原条件继续可新建 generation，改条件建立新 revision |
| FAILED | 无法完成，记录故障及可恢复位置 | 终态；显式重试创建新运行代次 |
| CANCELLED | 已取消，停止接受旧运行提交 | 终态；重新开始需显式操作 |

运行状态属于 task + revision（初次解析可为空）+ run_generation 的执行视图，每个运行代次保留终结记录；需求生命周期与执行状态分开。一个任务最多一个可调度的 confirmed revision。RUNNING 内的 `stage` 为 RETRIEVING、VALIDATING、DEDUPLICATING、COUNTING、DECIDING、FINALIZING，用于进度展示，不再各建 Agent。流水线开启时 stage 为主展示阶段，另返回 active_stages 及各阶段作业数；它们不表示互斥状态，不能据此禁止合法的检索/清洗重叠。

### 11.1.1 控制命令与并发

| 命令 | 前置条件 | 原子效果 |
| --- | --- | --- |
| pause | 当前 run 在 PARSING/PLANNING/RUNNING | 当前 run 进入 PAUSED，提升 generation 栅栏；保留任务与需求 |
| resume | 当前执行视图为 PAUSED，且无未决批准 | 结束旧 run 的暂停记录，创建新 generation/run；权限、策略重检 |
| cancel | 任一非终态 run，包括等待输入 | 终止当前 run，提升栅栏；已有快照保留；未决批准失效 |
| continue | PARTIAL/CANCELLED 且用户显式操作；RUNNING 转后台为单独 mode_update | 原需求新建 run；转后台只变执行策略，不重复派发已批准作业 |
| retry | FAILED | 新建 run，显式引用可复用的完成结果，失败部分按策略重试 |
| feedback | active task；包括旧 run 已完成的任务 | 新建需求草案；按第 11.2 节确认，不重开旧终态 run |
| archive/delete | 无活动 run 或先显式取消成功 | 更新 task_lifecycle；拒绝新调度，删除按保留策略异步执行 |

状态表中 PARSING/PLANNING 也允许 PAUSED；命令表为这些控制边的明确补充。generation 为单调提交栅栏，可在取消/暂停时递增而不创建新 run，不能假定每个 generation 都有 task_run 行。task_run 固定其创建时的 generation，只有等于任务当前 generation 且处于允许提交状态时才能提交。暂停后 UI 通过 current_run_id 展示旧 run 的 PAUSED 状态；恢复新建 run，旧 run 以 resumed_by_run_id 关联继任并终结为 CANCELLED，结束原因为 RESUMED，不覆盖历史。

暂停、取消、确认、反馈、重试、继续、归档都携带 expected_task_version 和 Idempotency-Key。并发竞争先取得任务行锁或等效 CAS；一个成功，另一返回 REVISION_CONFLICT。task_version 仅因控制/需求/策略变更递增，不因每条进度事件递增，避免用户确认被正常进度持续打断。result_version 和 event sequence 各自独立。

取消与最终交付竞争使用同一任务提交锁；最终交付先提交则取消返回 ALREADY_TERMINAL 并给出当前快照，取消先提交则旧批次不能发布。再次调用相同幂等键返回原响应；同键不同正文返回 IDEMPOTENCY_CONFLICT。

### 11.1.2 节点等待与 run 替换

node_status 为 pending/running/succeeded/failed/cancelled；succeeded 表示本节点计算完成，不代表后继获准执行。gate_status 为 blocked/awaiting_approval/approved/rejected/stale。失败节点不能靠批准改成 succeeded。

节点人工等待使用 AWAITING_INPUT，waiting_reason=NODE_APPROVAL；不提升 generation。批准且需求/输出未变时，同一 run 恢复 RUNNING，扩词后可先进入 PLANNING；这是状态表 AWAITING_INPUT 到 RUNNING 的明确补充。打包待批使用 PACKAGE_APPROVAL，保留 FINALIZING stage。

用户显式 pause 才栅栏旧代次；resume 结束旧 run 为 CANCELLED/RESUMED，创建新 run，经 PLANNING 核验输入、权限和待批节点后继续。初次确认关闭解析 run（CANCELLED/REQUIREMENT_CONFIRMED），新 run 从 PLANNING 开始。确认新增清洗诉求时旧活动 run 结束为 CANCELLED/SUPERSEDED_BY_REVISION，新 run 先核查复用输入再清洗。故障接管先结束旧 run（FAILED/LEASE_LOST），新 generation 经恢复核查后继续。

上述旧活动行关闭、新 run 插入、任务指针和 outbox 切换须在同一事务完成，满足单活动运行约束。恢复不跳过未批准门禁；旧终态 run 不因历史查看重开。

### 11.2 反馈与并发提交

用户提交反馈时携带 expected_revision（已确认版本）和 expected_task_version（任务乐观锁版本）：

1. 后端校验权限和 task_version；原子保存反馈草案、增加 task_version，默认暂停旧版本新增调度并提高 generation。并发请求使用旧 task_version 时返回冲突，避免多个草案同时覆盖。
2. 保存 proposed revision，confirmed_revision 保持旧值。新草案可供用户查看，但不能启动检索或清洗；旧结果标记为“上一确认版本结果”，不冒充新需求结果。
3. 明确、无歧义且在权限范围内的直接用户指令，可按规则自动确认，用户提交本身视为确认；新增费用或范围等需批准事项仍等待对应确认。无需对每次明确修改重复提问。
4. 存在歧义时进入 AWAITING_INPUT。确认请求绑定 proposal_id、base_revision、proposal_digest 和 task_version；只接受仍有效的草案，陈旧确认返回冲突。
5. 确认事务将草案设为 confirmed、旧需求设为 superseded，更新 confirmed_revision、增加 generation，并通过 outbox 派发重新评估。已确认 QuerySpec 内容不可修改。
6. 用户拒绝草案时标记 rejected；若原确认版本尚在运行，则恢复调度前检查权限和执行策略并开启新 generation。若原运行已结束，则恢复其既有 run_status/快照视图，未经继续指令不重新执行。不能静默应用被拒绝的条件。
7. 旧代次晚到只可保存合规的原始候选/检测事实，重新按生效版本验证后才能计数。

API 同时返回 confirmed_revision、pending_revision、task_version，避免前端以一个含糊的 current_revision 推断生效状态。初次创建任务时也先解析 proposed revision；需求明确时可自动确认，否则等待澄清。

### 11.3 幂等、租约和事件

- 任务创建使用 `Idempotency-Key`，作用域包含 tenant/user；同 key 不同请求体返回冲突。
- 每个 operation_id 唯一；同批次重试只更新同一作业，不能重复增加有效数量。
- 调度器使用任务租约与 fencing token，接管后旧协调器写入被拒绝。
- 状态更新与 outbox 事件同事务提交；消费者按 event_id 去重，允许至少一次投递。
- 不承诺分布式“消息恰好投递一次”；通过幂等与版本检查实现不重复的业务效果。
- 取消后允许已经发生的计算费用被记录，但禁止提交新的结果集或派生新作业。

### 11.4 实际调用用量与重试记账

“费用不重复记账”指同一真实费用事件或回调只入账一次，不表示外部供应商不会对重试收取费用。operation_id 标识逻辑业务作业，attempt_id 标识实际执行尝试；两次真实调用即使完成同一个逻辑作业，也要分别记录实际用量。

支持供应商幂等键时按其契约传递并保存请求 ID；请求超时且是否收费未知时记为待对账，保留适当资源预留，不能按零费用处理。重试需受当前执行策略和适用费用限制约束。结果集仅按逻辑作业幂等提交，成本汇总则包含所有真实尝试。

### 11.5 重启恢复

DSH 进程退出不应丢失已检索候选、作业 ID、执行策略/累计用量和有效集。恢复过程：读取 confirmed_revision → 检查未完成作业 → 查询或重试可幂等作业 → 重算结果 → 新建/恢复受支持会话 → 发送后端摘要继续决策。

若某个向量库不可用，可使用计划中其他授权库继续；如库故障使明确来源条件无法满足，则报告依赖不可用，不绕到其他来源凑数。

## 12. 用户交互与完整示例

### 12.1 页面最低规格

P1 必须交付五节点流程图、逐节点推进设置、实时结果面板和清洗诉求历史；本节是 UI 实现要求，不表示现有代码已实现。

| 区域 | 必备内容 |
| --- | --- |
| 需求输入 | 原始诉求、图片/视频、目标数量、可选业务域与例图 |
| 条件卡片 | 硬条件、排除条件、偏好、来源/风格区别、计数单位，可编辑 |
| 检索计划 | 所选库与理由、查询分支、预计耗时与可用执行模式；实际涉及费用时再显示费用信息 |
| 流程图 | 五节点及各轮实例、执行/门禁状态、人工/自动模式、输入输出量；点击查看详情 |
| 实时进度 | 当前阶段、已返回、通过、重复、有效、待复核、距目标差多少 |
| 结果区 | 预览、来源、规则证据、重复代表说明、接受/拒绝/复核 |
| 反馈区 | 对单条/一簇/全部生效的明确选择，显示影响范围 |
| 控制区 | 暂停、继续、转后台、取消、导出；额外付费只在适用时确认 |
| 结束报告 | 实际结果数、未满足条件、停止原因、建议及版本信息 |

进度不使用无法证明的“整体完成 80%”。可展示确切的“目标 100，当前有效 60；第 2 轮清洗中”。

### 12.2 数量闭环示例

需求：“100 张小红书风格室内家居图片，无水印，横图优先。”系统解析风格而非来源，选择有权使用的生活方式库和专业室内摄影库。

以下数字仅说明计数逻辑，不是性能预测：

| 轮次 | 本轮返回 | 本轮硬条件通过 | 去重后新增有效 | 累计有效 | 下一步 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1 | 120 | 70 | 60 | 60 | 缺 40，分析损耗并补检索 |
| 2 | 200 | 70 | 35 | 95 | 缺 5，针对高产出分支继续 |
| 3 | 50 | 15 | 8 | 103 | 交付排序后的 100 张，保留 3 张备选 |

随后用户说“再去掉所有包含文字的”，保存 proposed revision 2；在该指令明确且无须额外批准时自动确认生效。系统重验已有候选，若原 103 张仅 82 张通过，则显示缺口 18，并按同一任务的执行策略继续补数。不能仍显示 revision 1 的 100 张为达标，也不能让此反馈影响另一位用户。

### 12.3 人工确认点

必须确认：来源/风格存在实质歧义、条件冲突、扩大授权范围、增加超出策略的费用、放宽硬规则、启动离线数据生产、保存长期偏好、共享任务或数据集。

节点设为 auto 且无强制审批事项时，可自动执行已批准范围内的扩词、检索、清洗和补数。节点设为 manual 时每次节点实例完成均需批准，不得被自动补数或流水线绕过。

### 12.4 节点结果与实时查看

| 主节点 | 点击查看 | 完成后推进 |
| --- | --- | --- |
| 检索词扩词 | 原词/扩展词/排除条件、词来源、选库理由、查询分支，允许编辑重验 | 固定计划版本，批准后检索 |
| 检索 | 本轮及累计授权候选、来源、排名、缩略图，标注“未清洗” | 本轮批准批次全部完成或失败已明确处置，固定候选清单后清洗 |
| 清洗（DJ） | 配方/阈值、进度、合格/淘汰/待复核分页、逐条原因及去重说明 | 必要判定与跨轮去重完成，固定预览版本后进入补数 |
| 补数 | 目标/缺口、损耗、已尝试策略、拟增加查询/库/处理量或无需补数说明 | 冻结动作，批准后再检索或打包 |
| 打包 | 包生成进度、成员清单、数量、摘要、版本、失败原因 | 生成待发布包，批准后正式发布与下载 |

节点详情显示 branch/revision、iteration、输出版本及统计水位；run 放在执行历史中。检索阶段只显示已完成映射及当前授权校验的候选，不把原始召回数称为合格数。清洗阶段每个已提交小批次即可查看结果，无需等待任务结束。待复核与淘汰采用独立视图，不能混入合格集或 accepted_count。

SSE 通知 node.progress/output_available/gate_changed 和输出版本/统计；前端再分页拉取列表，不把全量图片或私有地址放进事件。P0 冻结首批及更新延迟目标，P1 验收实时查看。断线按 as_of_sequence 恢复。

浏览页固定视图版本；新增结果显示“新增 X 条”，用户点击加载，避免图片位置自动跳动。权限撤销立即阻断访问。新增需求时切到新分支，显示重验中；旧结果在历史分支查看并注明旧条件。候选与复核列表使用独立稳定清单版本/水位，不要求 unknown 属于合格 result_set。

### 12.5 逐节点人工确认与自动推进

创建页提供五节点各自的 manual/auto 设置，以及全部人工/全部自动快捷项；P1 默认 manual，界面明示后随任务提交。设置保存为 workflow_policy_revision，新 iteration 继承，每个节点实例独立过门禁。auto 不免除来源歧义、权限、额外费用等强制审批。

批准绑定 task/branch/revision、node_instance_id、iteration、output_version/digest、workflow_policy_revision；请求携带 expected_task_version、expected_node_version 和 Idempotency-Key。输出重做或需求/批准范围变化使旧请求 stale；重复批准幂等，陈旧批准返回冲突。后端在批准时重检权限和输入有效性。

manual 节点完成后可批准、要求修改重做或取消；拒绝后保持停止，不自动跳过。编辑扩词生成新计划版本并重做受影响下游；修改筛选规则创建新清洗诉求。manual 改 auto 时明确作用于当前待批节点还是仅未来节点，包含当前节点时展示其输出摘要并记录本次推进授权；auto 改 manual 不撤销已执行计算，只阻止未启动后继。

补数批准只批准当前补数计划；下一轮检索/清洗若仍是 manual，仍分别审批。allow_auto_refill=false 时不能借节点 auto 设置自动补数，必须显式批准补数计划或更新执行策略。

流水线只能跨 auto 且无强制审批的边界：检索 manual 时可实时看候选，但批准候选清单前不得启动 DJ；清洗 manual 时可看清洗结果，但不得进入补数/打包。P1 串行先验证门禁，P2 再验证流水线与门禁组合。

### 12.6 新增清洗诉求与分支

清洗诉求用 cleaning_request_id/branch_id，关联 parent_branch_id、base_revision、base_input_manifest、规则差异及完整生效规则。UI 展示“清洗诉求 1/2”，不是 run；一条分支暂停恢复或故障重试可对应多个 run。

追加条件先创建草案分支；确认后创建新 revision、切换 active_branch_id、终结旧活动 run 并栅栏旧作业。P1/P2 同任务只允许一个活动分支；历史分支保留节点输出及交付，可查看但不再新增派发。真正独立目标另建 task，不默认同时执行多条分支。

输入默认值按入口区分：需求详情页默认使用当前需求已检索候选；数据集详情页默认使用用户正在查看的固定数据集版本。提交时按第 12.8 节解析并冻结清单/水位，不在异步执行时重新解析“最新结果”。输入范围及补数设置在确认卡上分别显示，未经批准不得扩大。放宽规则且输入为全部候选时，历史淘汰项重新参与评估；输入为固定结果集时，只评估清单内样本。

仅新增条件时复用兼容检测事实和不变规则判定；已不满足原硬条件的候选无需再做新增昂贵检测。新分支独立判定、去重、排序、计数。旧代次晚到只保留合规事实，纳入新分支需明确登记输入扩展并按新需求验证。

示例：先明确“人脸小”的面积比/像素、多人脸取值口径及图片尺寸阈值。追加“去除男生”时新增清洗诉求，继承原规则；需明确任意人物还是主体、视觉标注依据和 unknown 处理，外观判断不等同身份事实。明确且能力已验证可按需求确认规则生效，否则等待澄清。旧版合格 60，新版重验后合格 42、待复核 8、淘汰 10，则当前合格 42、缺口 58，旧版数量不沿用。

### 12.7 打包批准与正式交付

FINALIZING 先生成不可变 staged delivery/manifest。打包 manual 时进入 AWAITING_INPUT/PACKAGE_APPROVAL，只提供受控清单预览，不能开放正式下载或发 dataset_snapshot.published。打包 auto 由服务端执行同一发布校验入口。

批准时重验成员、规则、权限和输出摘要，通过后原子切换交付指针并置 COMPLETED/PARTIAL。成员失效导致不足时旧批准作废，进入缺口处置或重建待发布清单，不能用审批补偿硬条件失败。

清单生成暂时失败有限重试，耗尽后 FAILED，保留发布恢复点。暂停/取消/新增需求先取得控制权时旧发布操作失效，未发布对象标记待清理；新 run 恢复重新核验且不跳过门禁。发布操作绑定 branch/revision/generation、plan_version 及节点输出摘要；旧分支包不能晚到发布。

### 12.8 在对话中追加清洗需求

业务诉求：同一个数据需求清洗后，用户可继续对话追加条件，并明确本次针对哪些数据。用户不必复制需求 ID；界面负责携带上下文，后端核验权限与版本。task_id 承接目标、历史对话和任务权限，数据集/结果版本确定输入，两者不互相替代。

| 入口 | 用户操作及默认上下文 |
| --- | --- |
| 需求列表 → 需求详情 | 按需求名称/历史找到任务，点击“追加清洗条件”，在常驻对话框输入；默认父分支为当前分支，输入为当前任务已检索候选 |
| 清洗节点/结果面板 | 点击“基于这版结果继续清洗”；绑定用户实际看到的 result_set_id，而非后台最新结果 |
| 数据集详情 | 点击“继续清洗”；绑定正在查看的 snapshot_id，按血缘解析可继续的原需求 |
| 全局对话框 | 未选中唯一需求或输入数据集时，先展示可访问需求/数据集供选择；不得猜测最近任务并执行 |

输入框上方持续显示需求名称、父清洗诉求、输入版本。允许通过名称搜索已授权任务；不能通过 ID 搜索泄露无权访问对象。需要人工确认的操作和节点模式继续适用。

提交确认卡至少包含：

- 原需求名称与目标数量。
- 继承条件、新增/删除/修改条件及合并后的完整规则。
- 输入范围：全部已检索候选、指定结果版本或指定数据集快照；显示数量与版本时间。
- 数量不足处理：仅筛选现有输入、接受数量减少；或维持目标、允许从明确的授权库补数。
- 新清洗诉求名称、五节点推进模式，以及是否将停止旧活动分支。

示例：需求“室内家居图 100 张”，继承人脸大小及图片尺寸规则，追加“去掉含文字的图片”，输入为快照 ds_01/v1。若选择仅筛选，最终剩余 72 张可按 PARTIAL 交付并显示 INPUT_ONLY_SELECTED，不自动查库；若用户选择维持 100 张并批准原授权库补数，先清洗固定输入，再按缺口检索。该确认卡同时提供补数范围批准，后续仍须遵守人工节点门禁。数量目标变更必须在新 QuerySpec 显式记录。

新诉求提交后在同一任务对话中生成“清洗诉求 2”卡片，关联清洗节点和独立结果版本。原诉求、原数据集保持历史可查。清洗分支与运行记录分开：需求确认产生新 revision/branch，暂停恢复只替换 run。

### 12.9 数据集血缘与原需求解析

| 情形 | 处理 |
| --- | --- |
| 单一来源任务，用户有继续操作权 | 返回原 task 及输入快照，显示继承规则，确认后在该 task 创建清洗分支 |
| 用户查看的是历史分支快照 | 明示从哪版规则继承；base_revision 可为历史版本，expected_task_version 校验当前任务；不能静默混入当前分支新条件 |
| 原任务已完成 | 通过新增清洗需求建立新 revision/run，不调用仅限 PARTIAL/CANCELLED 的 continue，也不重开旧 run |
| 原任务已归档/删除或用户只有数据集使用权 | 不隐式恢复原任务；用户确认后，以可访问快照新建任务，原任务无权内容不得返回 |
| 多任务合并的数据集 | 建立新的清洗任务，以合并数据集版本为输入；记录所有可追溯父来源，不任意选择一个原 task 续聊 |
| 血缘缺失 | 明示无法继承原需求；取得用户新规则后创建新任务，不能猜测来源或继承约束 |

数据集访问权不等于原任务编辑权，新任务也不扩大素材用途或权限。合并数据集的规则可能互相矛盾，不能直接将各来源 QuerySpec 拼接；继承已批准用途/必要约束，清洗目标与规则由新需求确认。P1 实现单任务结果继续清洗；合并/外部数据集续洗在 P4 接入，P1/P2 遇到此类输入返回 FEATURE_NOT_SUPPORTED，不错误挂到某个原任务。

## 13. 数据模型与持久化规格

### 13.1 设计原则与关系

本节定义目标逻辑模型，不要求每个实体独立部署或首期全部启用。先采用一个 PostgreSQL 业务实例，按模块管理表和迁移；是否分区、读副本或拆库须依据实测容量和维护需求。DSH 会话及 MLflow 实验/追踪使用各自的受控存储，业务库保留关联 ID，不把它们当作任务账本。

必须分开四种数据：来源素材与版本、算子检测事实、任务相关规则判定、最终交付成员。不得在共享素材表上设置一个全局 is_valid 来表达所有用户的合格结论。

```text
library_catalog → library_index_version → vector_record_mapping
                                              │
asset_version → media_unit ←───────────────────┘
                    │
retrieval_task → task_candidate → candidate_hit → search_batch
       │                │
       ├→ query_revision ├→ validation_result ← feature_record
       ├→ task_run       └→ dedup_membership
       └→ result_set → result_membership → dataset_snapshot（冻结清单）
```

此图表示关联，不表示引用即获得访问权。媒体记录可在授权范围内复用；候选、反馈、判定和交付默认限定任务与需求版本。

下表中的 tenant、task、revision 等均为服务端绑定的标识。媒体资源共享使用明确的 resource_scope 与 ACL；任务域使用 tenant_id 与 task_id，不能仅凭共享媒体 ID 跨任务读取结果。

### 13.2.1 流程持久化扩展

| 实体 | 关键字段 |
| --- | --- |
| workflow_policy_revision | task、版本、五节点推进模式、操作者、生效范围/时间 |
| cleaning_request | branch/parent、task/revision、输入范围及清单水位、差异/完整规则、草案/活动/历史状态 |
| workflow_node_instance | task/branch/revision/iteration/type、node_id/version、run/generation、执行及门禁状态、策略版本、输入输出摘要、时间/错误 |
| node_output_version | 节点/版本、视图类型、不可变清单或水位、统计与摘要 |
| node_approval | 输出/策略摘要、批准者/决定/时间、幂等键及失效原因；可扩展 confirmation_request 实现 |

retrieval_task 增加 active_branch_id；run/batch/cleaning_operation/result_set/snapshot 关联 branch_id 并约束 task/revision 一致。节点实例按 task/branch/iteration/type 唯一；重试记录 attempt，重做产生新输出版本并失效旧审批。分支切换和运行替换按第 11 节原子执行。已有 P0 工件须据此迁移，不表示现有实现已支持。

### 13.2.2 追加清洗的输入与对话绑定

cleaning_request 补充 origin_entry、conversation_id、source_task_id（可为空）、parent_branch_id、base_revision、input_selector、input_manifest_ref/digest、input_watermark、refill_policy、规则差异及完整规则摘要。input_selector.kind 为 task_candidates/result_set/dataset_snapshot，并携带对应引用；候选池在提交事务的可见水位冻结成员，结果集/快照引用不可变版本。

refill_policy.mode 为 input_only/maintain_target。input_only 不派发范围外检索，必须与 allow_auto_refill=false 一致；maintain_target 记录目标及批准的库范围，并与 QuerySpec/执行策略一致校验。后者表示“固定起始输入 + 允许补充”，不能在 UI 标成“仅清洗该数据集”。批准摘要覆盖输入版本、规则、目标及补数范围。

conversation_message 保存 message_id、task/branch/revision、输入引用和操作者，形成需求消息到分支的可追溯映射；DSH 会话仍按第 9—10 节隔离，不直接复用其他分支完整对话作为执行依据。数据集血缘保存来源 task/revision/result_set 与多父来源；引用不授予访问权。

创建新任务或新分支时，对消息、草案、输入绑定和幂等账本原子提交或以持久操作恢复。相同客户端提交幂等重放，避免反复点击生成多个清洗诉求。权限失效时暂停并说明可见原因，不用其他数据集静默替换。

### 13.3 素材标识、媒体粒度与向量映射

1. 默认 source_asset_id 只在 source_namespace 内唯一。asset_version 的逻辑唯一键为 resource_scope + source_namespace + source_asset_id + source_version；已有全局 ID 可复用，但要登记生成规则与来源映射。
2. source_namespace 表示来源 ID 所属系统/集合，library_id 表示检索入口，两者不是同一概念。不同来源即使 ID 或内容哈希相同，仍保留独立来源和授权关系。
3. 来源没有可靠版本时，先用可靠内容摘要或来源服务确认的不可变版本补齐；只有可变 URL 时记录观测版本和“可复现性受限”，不能伪造稳定内容版本或永久复用旧特征。
4. media_unit 使用明确粒度。clip 区间按整数毫秒规范化为半开区间 [start_ms,end_ms)，满足 0 ≤ start_ms < end_ms；whole_video 与覆盖全长的 clip 仍有不同类型，计数时按规则归并。帧保存可靠帧序号/时间定位；未经验证不能从帧数换算视频数。
5. image/whole_video 无片段区间，不能依赖普通含 NULL 组合唯一键自动去重。可采用按 unit_type 的独立唯一约束/部分唯一索引，或服务端生成且数据库唯一约束的 canonical_unit_key；字段 CHECK 同时限定类型与区间合法性。
6. Milvus 主键须连同连接/database/collection 的不可变绑定、向量字段、业务索引版本和主键类型解释。不得以一个裸 ID 在所有库内查找。主键可能被复用的索引重建必须产生新业务版本。
7. 一条向量映射到明确的检索媒体单元；同一单元可以有多条向量。帧命中聚合为片段时，保存生成规则与原帧命中证据，交付候选引用片段 unit_id，不丢失帧级血缘。
8. 初期复用已有映射，先盘点与补齐缺口，不要求全库重新编号或重新生成 embedding。候选命中后按需登记映射可以作为受控接入方式，但缺失或冲突映射不得进入可交付集合；已有映射可由现有服务解析，无须在 PostgreSQL 复制全库全部行。

只在任务候选和命中表记录 ID、版本、分数、来源等，不把命中的 embedding 逐份复制到 PostgreSQL。内容去重只产生关系和代表选择，不物理删除来源记录或绕过来源授权。

### 13.4 唯一性、索引与数据库隔离

| 对象 | 必须落实的约束 |
| --- | --- |
| query_revision | tenant + task + revision 唯一；内容确认后不可原地修改 |
| task_run | tenant + task + generation 唯一；同任务最多一个具有有效提交资格的运行代次 |
| task_candidate | tenant + task + unit_id 唯一 |
| vector_record_mapping | index_binding_id + vector_field + 类型化 Milvus 主键唯一；相同物理记录的多个业务入口须解析到相同媒体版本，不一致视为冲突 |
| candidate_hit | batch + candidate + 原始向量记录/命中单位唯一，防重试重复写入 |
| validation_result | 同一判定执行幂等；按 revision + candidate + rule_digest + evaluator_version 选择有效判定；重评尝试保留历史而非覆盖 |
| result_membership | result_set + candidate 唯一；同一结果版本中一个去重簇最多一个交付代表 |
| task_event / outbox | event_id 唯一；task 内 sequence 唯一且单调 |
| operation_ledger / usage_attempt | 逻辑 operation 与真实 attempt 分开唯一；费用事件在供应商/账号作用域内幂等 |

同任务的活动状态集合必须在实现前明确，使用状态约束/部分唯一索引和行锁维护；时间到期不会自动改变唯一索引中的状态，接管必须在事务内终止旧代次并提升 generation。Worker 提交仍需 fencing 校验，租约不代替代次栅栏。

任务域关联使用包含 tenant/task 的复合外键或等效强约束，防止把另一租户候选挂进本任务。共享媒体关联先检查 resource_scope/ACL，不把“外键存在”当作可访问证明。PostgreSQL RLS 可作为纵深防御，不能替代应用授权；运行角色不能以 superuser/BYPASSRLS 绕过，表所有者绕过行为需专门处理。连接池使用事务局部身份上下文并验证复用不会串租户。[PostgreSQL 行级安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

常用索引优先覆盖 tenant/owner/state/created_at、task/revision、task/generation、task/unit、batch/candidate、operation/state、outbox 投递状态与重试时间。主键、状态、时间、版本和关联字段采用普通列；QuerySpec、算子参数、灵活检测值可用 JSONB。大型 OCR、逐帧特征及完整证据放受控对象存储，以引用和摘要关联，不无限堆入 JSONB。

NULL、部分唯一索引与外键约束需在选定 PostgreSQL 版本实测，不能只靠应用先查询再插入防并发重复。[约束文档](https://www.postgresql.org/docs/current/ddl-constraints.html)、[部分索引文档](https://www.postgresql.org/docs/current/indexes-partial.html)

### 13.5 事务、运行代次与结果版本

禁止把向量搜索、媒体下载、LLM 推理或清洗计算包在长数据库事务中。耗时任务在事务外执行，提交阶段用短事务验证资格并持久化。

- **确认需求**：校验 task_version、base_revision、proposal_digest → 更新需求状态/当前指针 → 递增 generation 并栅栏旧 run → 创建新 run/待执行记录 → 写 outbox，在同一事务内完成。
- **提交检索/清洗结果**：校验 tenant/task、confirmed_revision、generation 和 operation 输入摘要 → 幂等写入候选/命中/判定 → 更新结果发布所需状态及 outbox。过期结果可按策略保留为历史证据，但不得进入当前有效集。
- **发布结果版本**：先构建待发布 result_set，确保判定和重复关系完整；再以短事务校验当前版本及资源有效性、切换 current_result_set_id、更新统计并写事件。构建中成员不能作为已交付结果暴露。
- **计数**：accepted_count 是当前已发布预览或最终结果的可重建统计，不是独立事实。与结果版本一致提交；定期重算对账。待复核、被拒绝、备选和重复代表之外的样本不能计入交付数。
- **事件与费用**：outbox 与业务变更同事务写入；消费者按 event_id 去重。真实 paid attempts 分别记录，重复费用回调不重复入账；未知费用保持待对账。

分页游标必须绑定 tenant/task/revision/result_set_id 与稳定排序键。补数和反馈发布新版本时，原分页继续读取原结果版本，或明确返回需刷新，不能静默把不同版本拼成一页。可通过增量成员/版本区间等方式降低存储开销，但不能改变稳定读语义。

结果成员不可变不等于访问权不可变。每次读取、预览、签发媒体地址及导出仍核查当前权限；撤销后即时阻断，异步发布新的可见结果版本并重算达标状态。在重算完成前统计标记“权限变更后重算中”，不继续宣称当前可交付数量已达标。

“即时阻断”适用于服务端受控访问路径。已签发的对象存储直链未必支持单链接即时撤销：要求严格撤权的媒体必须经授权网关读取，或使用已验证的可撤销访问机制；仅使用短期签名链接时，明确其剩余有效期和已批准的风险窗口，不承诺零延迟撤销。已下载到客户端的内容不能技术性召回。

### 13.5.1 工作集、预览与交付

| 对象 | 生命周期与用途 | 对用户承诺 |
| --- | --- | --- |
| working_set | 构建中，可持续更新；内部计算使用 | 不直接提供分页或交付计数 |
| result_set，kind=preview | 每次发布均不可变；RUNNING/PAUSED 可查看、复核和反馈 | 合格预览，尚未构成最终交付 |
| result_set，kind=delivery | 最终重新校验后发布；可为完整或部分交付 | 成员、排序、判定引用冻结 |
| dataset_snapshot | 引用 delivery 生成不可变清单及摘要 | 固定历史内容；访问仍受当前授权约束 |

result_set.status 为 building/published/abandoned；kind 与 status 分开，预览变最终须创建新 ID，不原地换类型。working_set 可由内部表/未发布 result_set 实现，不要求新建服务。preview 发布事务校验 revision、generation、选择策略及资源有效性，然后原子切换 current_result_set_id。

计数固定为 eligible_unique_count（去重后合格候选总量）、accepted_count（当前发布版本选中数）、reserve_count、pending_review_count、currently_accessible_count 和 counts_status（fresh/recomputing）。103 条合格且目标 100 时分别为 103、100、3；缺口按当前可交付选中数计算。撤权处理中 currently_accessible_count 可为 null，counts_status=recomputing，禁止继续显示“当前已达标”。历史 snapshot_count 固定为导出时数量。

预览反馈必须附 result_set_id 与 candidate_id；针对重复簇还附 dedup_version/cluster_id。新版本簇发生拆合时旧簇反馈不能自动扩大到新成员，须重新确认作用域。只删单条的反馈随任务保存并在新 revision 显式继承；恢复拒绝项须用户显式操作。

终结准备事务创建待发布 delivery、写 snapshot 待生成记录并将 stage 设为 FINALIZING，关闭检索/清洗提交资格，仅保留受控快照发布操作资格；清单写入、摘要核对后还须通过打包节点门禁，再切换发布指针并置 COMPLETED/PARTIAL。对象生成采用 outbox/有限幂等重试，重试中停留 FINALIZING，耗尽后 FAILED；人工打包批准按第 12.7 节等待，待批准清单不能作为正式交付。取消若先取得提交权则未发布对象标记待清理；终结完成后晚到批次不得更换 delivery。

### 13.6 PostgreSQL 与 Milvus 的同步及故障处理

不假定两个数据库存在统一事务。由已有索引生产链路或业务索引接入服务负责同步，不让检索 Agent 自行修改 collection。Milvus 标量字段是业务/来源元数据的检索副本，不开放两套独立人工修改入口。

建议同步状态：pending → writing → verifying → ready；失败进入 failed，可幂等重试；删除/撤销使用 tombstoned 或等效失效状态。ready 的含义是映射正确且在约定读取一致性与可见水位下已可查询，不等于索引构建状态或全局所有副本瞬时可见。

| 场景 | 处理契约 |
| --- | --- |
| 新增/更新素材索引 | 先登记预期映射/版本与持久化事件，再异步按稳定主键写 Milvus；校验媒体映射、模型信息和可查询性后发布 ready |
| Milvus 已写成功但确认丢失 | 按索引版本/主键幂等重试并对账，不能再造一份业务素材或假设一次网络超时就是失败 |
| 现有索引接入 | 只读盘点并登记版本/能力，抽样及自动校验主键映射；无法证明映射的命中隔离，不要求先重建所有向量 |
| 召回存在但找不到媒体 | 标记映射异常或来源失效，不计有效；告警/补偿，并按缺口补数 |
| 删除、许可变化或权限撤销 | 业务访问路径即时拒绝，失效媒体引用/缓存；异步更新过滤字段或删除向量，由授权的索引管理链路执行；不能等 Milvus 更新才阻断 |
| 模型/索引重建与别名切换 | 注册新版本、验证匹配编码器和映射，按第 6.5 节处理旧计划；不静默把旧计划指向新空间 |
| PostgreSQL 不可用 | 停止新调度及结果发布；Worker 只能暂存有摘要的尝试结果，不绕过权限/账本直接交付 |
| Milvus 不可用 | 保留业务任务和已完成结果；受控重试、部分交付或暂停，不宣称全库无数据 |

对于动态 ACL，检索范围须由当前权威授权决定；若检索副本过期而无法安全限定范围，应暂停该分支或使用已批准的安全范围，不能仅靠最终展示过滤来弥补前置越权。媒体读取前也必须复核，避免未授权内容进入模型或算子。

对账至少覆盖映射缺失/冲突、孤立向量、失效素材残留、模型/维度不匹配、同步积压及失败。不要仅比较两边总行数：同一素材可能存在多个向量，合法删除也可能异步完成。同步完成时限、撤权传播/阻断指标和对账频率在 P0 冻结。

### 13.7 特征缓存、用户反馈与数据集清单

feature_record 只保存可复用事实。缓存键包含媒体单元/内容版本、特征 schema、模型/算法、预处理和检测参数；涉及用户提示词时加入提示词与上下文指纹并限制作用域。内容哈希相同不自动授予跨来源/跨租户缓存读取权。

validation_result 属于任务需求版本。例如 A 要“不要文字”，B 要“保留品牌文字”，两者可在授权范围内复用 OCR 事实，但各自产生不同判定。缓存的旧判定只有在规则、素材、模型、授权与执行语义均兼容时才可被新版本显式引用；不得直接沿用另一任务的有效数量、用户反馈或代表样本选择。

导出清单包含媒体单元稳定 ID、来源及素材版本、内容摘要、视频区间、命中与验证引用、去重策略、QuerySpec revision、result_set_id、Skill/模型/算子版本和授权用途。访问地址按需签发，不把长期有效的私有链接写进永久清单。若源库无不可变媒体版本，明确标记可复现性受限。

数据保留按候选、证据、事件、快照分别制定期限；引用中的审计/交付对象不能被缓存清理误删。删除用户任务不等于删除共享媒体或 Milvus 向量。备份恢复需验证业务账本、媒体清单与索引版本可重新关联；现有向量库的备份由其维护流程负责。

### 14.1 接口清单

所有接口在业务服务实现，不对外暴露 DSH 内部 RPC。身份由登录令牌确定，前端请求中的 tenant/user 字段不作为授权依据。

| 方法与路径 | 功能 | 核心约束 |
| --- | --- | --- |
| POST /v1/retrieval/tasks | 创建任务 | Idempotency-Key；返回 202 和 task_id |

需求内容变化才创建新需求 revision；暂停恢复、原条件继续、执行模式或限制变化均保留 confirmed_revision。恢复/重试创建新的 generation，执行策略变更单独版本化。COMPLETED 默认返回既有快照；要求补充/更新内容须作为明确的新需求处理。FAILED/PARTIAL/CANCELLED 的原条件继续须为用户显式操作，历史运行和故障记录保留。

### 14.1.1 API 实施约定

P0 交付并评审 OpenAPI 3.1、QuerySpec/规则/清洗清单 JSON Schema 及错误样例；P1 前后端契约测试引用同一工件。本文接口表规定语义，不代替完整 OpenAPI。创建和异步操作返回 202 + operation_id/status_url；同步读取返回 200；版本冲突 409、语义/能力不支持 422、未认证 401、无权访问 403 或按统一存在性隐藏策略 404、限流 429、依赖不可用 503。错误体包含稳定 code、字段路径和 retryable，不能以 HTTP 200 包装失败。

所有有副作用的 POST 使用 Idempotency-Key；作用域为 tenant/user/task/route，创建任务为 tenant/user/route。最小保留期在 P0 冻结，过期不得宣称仍能防重复；异步长操作还依赖持久 operation_id。重试原请求使用相同 key 和正文。控制接口统一使用 expected_task_version，不混用另一套 ETag 并发规则。

补齐以下接口：

| 接口 | 阶段 | 契约 |
| --- | --- | --- |
| GET /tasks/{id}/confirmations | P1 | 返回授权用户可处理的未决提案、摘要、影响与 task_version |
| POST /tasks/{id}/reviews | P1 | 绑定 result_set/candidate/rule_digest，记录人工证据与复核结论 |
| POST /tasks/{id}/finalize | P1 | 用户显式请求完整或部分交付；校验 task_version，进入 FINALIZING；不足不可标记 COMPLETED |
| POST /tasks/{id}/mode | P2 | RUNNING 时更新交互/后台模式与策略；不重复新建检索批次 |
| GET/POST /tasks/{id}/acl | P2 | owner 管理角色；只能共享所有参与者有权访问的结果，禁止转授源素材权限 |
| POST /tasks/{id}/archive | P2 | 无活动运行才归档；不删除素材 |
| DELETE /tasks/{id} | P2 | 幂等创建删除作业，返回删除操作 ID；受保留规则约束 |
| GET /operations/{id} | P1 | 授权后查询导出/复核/删除等异步作业 |
| GET /snapshots/{id} | P1 | 历史数量、清单摘要、当前授权状态和访问能力 |

以上路径均带 /v1/retrieval 前缀。P1 未支持的协作/模式功能不在 UI 展示，直接调用返回 FEATURE_NOT_SUPPORTED。reviews 不能替代修改规则的 feedback；VALIDATION_UNCERTAIN 作为逐候选判定原因，批次含 unknown 时仍可正常成功返回。

results 明确指定 revision 和可选 result_set_id，首屏返回固定版本及游标；游标绑定身份作用域、过滤、稳定排序键和结果版本，签名防篡改。旧版本过期返回 RESULT_VERSION_EXPIRED，不静默跳到新版本。export 只接受 delivery/snapshot；运行中请求导出先要求显式部分交付，不能把 preview 标为最终结果。

SSE sequence 在 task 生命周期单调不重置。重连使用 Last-Event-ID；事件过期返回 EVENT_HISTORY_EXPIRED 及状态快照入口。状态快照带 as_of_sequence，客户端随后订阅大于该位置的事件，服务端须支持回放以弥补获取快照与订阅之间的窗口。payload 含 task_version、revision、generation、result_set_id 和 event_schema_version。

### 14.1.2 流程与分支 API

以下接口带 /v1/retrieval 前缀，P1 实现，写入统一授权、幂等与版本校验：

| 接口 | 用途 |
| --- | --- |
| GET /tasks/{id}/workflow | 当前或指定分支的各轮节点、门禁和策略版本 |
| GET /tasks/{id}/nodes/{node_id}/outputs | output_version/view_type 分页读取扩词、候选、合格/淘汰/待复核、补数计划及包清单 |
| POST /tasks/{id}/workflow-policy | 修改五节点模式及生效范围；包含当前待批节点时绑定其输出 |
| POST /tasks/{id}/nodes/{node_id}/decisions | approve/reject，绑定输出摘要与 node/task 版本 |
| GET/POST /tasks/{id}/cleaning-requests | 列出历史或新建草案分支，绑定 parent/base_revision、输入范围及新增条件 |
| GET /tasks/{id}/runs | 执行历史、分支、触发原因、前后继 run 和停止原因 |

cleaning-requests 与 feedback 共用领域事务，不因一次反馈建立两份需求；草案继续通过 confirmations 确认。reviews 使用 review 视图版本及 candidate/rule_digest，不要求 unknown 在合格 result_set 内。人工节点批准仅接受具备权限的用户操作；auto 推进由服务端策略执行并记录来源。

创建任务增加 node_modes；省略时采用界面明示的五节点 manual 基线，并在响应返回实际 workflow_policy_revision。字段纳入 OpenAPI/schema 和幂等摘要。SSE 增加 branch_id、node_instance_id、iteration、node_version、output_version、gate_status；历史分支事件不能覆盖当前分支视图。

### 14.1.3 追加清洗上下文与提交

新增 GET /v1/retrieval/snapshots/{id}/continuation-context，只读返回当前用户可见的 origin_task、可继承规则、输入版本摘要、can_append_to_task、是否需新建任务及可见原因。此接口不自动创建或恢复任务。

POST /v1/retrieval/tasks/{id}/cleaning-requests 增加 origin_entry、parent_branch_id、base_revision、expected_task_version、input_selector、refill_policy 和 text。后端从真实关联核验来源，不信任客户端任意组合的 task/result/snapshot。所有提交保留 Idempotency-Key，响应返回 cleaning_request_id、branch_id、confirmed_revision/pending_revision、输入摘要、规范化规则差异、所需确认及 workflow_url。

```json
{
  "origin_entry": "dataset_detail",
  "parent_branch_id": "branch_1",
  "base_revision": 1,
  "expected_task_version": 7,
  "input_selector": {
    "kind": "dataset_snapshot",
    "snapshot_id": "ds_01"
  },
  "refill_policy": {
    "mode": "input_only"
  },
  "text": "再去掉含文字的图片"
}
```

该请求只表达输入与新增条件；身份由 W3 认证边界提供，完整 QuerySpec 由解析/合并/验证后确认，不将 text 当作直接执行脚本。引用过期或不可访问不得自动解析到最新版本。历史 base_revision 可以作为分支来源，但并发保护仍使用当前 expected_task_version。

需新 task 的场景使用创建任务接口的 source_input 扩展，包含固定输入引用及显式新目标/规则；P4 合并数据集能力未启用时明确拒绝。不得用仅访问数据集的权限调用原任务写接口。OpenAPI/schema 与服务实现须一起更新后才可启用上述字段；现有代码尚未支持。

### 14.5 错误规范

统一结构为 `code / message / retryable / task_id / revision / operation_id / trace_id`，不得返回密钥或底层内部地址。

| 错误码 | 处理 |
| --- | --- |
| INVALID_SPEC | 指出冲突或缺失字段，请用户修正 |
| REVISION_CONFLICT | 返回可访问的最新版本，要求重新确认 |
| ACCESS_DENIED | 不返回受限资源详情；资源存在性按组织策略统一隐藏 |
| EMBEDDING_INCOMPATIBLE | 停用该库分支，修正查询编码器配置 |
| LIBRARY_UNAVAILABLE | 受限重试或报告来源不可用 |
| EXECUTION_LIMIT | 保留部分结果，按策略继续或转后台 |
| COST_LIMIT | 在费用限制适用时停止新增付费调用并提示 |

| INDEX_SNAPSHOT_EXPIRED | 旧快照不可读取，暂停分支并按策略选择新版本 |
| STALE_GENERATION | 拒绝旧执行提交，记录后忽略 |
| MODEL_OUTPUT_INVALID | 有限修复尝试后暂停/失败 |
| VALIDATION_UNCERTAIN | 进入待复核，不当作硬规则通过 |

```json
}
```

数值、素材和规则判定仅为协议示例。输出还需在作业级记录 Data-Juicer/扩展包/模型/环境/配方版本、输入摘要和成本。执行失败时 observation 可为空、error 必填，受影响规则为 unknown 或未执行，不伪造业务 fail。

完成协议：

1. Worker 将逐条结果写到当前 attempt 的临时或不可变结果清单。
2. 每个输入候选在约定阶段都有结果、错误或未执行记录；不得无记录地丢失。
3. Worker 返回结果清单、摘要、输入/输出覆盖统计和 attempt_id。
4. 服务端校验身份、generation、清单完整性及版本，在幂等事务中引用结果并发出事件。
5. 结果集服务统一维护跨轮重复簇与有效数量；Worker 不自行设置任务 COMPLETED。

单条成功结果可保留以便重试失败部分，但不能在作业尚不完整时宣称整个批次完成。相同 operation_id + 输入/配方摘要的重复请求返回同一逻辑作业；同 ID 不同摘要拒绝。Worker 崩溃后读取已提交条目恢复，不要求上游执行器天然提供这一业务语义。

取消采用“停止派发 + 尽力中断 + 代次栅栏”：不可中断的 GPU/API 调用允许结束并记账，但不能再提交为当前任务有效结果。错误补偿不删除源素材。


## 15. 配置、部署、容量与可观测性

### 15.1 初始配置建议

以下为试点配置建议，不是实测最优参数，也不是上线 SLA；应随媒体类型、目标数量、算子成本和向量库能力配置。

| 参数 | 图片试点建议 | 说明 |
| --- | --- | --- |
| 初始选库数 | 由相关性及库吞吐配置 | 可先少量库探索，按缺口扩展 |
| 单轮查询分支 | 按资源和查询收益分配 | 包含原始核心语义，避免重复扩词 |
| 自动检索轮数 | 后台模式默认不设固定上限 | 由达标、取消、无进展和故障规则控制；交互模式可设响应窗口 |
| 单批候选数 | P0 实测后设定 | 总额度在并行分支之间分配，防止瞬时超载 |
| 任务候选总上限 | 可选 | 若启用，明确适用模式；达到后支持继续/转后台 |
| 无进展窗口 | 按媒体和策略配置 | 看新增有效数据与替代策略，不只看某轮低产出比例 |
| 结构化输出修复 | 有限次数，P0 校准 | 格式修复与正常检索轮次分开 |
| Agent/清洗模型用量 | 分项记录、共享任务资源策略 | 付费场景另设费用限制；后台任务按公平调度执行 |
| 单用户并发 | 按目标负载压测确定 | 超出排队，不直接拒绝合理目标数量 |
| 视频处理限制 | 单独配置 | 基于时长、抽帧和模型开销 |
| 结果分页 | 可先每页 50 条 | 只是展示参数，不是交付数量上限 |

此前版本“最多 5 轮、2500 候选、20 次模型调用”等数值未经过试点验证，本版取消其通用默认地位。团队可在受控试验配置中使用有限值，但必须明确适用场景和依据。

时间策略区分活跃执行、绝对截止、用户等待及队列等待；配置必须说明哪些时间计入限制。任务等待期间释放运行资源并保留状态。付费或内部成本限制仅在有真实价格/计费系数且业务需要时启用。

近重复、水印和风格阈值随验证器版本发布，不设跨模型通用阈值。创建任务时根据可获得的产出率和资源吞吐给出耗时/处理量估计，标记不确定性；目标超出交互窗口时推荐后台或分批。若超出当前硬能力，返回能力说明及可选方案，不静默缩小目标数量。

### 15.2 初期部署单元

1. 业务 API 与任务协调器：可先同一代码仓库、独立进程部署。
2. DSH Runtime Worker：受适配层管理，配置与业务服务独立发布。
3. Retrieval Worker：I/O 密集任务，可按库限流。
4. 清洗执行 Worker：独立 Python 环境承载 Data-Juicer 适配器和内部算子包，CPU/GPU/外部模型按资源类别排队；在线优先常驻模型、小批量执行。
5. PostgreSQL：目录/授权关联、媒体映射、任务事实、需求/运行/结果版本、事件与审计；不默认安装 pgvector。
6. 任务队列：至少一次投递、可见性超时、重试及死信处理。
7. 现有 Milvus 与素材存储：通过连接器接入，embedding 不迁移；索引同步/对账优先复用已有管道。Redis 为可选加速依赖，不是任务事实来源。

算子扩容与 DSH 扩容分离：增加 GPU 清洗能力不要求增加 Agent 数量。每个任务的有效调度器最多一个；同轮已批准检索批次可以受限并行。

### 15.3 容量估算方法

至少采集峰值到达率、平均任务活跃时长、每任务候选数、每候选验证耗时和模型调用次数。粗估：

- 平均在途任务数约等于任务到达率 × 平均活跃时长。
- 验证吞吐需求约等于任务到达率 × 每任务实际验证候选数。
- 并发模型需求取决于每任务需要推理的时间比例，不等于在途任务总数。

大批量导出和视频验证应使用异步通道。采用每用户/租户队列配额和公平调度，防止一个大任务耗尽所有模型或向量库并发。未取得实际负载数据前，不承诺“单机支持多少人”。

### 15.4 日志、指标和审计

所有链路带 `trace_id / task_id / revision / generation / operation_id`。至少记录：

| 维度 | 指标 |
| --- | --- |
| 检索 | 每库延迟、超时率、候选量、重复返回率、查询分支产出 |
| 清洗 | 每规则通过/拒绝/unknown 比例、耗时、算子/配方/环境版本、缓存命中、冷启动与模型推理次数 |
| 去重 | 精确/近重复比例、误合并抽检率、替换代表样本数量 |
| 闭环 | 首轮有效数、补数轮数、边际有效产出率、停止原因、损耗归因、Agent 唤醒原因/次数、自动执行动作数 |
| 成本 | 单任务模型 token/费用、算子时间、每新增有效样本成本 |
| 用户体验 | 创建响应、首批结果时间、有效数达标时间、反馈重算时间 |
| 可靠性 | 作业重试、重复事件、过期提交拒绝、恢复成功、积压时间、背压暂停/恢复、在途及预取量、重复检测合并次数、取消后浪费 |
| 安全 | 越权拦截、导出、共享、权限撤销、执行策略变化及适用的费用批准 |

审计保留“采取了什么动作、依据哪些可见证据、使用什么版本”，不要求存储模型隐藏思考过程。模型给出的简短决策理由可记录，但不能替代执行证据。

### 15.5 DSH 升级与回滚

升级流程：新版本隔离验证 → 适配层契约测试 → 固定离线任务回放 → 内部试用 → 小比例新任务灰度 → 观察 → 全量新任务切换。

运行中的任务尽量保留旧版本直到结束；新版本失败时把新任务流量切回已验证版本。业务数据格式的迁移独立管理，DSH 会话存储升级前备份，不假设升级后的会话文件可直接被旧版本读取。

### 15.6 Data-Juicer 与算子环境发布

单独维护三类版本：运行框架版本、业务算子/模型版本、配方/规则版本。任一变化都记录影响范围，不要求与 DSH 同步升级。

- 使用锁定依赖和镜像摘要部署；模型权重提前准备并校验，禁止线上首次请求触发未批准安装或下载。
- 内部算子包为独立发布物，镜像中预先安装。插件发现只允许已批准来源，不扫描用户可写任意目录。
- CPU、GPU 与外部 API 算子按资源分类路由；不为每个 OP 部署微服务。
- 本地、Ray 或其他执行路径逐个验证；在线模式不支持某 OP 时显式路由到已批准路径或拒绝，不偷偷切换资源规模。
- 工作目录、临时媒体、追踪输出按租户/任务/operation 隔离；Data-Juicer 的中间文件与日志同样纳入清理和权限控制。
- 任务终止、重试和保留期清理只作用于准确的作业目录；不得递归清理共享模型缓存或源库。
- 升级先跑单算子契约、质量、配方整体与在线/离线一致性回归，再灰度新作业。旧作业继续使用绑定版本。
- 缓存以版本为键；回滚切回旧版本及其对应缓存，不覆盖旧特征。新版本产生的事实不能无校验标成旧版本输出。

发布前必须确认依赖许可证、模型使用许可、外部调用数据出域规则和素材转换权限。Data-Juicer 的成熟度标签可用于筛选候选算子，但不替代本业务的测试门禁。


### 15.7 运维参数冻结与恢复

参数值不由本文猜测。P0 建立 parameter_baseline，字段包含名称、值/单位、适用阶段和媒体、测量方法、责任人、批准人、证据、配置版本。值未冻结标记 UNRESOLVED，不允许在相应上线门禁中记作通过。

| 参数组 | 内容 | 责任与最晚门禁 |
| --- | --- | --- |
| 在线性能 | T_first、T_batch、T_cancel、并发、数据规模、候选分布、单项资源 C_item | 后端/算法/业务，P0 试验前设目标，P1 退出前验收 |
| 检索能力 | 深度上限、游标寿命、过滤限制、读取一致性及 ANN 参数 | 搜索/索引团队，P0 |
| 闭环策略 | 单批上限、观察窗口、可执行策略集、Agent 唤醒条件、重试退避、队列等待/执行计时；P2 增加预取/在途上限与背压高低水位 | 后端/业务，P1；优化变更 P3 重验 |
| 权限传播 | 授权事件延迟、受控读取阻断时间、缓存失效、直链风险窗口 | 身份/素材团队，P2 前 |
| 可靠性 | PostgreSQL/队列/对象存储 RPO、RTO，outbox 延迟、死信处置时限 | SRE/后端，P2 前 |
| 保留与恢复 | SSE 保留、幂等保留、结果游标寿命、候选/证据/快照/审计期限 | 后端/数据负责人，P2 前 |
| 容量 | GPU/内存/临时盘、队列积压、租户公平调度和长期任务等待策略 | SRE/算法，P2 前 |

备份恢复演练包含数据库时间点、对象清单摘要、索引绑定和未完成操作对账。恢复期间停止调度，重新确认权威授权有效后才签发媒体访问；历史备份不能恢复已撤销的访问权。队列丢失时由持久未完成操作/outbox 重建；对象存在但数据库未引用时先对账，过保留窗口才清理。

### 15.8 媒体处理与数据保留

媒体解析 Worker 使用受控解码器与最小网络权限；下载前校验授权引用，下载中执行字节上限，下载后校验真实格式、大小和内容摘要。限制图片像素、视频时长/帧数、解码 CPU/内存、GPU 和临时盘；限值在 P0 绑定媒体配置。异常文件返回 RESOURCE_LIMIT/UNSUPPORTED_MEDIA/DECODE_ERROR，不伪造成业务条件失败。P1 试点即须测试损坏媒体、超大媒体和 MIME 不符。

删除任务先设置 task_lifecycle=deleted、deletion_status=pending 并撤销入口访问、栅栏运行，再通过删除作业清理任务域对象、DSH 会话、缓存引用和导出地址；deletion_status 独立记录 running/completed/completed_with_retention/failed，不新增任务生命周期枚举。共享媒体与共用特征只移除该任务关联；无其他合法引用且达到保留期的对象才清理。最小审计按批准保留策略保留，记录清理范围、例外、原因和完成时间；legal hold 由授权管理员设置，不由模型决定。备份中的保留/到期删除及恢复后重新执行删除登记必须形成操作流程。用户可查询删除作业和仍保留的最小数据类别，不能在存在保留例外时宣称全部物理删除。

## 16. 测试与验收规格

### 16.1 固定评测集

试点建议建立至少 200 条业务需求，覆盖图片与视频、来源/风格混淆、否定、数量、配额、跨库重复、多轮反馈、无法满足的条件；另建近重复正负样本对与视频时序验证集。

评测集需固定可访问素材快照或可追溯版本。标注者记录目标库、硬条件、允许解释和相关素材；主观风格由业务制定标注准则，并抽取双人复核。不能只用 Agent 自评证明质量。

### 16.2 必须通过的验收场景

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A01 | 用户表达“不要人物” | 否定进入规则并被执行，扩词不丢失否定 |
| A02 | “小红书来源”与“小红书风格” | 解析不同；不确定时澄清，不静默混同 |
| A03 | 用户无权访问的库最相关 | 不检索、不展示该库描述或候选 |
| A04 | 两个库使用不兼容 embedding | 分别正确编码或明确拒绝不支持分支 |
| A05 | 同一素材来自多库、多轮 | 计数不重复，来源证据完整 |
| A06 | 两张语义相似但不同的照片 | 不因单一语义相似阈值被误删 |
| A07 | 召回 100，清洗去重剩 60 | 显示有效 60，自动补数而非宣称完成 |
| A08 | 数量始终不足 | 到已配置执行限制或无进展条件时交付部分结果，支持继续且不放宽规则 |
| A09 | 用户新增文字排除规则 | 新 revision，旧结果重验，旧数量不沿用 |
| A10 | 用户放宽旧规则 | 可恢复此前候选，不只过滤上轮剩余集 |
| A11 | 两个用户同词检索但反馈相反 | 各自结果、Skill 上下文与历史互不污染 |
| A12 | 同用户两个任务 | 默认独立候选池和拒绝记录 |
| A13 | 两条并发反馈更新同 revision | 一条成功，另一条收到冲突，无静默覆盖 |
| A14 | 旧批次晚到、重复完成事件 | 不污染新版本，不重复计数或调度 |
| A15 | DSH/协调器/Worker 分别重启 | 已完成结果可恢复，重复回调不重复记账；实际发生的多次调用各自记录并计入用量 |
| A16 | 用户暂停/取消 | 停止新作业，旧代次不能发布结果 |
| A17 | 一段视频返回多个命中帧 | 按声明单位聚合计数，不按帧数凑数量 |
| A18 | 时序条件与单帧证据冲突 | 不以单帧证明动作顺序，unknown 不计入合格 |
| A19 | 库描述/OCR 含恶意指令 | 作为数据处理，不能开启工具或外传信息 |
| A20 | 检索中途撤销权限 | 后续读取、预览和导出被阻止，交付集及时重算 |
| A21 | SSE 断线重连 | 补齐事件或恢复快照，无倒退与重复计数 |
| A22 | 同幂等键重复创建 | 只产生一个任务；不同请求体返回冲突 |
| A23 | 快照导出后源素材变化 | 能按版本读取或明确标记可复现性受限 |
| A24 | 多分组配额 | 总数够但某组不足时，不宣称达标 |
| A25 | 同素材两个用户的文字阈值不同 | 可授权复用检测事实，但判定分别生成，不串规则 |
| A26 | 过滤器移除样本 | 每个被移除样本保留规则、原因、证据或明确未知状态 |
| A27 | 更换阈值与更换模型 | 仅改阈值复用兼容事实；模型/预处理变化正确失效缓存 |
| A28 | 算子超时、解码错误、依赖缺失 | 与内容 fail 分开，按策略重试或 unknown，不误计合格 |
| A29 | Data-Juicer Worker 崩溃及重试 | 已提交条目不重复计数，缺失条目可恢复，完整性可核验 |
| A30 | 新批次与旧批次出现重复 | 执行新增对历史比较，而非只做批内去重 |
| A31 | “不要水印”的清洗计划 | 采用检测筛除，不自动去除水印或修改源素材 |
| A32 | 非白名单算子/模块路径/依赖 | 编译或执行前拒绝，不动态安装或执行 |
| A33 | 在线与离线采用同配方 | 确定性检测在约定数值容差内一致；模型型算子满足冻结的统计质量门槛 |
| A34 | 取消期间长模型调用完成 | 费用可记录，过期代次不得发布当前有效结果 |
| A35 | 算子/环境升级回滚 | 作业版本可追溯，缓存不误用，旧配方能在绑定环境执行 |
| A36 | 两来源素材 ID 相同但内容不同 | 原始候选不覆盖、不误归并，来源血缘可追溯 |
| A37 | 检索过程中索引重建或快照到期 | 旧游标不跨版本复用；新 epoch 去重续查，无法续查明确暂停 |
| A38 | 歧义反馈等待确认、拒绝及陈旧确认 | 草案不执行，旧结果有版本标记；拒绝可恢复，过期确认返回冲突 |
| A39 | 总数够但某组不足 | 按组缺口补数，不以总缺口 0 停止；未启用配额时明确拒绝 |
| A40 | 后台长任务与执行限制 | 不因固定轮数结束；达到已配置限制保留结果，继续不清零用量 |
| A41 | 外部调用超时后发生真实重试 | 实际尝试分别计量，同一费用事件不重复记账，未知费用待对账 |
| A42 | 无匹配/多匹配/失效 Skill | 按阶段能力回退或澄清，不静默改用户硬条件 |
| A43 | 并行批次共享执行额度 | 原子预留与结算，不能各自取得整份剩余额度 |

### 16.3 质量与性能门槛

质量门槛需要业务评审签字后冻结。建议首轮讨论目标如下，均为拟定验收线，不是已经达到的结果：

- 明确实体、数量和否定条件的结构化提取准确率不低于 95%；高风险歧义允许澄清，不把猜测记为正确。
- 经授权库目录 top-3 覆盖标注目标库的比例不低于 90%；多目标场景同时报告目标库召回率。
- 交付样本经人工抽检的硬条件符合率不低于 95%；业务零容忍条件采用单独人工或确定性门禁，不用平均值豁免。
- 精确重复测试不得重复计数；近重复误合并与漏检分别报告，阈值由业务决定，不能只报告总体准确率。
- 同时对比“无扩词”“通用扩词”“业务 Skill 扩词”，衡量有效唯一产出与成本；不得只看召回数增加。

性能验收必须附硬件、并发用户数、库规模、素材大小、算子版本和缓存条件。试点可将非检索控制 API 的 p95 小于 1 秒作为初始目标；首批结果和任务完成时长先测基线再定 SLA，图片和视频分别报告。

### 16.4 评测统计口径与门禁

“200 条需求”是探索集起点，不保证每个关键分层有足够证据。P0 为图片/视频、规则类型、业务域、难例、可满足/不可满足条件分别制定样本量与最低覆盖；P1 只验收其开放能力，未开放视频不纳入 P1 分母。训练/提示词调整集与冻结验收集分开，发布后不得用同一验收集调参再宣称独立验收。

| 对象 | 必须报告 |
| --- | --- |
| 需求解析 | 全规则完全匹配率；数量、实体、否定分别的 precision/recall；自动确认覆盖率、澄清率与澄清后正确率 |
| 库路由 | 标注相关库集合上的 recall@k、至少命中一个有效库的比例；同时报告下游有效唯一产出 |
| 硬规则 | 逐规则误接收率、误拒绝率、unknown 比例；交付样本全部硬条件同时成立的比例 |
| 去重 | 样本对 precision/recall、误合并/漏合并、代表稳定性；对跨批次及链式相似另设用例 |
| 风格/语义 | 明确标注准则、双人一致性及分歧仲裁；业务接受率，不能只采用模型自评 |
| 闭环 | 目标达成率、部分交付率、有效样本成本、首批/最终/反馈延迟；按停止原因分层 |

比例指标均附 numerator/denominator 与 95% 置信区间；独立二项样本使用冻结的方法（如 Wilson），同任务内相关样本按任务聚类重采样，方法随 evaluator_version 固定。第 16.3 节的 95%/90% 是拟定点估计目标，P0 还须冻结置信下界或容差规则，证据不足记 INCONCLUSIVE，不能当成 PASS。

授权、越权、旧代次覆盖、重复计数等采用确定性断言，任一失败阻断对应阶段；零容忍业务条件由单独门禁验收。自动拒识不能通过缩小交付分母掩盖能力不足，质量必须和覆盖率/目标达成率一起评审。P2 图片生产开放前必须完成图片质量门槛，不能整体推迟到 P3。

每条测试记录包含 test_id、阶段、版本组合、输入/预期断言、数据快照、actual、PASS/FAIL/INCONCLUSIVE/NOT_RUN、证据引用及负责人。一个 A 场景可拆成多个 test_id，覆盖完成要求全部适用断言通过。

### 17.4 P0 在线清洗可行性验证

P0 已包含 Data-Juicer 兼容性验证；本节把通过条件明确为可测合同，不预先判定框架不适合在线执行。首选验证 Data-Juicer 适配器；有具体瓶颈再针对该算子比较常驻轻量调用路径，双方复用相同算法/模型，不重复建设整套清洗系统。

测试前由业务和研发登记首批延迟目标 T_first、单批 p95 目标 T_batch、单候选资源上限 C_item、取消后停止新增派发的时限 T_cancel、目标并发与素材分布。未确定这些值时可做探索实验，但不能宣告在线链路已验收。

| 验证项 | 方法 | 退出条件 |
| --- | --- | --- |
| 逐条证据 | 固定包含通过、失败、unknown 和执行错误的候选集 | 每条都有约定记录；移除样本原因可追溯 |
| 模型复用与延迟 | 在实际硬件测冷启动/热启动，采用多个批量档位 | 目标负载下达到已冻结 T_first/T_batch，记录初始化占比 |
| 用量与成本 | 分离模型调用、CPU/GPU 与检索开销 | 满足 C_item 或已批准资源档位，实际重试可计量 |
| 取消和恢复 | 批内取消、Worker 崩溃、重复回调 | 新派发在 T_cancel 内停止，旧代次不提交，已完成条目可恢复 |
| 隔离与版本 | 两用户相反规则、模型/配方切换 | 不串规则，正确缓存失效，版本可追溯 |
| 算子适配 | 所选执行模式运行完整配方 | 不支持能力显式拒绝，不能静默改变质量规则 |

试验结果形成“可用于在线 / 仅用于离线 / 需适配后复测”的逐算子清单。P1 只使用已通过所需门槛的路径；确认不适合在线的算子可改为预计算特征或批准的常驻适配，外部清洗契约保持一致。

### 17.5 存储与数据模型的分期要求

第 13 节是完整逻辑模型，按以下顺序落实，避免第一期同时建设全部扩展能力。

| 阶段 | 必须落地 | 可以暂缓 |
| --- | --- | --- |
| P0 | 盘点 Milvus 版本/collection/编码器/媒体映射，冻结授权、可见性、版本及计数契约；确定容量与恢复目标 | 不要求迁移向量、全量重编号或重算 embedding |
| P1 | 库目录与现有权限接入、媒体标识解析、任务/需求/运行代次、候选/命中、逐条判定、跨轮去重、结果版本与最小导出清单；相关唯一约束和故障幂等 | 目录向量化、跨任务特征共享、Redis、复杂分区、多维配额 |
| P2 | 多租户/任务隔离、连接池/RLS 适用验证、权限撤销、可靠 outbox、同步对账/恢复、备份演练及多人压测 | 在无容量证据时拆库或微服务化 |
| P3/P4 | 视频粒度扩展、配额、授权范围内的跨任务特征复用、规模化优化及下游数据集发布 | 只有真实效果/运维收益经验证时再评估引入 pgvector 或其他新存储 |

P1 的导出清单用于验证单任务交付与复现，P4 的发布是面向下游训练平台的正式契约，两者不冲突。P1 保留全部候选和淘汰依据；不能以“简化”为由只保留最终通过样本。

A44/A45/A48/A50/A51 中与图片试点相关的映射、计数、分页及约束场景在 P1 通过；A46/A47/A49 及完整多用户隔离、双库故障场景必须在 P2 开放多人生产前通过。只读接入现有索引时，A46 由索引生产团队联测或提供可核验证据，不能因检索服务不写向量而取消一致性责任。

### 17.6 阶段验收与执行顺序

阶段 P0—P4 表示实施顺序，不表示缺陷严重等级。安全条件从首次处理真实数据起生效；P2 是完整生产验证，不能理解为 P1 可以跳过基本授权、隔离和安全解码。

| 阶段 | 必须通过的 A 场景 | 限定 |
| --- | --- | --- |
| P0 | A04/A52/A57/A60 的能力探针及第 17.4 节算子试验 | 形成实测矩阵与冻结工件；不声称全链路已实现 |
| P1 | A01—A10、A13/A14/A16/A19/A22/A23、A26—A32、A34/A36/A37/A38/A40/A42/A43、A44/A45/A48/A50/A51、A52—A57、A59/A60/A62/A64/A66、A67/A68/A69/A71/A72、A73—A77、A79/A80/A81/A83 | 图片及单用户范围；A40 验证可恢复策略，生产后台调度在 P2 全量验收；A45 验证多向量/映射，帧聚合 P3 |
| P2 | P1 全量回归 + A11/A12/A15/A20/A21/A25/A33/A35/A41/A46/A47/A49/A58/A61/A70/A78 | 多人图片生产；A25 用安全测试验证隔离，跨任务共享未启用时应拒绝共享；A33 以清洗执行路径等价性验证，不开放数据生产 |

| P4 | 前期回归 + A58 的下游联测、A65/A82 | 发布/消费/撤权、缺口审批、训练评测集合隔离形成证据 |

A46 可由索引团队提供可核验联测证据。A58 在 P2 验证本服务快照撤权，P4 再验证消费者；阶段通过只覆盖明确列出的变体。A24/A39 保留历史编号，分别验证分配规则和总数足够时继续补组缺口，不删除旧测试记录。

落地顺序：

1. P0：产品确定图片试点场景、数据团队盘点两库与授权、算法验证必要算子；后端同步完成 schema/OpenAPI/DDL/状态转换设计；SRE 冻结试验环境和目标。
2. P1：先完成可信身份和媒体映射、候选账本及最小结果版本，再接入检索和清洗、固定补数与 DSH 决策，最后接 UI/复核/导出。每条链路携带版本与幂等标识。
3. P2：在同一契约上完成持久调度、多人权限、撤权、恢复、观测与容量验收；前三项流程优化（协调器常规执行、目录/检索分离、检测复用）在 P1 验证后，再启用并验收有界流水线。未经门禁放行，部署只允许受控试点入口。
4. P3：视频先完成媒体单位/片段生成/时序证据，再开放数量承诺；配额与自适应优化独立验收，不能一起上线后无法归因。
5. P4：先与下游冻结数据集消费和撤权协议，再接训练/评测入口；跨任务组装由下游服务负责。

## 18. 训练评测闭环的预留规格

### 18.1 数据集发布事件

检索结果确认后发出 `dataset_snapshot.published`，至少包含快照 ID、任务与需求版本、素材数、清单引用、内容摘要、授权用途、生产者及时间。它只表示数据集可供授权消费者使用，不等于批准立即训练。

多个管道进入训练前，由数据集组装服务负责：跨管道去重、来源比例、标签规范、训练/验证/测试集合隔离、许可兼容性和最终版本冻结。训练任务引用这个组装后的版本，而不是引用动态检索结果页面。

### 18.1.1 快照授权失效与消费者契约

快照的成员、摘要、生成时数量和授权用途不可变；当前 entitlement_status 与 currently_accessible_count 作为独立可变访问投影，不改写历史快照。发布时保存 authorization_snapshot（策略版本、用途、资源范围、核验时间），该记录是历史证据，不是永久访问令牌。

撤权、许可到期或用途限制变化时，本服务先阻断受控访问、失效地址及缓存，再通过 outbox 发布 dataset_snapshot.access_changed；完整失效使用 dataset_snapshot.revoked，部分成员失效使用 dataset_member.revoked。事件包含 event_id、snapshot_id、授权版本/生效时间、失效原因和受控成员清单引用，不把受限媒体内容放入事件。消费者幂等处理并可查询当前授权投影以对账，不能只依赖一次事件送达。

P4 消费者在下载和启动训练前重新核验用途与访问权限。事件接收者负责按冻结的用途政策决定暂停、停止、隔离或阻止下一次使用；具体在训任务、已生成模型的处理由训练平台/数据负责人审批，本检索服务不擅自终止外部训练。未确认处理责任、响应时限和联测结果时，不开放正式下游发布。

已下载文件不能技术性召回，消费者需有可审计处置流程。许可用途变化需要新的发布批准；不能只修改旧 snapshot 的用途。源素材无不可变版本的快照标记 reproducibility=limited，P1 可用于检索试点；进入正式训练须经过数据集组装服务显式接受或补齐版本，不能默认满足复现门槛。

已完成任务因撤权失去达标资格时只更新当前访问投影和通知，不自动开启新 run。用户显式继续/更新需求后再补数并发布新 delivery；历史快照保留原清单及失效状态。

### 18.2 评测问题进入检索

评测分析形成 `data_gap_request`：问题类别、失败样例引用、期望数据特征、目标数量/配额、允许来源、验收规则、负责人。检索 Agent 将其转为 QuerySpec，按本规格运行。

默认审批节点：问题归因确认 → 数据需求确认 → 数据集验收 → 训练预算与配置批准。对于低风险、固定预算、固定训练模板的场景，未来可按白名单自动通过部分节点，但需要单独评审。

### 18.3 防止评测污染

评测失败样例可用于分析，但不能自动把保留评测集原样加入训练集。下游组装服务必须按内容哈希、近重复和实体/时间等业务策略检查泄漏，并区分“新生产的相似场景数据”和“评测原样本”。

检索侧保存来源血缘和去重特征，为此提供依据；它不替代训练平台的最终集合隔离检查。

## 19. 主要风险与上线检查表

### 19.1 风险登记

| 风险 | 早期信号 | 处理 |
| --- | --- | --- |
| 向量与媒体映射错误 | 返回文件与命中内容不一致、同主键覆盖 | 物理绑定/索引版本/主键联合定位，缺失或冲突映射隔离 |
| 双库同步与权限漂移 | 失效素材仍被召回、过滤字段过期 | 权威权限前置校验与读取复核，异步同步、对账告警 |
| 动态结果翻页漂移 | 翻页重复/漏项或数量跳变无版本说明 | 发布 result_set 版本，游标绑定版本，计数同事务切换 |
| DSH 版本破坏兼容 | 启动/工具/事件契约回归失败 | 固定版本、适配层、灰度，不修改业务契约 |
| 清洗框架/依赖升级 | 算子输出或执行模式变化 | 固定镜像、契约/质量回归、按作业绑定版本 |
| 仅保留过滤后的数据 | 无法解释淘汰或放宽后恢复 | 检测事实、逐条规则判定与原始候选分别持久化 |
| 在线清洗启动开销过高 | 首批延迟主要耗在初始化 | 常驻 Worker/模型预热、增量计算，实测选择执行器 |
| 扩词语义漂移 | 候选增加但有效率下降 | 原始查询保底、扩词血缘、逐分支评估 |
| 去重过强 | 不同场景误合并 | 人工样本对评测，语义相似不直接等于重复 |
| 补数无限循环 | 游标不变、低增益、费用增长 | 查询指纹、任务执行限制、无进展停止和缺口报告 |
| LLM 自报完成 | 文本说完成但数据库数量不足 | 完成动作由服务端重新校验 |
| 多人污染 | 用户看到其他人的偏好/样本 | 会话、目录、缓存、权限多层隔离 |
| 故障恢复重复执行 | 重复有效计数或重复计费 | 幂等账本、fencing token、事件去重 |
| 规则识别误判 | 抽检发现水印/文字等漏检 | 三态、证据、阈值校准、高风险人工门禁 |
| 视频计数虚高 | 多帧或重叠片段重复计数 | 明确 count_unit、原视频映射及片段去重 |
| 用户目标不可达 | 指定范围与数量冲突 | 部分交付、解释约束、显式请求变更 |
