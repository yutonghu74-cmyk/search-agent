# 多规则清洗内部执行契约 v1

状态：通用框架基础契约与合成检测器执行器已实现；业务批准到执行的正式装配尚未实现。

## 输入

`ApprovedCleaningJob` 由受信业务层在发起人确认正式任务后构造，不接受草稿、模型输出或外部 JSON 直接发起。绑定必须含 tenant、owner、project、task、revision、generation、task_version、operation_id、输入清单摘要和配方摘要。候选只携带逻辑 ID、素材版本与内容哈希；受信媒体读取器再次核验当前授权、素材字节与摘要。

`CleaningRecipe` 记录来源审阅摘要、能力目录摘要、媒体类型、受信检测步骤和全部硬规则。同一检测步骤可为多个规则提供事实。规则仅支持显式 `eq`，软偏好留在排序层，不能当硬过滤。步骤使用逻辑 backend_ref、validator_ref、evidence_ref，不含 Python 模块路径、命令、URL、工作目录或用户注入参数。真实算子发布仍需满足规格书 7.8 的完整清单、模型/参数/资源/评测要求；当前没有默认已发布检测器。

`DetectionResult` 由已登记执行器返回：status 为 ok 时须有匹配验证器及证据引用，facts 是有限标量映射；unknown 没有事实/成功证据。逐候选逐规则输出 pass/fail/unknown。执行异常、无事实、证据不一致为 unknown 或整个作业失败，不能变成 fail 或 pass。所有硬规则 pass 只表示清洗判定通过；有效交付数量仍由业务层在授权、去重、版本检查后计算。

`recipe_bridge.compile_reviewed_recipe` 从受信编译器重新读取当前审阅草稿与能力目录，要求创建人审阅动作、版本和审阅摘要一致，再把硬规则转换为不可变 `CleaningRecipe`；软偏好不进入硬规则。它不接受外部预览 JSON，也不创建任务、批准作业或发起执行。来源审阅摘要和能力目录摘要保留在配方中；后续业务批准记录还须显式绑定正式 task/revision/generation、候选清单和配方摘要，不能把“审阅过”当作“批准执行”。

`recipe_bridge.require_confirmed_rules` 要求受信业务层先以当前授权读取正式任务，再核对任务保存的确认方案摘要、媒体类型和完整硬规则序列与配方逐项一致。例如确认方案包含 `text.present@1 == false` 与 `watermark.present@1 == false`，配方少一条、增加一条、改值或改类型均拒绝；确认方案中的软规则不转成硬过滤。纯校验不签发执行许可，也不证明该解释草稿就是任务确认时使用的来源；正式批准记录仍须保存来源审阅、任务需求版本与配方关联，在同一事务检查当前任务版本/generation 和候选清单。

`CleaningApprovalProposal` 冻结正式任务的 tenant/owner/project/task、revision/generation、批准前 `expected_task_version`、确认需求摘要、已发布候选清单引用与其素材身份/内容哈希、不可变配方。`proposal_digest` 覆盖这些字段；用户确认必须回传此摘要与期望任务版本，换清单、换规则、换版本都不得复用原批准。业务账本原子批准后生成 `CleaningApproval`，其 `task_version` 必须恰为批准前版本 +1；`approval.job` 才可构造执行器输入。数据类本身不代表授权或持久批准，不能接受普通用户/模型自行构造的对象作为凭据。

`src/dsh_retrieval/adapters/cleaning/` 已有受控通用调度：每项候选一次授权读取/哈希校验，相同步骤只执行一次，结果绑定原作业的 operation/revision/generation/recipe/input 哈希；返回前再次检查当前授权和版本，发布时仍需业务账本原子栅栏。当前配方仅支持独立步骤、`eq` 硬规则；规格书要求的显式步骤依赖/资源上限/失败处理版本化仍待补齐，不能静默运行依赖链。测试检测器仅提供合成事实，标 SIMULATED。真实 DJ 仍只有旧的宽度规则独立桥接，不能将本框架标作多规则真实 DJ 联测。

本地串联入口现在要求服务端注入 `ReleasedDetectorRegistry`，在读取媒体或发布尚未完成的预览前，将配方的能力目录摘要与当前目录逐项比对，再核对每条硬规则的已验证能力、谓词/媒体/操作符/值类型、编译后步骤绑定及实际检测器元数据。目录变更、人工/未发布能力、缺失或替换的后端均失败关闭；已发布预览的读取仍按业务账本重新鉴权。服务端还须注入 `DetectorArtifactManifest`：它在固定、非符号链接的部署根目录下，将每个 backend_ref 绑定到实现文件及可选模型文件的相对路径与 SHA-256，并要求运行时检测器声明同一绑定摘要。每次未完成执行/预览重试均复核根目录身份、文件类型、路径边界、符号链接、内容摘要及检测器元数据；缺失、替换、篡改或目录漂移在任何候选媒体读取前失败关闭。路径、摘要和清单只来自受信部署配置，业务请求、配方和普通用户不能提供或覆盖。

制品摘要验证只证明本地发布文件与已批准清单一致，不证明模型效果、许可证、资源策略、在线性能或质量门槛。真实发布仍需规格书 7.8、15.6 和 17.4 的登记、评测与环境验收；当前仓库不登记真实模型或生产实现制品。

`CleaningJobResult` 是唯一共享的逐素材多规则输出契约。它保留完整 `CleaningBinding`、候选身份、整体三态及每条硬规则的三态/原因/证据引用。`require_complete_cleaning_result` 要求绑定与已批准作业完全相同，候选和规则的数量、身份及顺序完全匹配；缺失、多余、换序、伪造绑定或错误总结均拒绝。`result_digest` 是稳定内容摘要，不是授权凭据。该数据类不做当前权限检查、不持久化、不计算有效数量；受信业务账本必须在同一发布事务中重新校验 task/revision/generation/operation/权限及输入清单。
