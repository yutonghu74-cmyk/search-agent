# 多规则清洗内部执行契约 v1

## 多节点 VLM 指令（2026-10-29）

已确认的单条语义图片规则可编译成多个 VLM 检查节点。服务端先按原文显式标点划定 1–8 个覆盖片段，每片段最多 320 字；超过边界拒绝准备，不删减需求。选定 VLM 以文本模式为每个片段整理检查说明，严格校验输出项数、顺序和长度；服务端把对应确认原文逐字附到最终指令，原文始终是判定依据，模型整理不得增加条件。每条指令连同执行顺序进入 recipe digest、检测器发布摘要和清洗批准卡；确认后后台逐节点用同一冻结 VLM 判图，任一必需节点 fail 则淘汰，unknown 不计入有效素材。最多 400 次 VLM 检查/批次，超过预算在准备时拒绝。

步骤结果按规则分别保留 pass/fail/unknown 与短原因；执行快照保存每个节点的原文、指令、模型与提示版本。当前图片每个完成节点的规则判定持久化在清洗检查点；重启后复验任务/授权/媒体哈希，仅跳过已持久化节点，继续未完成节点。未保存的外部 VLM 调用可能重复，非 exactly-once。原单节点记录没有新 `instructions` 字段时按旧配方摘要解释；旧结果读取不重算模型指令。

状态：通用框架基础契约与合成检测器执行器已实现；业务批准到执行的正式装配尚未实现。

## 逐图短原因（2026-10-28）

### 清洗批准卡执行说明（2026-10-29）

`cleaning/prepare` 兼容增加 `execution`、`detector_release_digest`、`steps`、`unknown_policy` 与 `confirmation_note`。VLM 执行说明由受信 registry provider 从正式任务生成，在保存提案前复验模型绑定；不接受客户端上传的模型/指令，不在准备时发送图片或调用模型。通用非 VLM registry 的 execution 为 null，不冒充 VLM。

批准提案仍由已有 recipe 与 detector release 摘要绑定规则、指令及模型配置；实际执行复验同一发布摘要。页面按钮捕获对应卡片的 task/proposal，而不是读取全局最新提案；取消卡片不提交批准，修改规则走既有需求反馈与新版本确认，不直接修改已批准配方。此切片不实现人工证据复核、复核计数重算或失败项手动重试。

`DetectionResult` 与持久化 `CleaningRuleVerdict` 新增可选 `reason_summary`（默认 null）与 `reason_truncated`（默认 false）。适配器先清理控制字符并按 Unicode 码点截断到 50；公共模型在写入前拒绝超长、空白、非法类型或无摘要的截断标记。VLM 的 fail/unknown 保留实际返回的可观察短理由，pass 默认省略摘要；不额外请求模型解释，不保存完整回答、内部推理或异常原文。

未知仍是待复核：事实不足为 `FACT_UNAVAILABLE`，普通检测器异常为 `DETECTOR_ERROR`，返回对象或验证器不匹配为 `DETECTOR_OUTPUT_INVALID`。授权、模型绑定及服务错误继续中止作业，不转换成图片淘汰。摘要只用于展示，不参与事实判定或合格计数。步骤接口返回短原因和截断标记，Chat 清洗明细按纯文本展示；历史缺失摘要明确显示未保存，不补造说明。

SQLite 读取旧规则记录时补两个默认值；无摘要的旧结果摘要保持不变，有摘要的结果使用 `multi-rule-cleaning-result@3`，摘要和截断标记参与结果哈希。升级后的记录不能由未支持新字段的旧服务写回。此变更不重跑旧任务、不补写历史理由、不改变配方批准或模型提示版本；仍未实现逐图检查点、持久化有限重试及人工复核处置闭环。

## 输入

### 逐图检查点与执行快照（2026-10-29）

`cleaning_checkpoints` 按 operation_id 保存批准 binding、实际执行描述、已完成候选的有序前缀、开始与更新时刻；与任务账本同库、同事务，硬删除会话时级联清理。执行描述仅接受受信服务提供的模型 ID/名称/提供方、指令、提示版本、配置摘要、算子；不保存连接地址或凭据。通用非 VLM 检测器只记录 backend_refs，不编造模型信息。

每张图片的全部规则完成并复验当前授权/任务版本后，原子保存该图片判定。重启/退避重试读取相同 binding 的已完成前缀；重复相同判定幂等，冲突、候选乱序、规则缺失、旧版本与撤权都拒绝。恢复时仍重新授权读取素材并校验字节摘要和大小，再复用判定，不重复调用模型。图片尚未保存、保存失败或执行中途退出可能再次调用该图片，不宣称外部 VLM exactly-once；当前不是逐步骤检查点。

`cleaning/status` 增加 progress：total/completed/pending/passed/rejected/review、已完成候选 ID/三态、开始/更新时间。completed 只表示完整保存的逐图判定，不是作业发布完成；只有所有候选完整且结果/预览事务成功才返回 completed 状态。通过数不等于去重入选数。当前最多 100 张，轮询读取固定事务快照，不是 SSE 或无限分页。Chat 活跃清洗期间持续轮询显示数量，切换任务后忽略晚到响应。

步骤结果返回各运行保存的 execution 与时间，elapsed_seconds 是开始至最后检查点的墙钟跨度，包含等待/重试，不是模型推理耗时。历史读取不再访问当前模型配置；旧记录没有快照时明确返回无快照，不回填伪造历史。运行时首次创建快照早于模型调用，不代表模型已完成。恢复须与原执行描述完全一致，配置变化仍需新版本确认。

### 清洗自动重试与恢复（2026-10-29）

SQLite 新增 `cleaning_dispatch_attempts`，按批准 operation_id 记录 task_id、尝试次数、状态、下次时间、尝试 token 和安全错误码。不改既有清洗结果账本格式；会话硬删除同时删除对应调度记录。没有历史记录的批准作业从零次开始，旧进程的内存失败无法追溯迁移。

自动执行最多 3 次（含首试），失败后退避 5 秒、10 秒；普通异常同样受预算限制。不可重试失败立即持久化 failed，预算耗尽为 RETRY_EXHAUSTED；重启和重复确认原操作不重置预算。终止失败没有绕过确认的手动重试端点，应检查原因后通过现有正式新版本确认流程执行。

外部调用前在事务内校验权限与当前批准版本并预占次数；结果回写按尝试 token 防止旧尝试覆盖新记录。外部调用不持有数据库事务。完成的权威结果优先返回 completed，旧版本返回 superseded，失败不得覆盖业务结果；错误正文不持久化。`cleaning/status` 增加 attempts、max_attempts；retry_wait 返回 next_attempt_at（Unix 秒），Chat 显示等待重试。

进程崩溃/最终状态写入失败时，预占次数仍保留，最早一小时后再次恢复；已持久化清洗结果沿用原恢复逻辑，不重跑检测。该时间窗是本地恢复保护，不是可续租的分布式执行租约，不能据此宣称长任务跨进程 exactly-once。运行中逐图断点和人工复核不在本次修复范围。

`ApprovedCleaningJob` 由受信业务层在发起人确认正式任务后构造，不接受草稿、模型输出或外部 JSON 直接发起。绑定必须含 tenant、owner、project、task、revision、generation、task_version、operation_id、输入清单摘要和配方摘要。候选只携带逻辑 ID、素材版本与内容哈希；受信媒体读取器再次核验当前授权、素材字节与摘要。

`CleaningRecipe` 记录来源审阅摘要、能力目录摘要、媒体类型、受信检测步骤和全部硬规则。同一检测步骤可为多个规则提供事实。规则仅支持显式 `eq`，软偏好留在排序层，不能当硬过滤。步骤使用逻辑 backend_ref、validator_ref、evidence_ref，不含 Python 模块路径、命令、URL、工作目录或用户注入参数。真实算子发布仍需满足规格书 7.8 的完整清单、模型/参数/资源/评测要求；当前没有默认已发布检测器。

`DetectionResult` 由已登记执行器返回：status 为 ok 时须有匹配验证器及证据引用，facts 是有限标量映射；unknown 没有事实/成功证据。逐候选逐规则输出 pass/fail/unknown。执行异常、无事实、证据不一致为 unknown 或整个作业失败，不能变成 fail 或 pass。所有硬规则 pass 只表示清洗判定通过；有效交付数量仍由业务层在授权、去重、版本检查后计算。

`recipe_bridge.compile_reviewed_recipe` 从受信编译器重新读取当前审阅草稿与能力目录，要求创建人审阅动作、版本和审阅摘要一致，再把硬规则转换为不可变 `CleaningRecipe`；软偏好不进入硬规则。它不接受外部预览 JSON，也不创建任务、批准作业或发起执行。来源审阅摘要和能力目录摘要保留在配方中；后续业务批准记录还须显式绑定正式 task/revision/generation、候选清单和配方摘要，不能把“审阅过”当作“批准执行”。

正式任务进入清洗时，`compile_confirmed_recipe` 只从当前已确认 `query-spec@2` 与服务端
`ReleasedDetectorRegistry` 重建配方；HTTP 调用方只能引用已发布候选清单和确认服务端提案，
不能提交 recipe、backend、模块路径、发布摘要或检测结果。批准 operation 本身构成持久派发源：
后台协调器扫描“已批准但尚未发布 result-set”的当前 operation，进程重启后继续；若逐条结果已
原子落账但预览尚未发布，重试只续发预览，不得再次读取素材或调用检测器。旧 revision/generation、
撤权、发布制品变化及不可重试错误仍失败关闭，不能转换为 unknown 或清洗通过。

`recipe_bridge.require_confirmed_rules` 要求受信业务层先以当前授权读取正式任务，再核对任务保存的确认方案摘要、媒体类型和完整硬规则序列与配方逐项一致。例如确认方案包含 `text.present@1 == false` 与 `watermark.present@1 == false`，配方少一条、增加一条、改值或改类型均拒绝；确认方案中的软规则不转成硬过滤。纯校验不签发执行许可，也不证明该解释草稿就是任务确认时使用的来源；正式批准记录仍须保存来源审阅、任务需求版本与配方关联，在同一事务检查当前任务版本/generation 和候选清单。

`CleaningApprovalProposal` 冻结正式任务的 tenant/owner/project/task、revision/generation、批准前 `expected_task_version`、确认需求摘要、已发布候选清单引用与其素材身份/内容哈希、不可变配方，以及批准时的 `detector_release_digest`。发布摘要存在时使用 v2 提案摘要并覆盖该字段；用户确认必须回传此摘要与期望任务版本，换清单、换规则、换版本或换检测器实现/模型制品都不得复用原批准。业务账本原子批准后生成 `CleaningApproval`，其 `task_version` 必须恰为批准前版本 +1；`approval.job` 将发布摘要带入 `CleaningBinding`。数据类本身不代表授权或持久批准，不能接受普通用户/模型自行构造的对象作为凭据。

为允许 core 账本按独立任务迁移，`detector_release_digest=None` 暂时只表示旧数据/旧调用，沿用 v1 提案和结果摘要；它不是可执行发布。所有新的执行入口必须先调用 `require_released_cleaning_job` 并失败关闭，后续 core 任务负责让新提案强制保存当前受信发布摘要，integration 任务再把该摘要与执行时 `ReleasedDetectorRegistry.release_digest` 比对。旧账本迁移完成前不得因为字段缺省而补猜当前发布，也不得把当前发布静默写进已有批准。

服务端通过 `prepare_released_multi_rule` 创建新的批准提案。该入口只接受已经由受信配置装配的 `ReleasedDetectorRegistry`，先重新执行完整发布预检和当前配方的能力/步骤/检测器/制品核对，再将内部 `registry.release_digest` 传给 core 账本；调用方不能提交发布摘要、配置路径或覆盖发布身份。任何预检或配方不匹配都发生在账本 `prepare` 之前，不留下可供确认的提案。core 的底层 `prepare(..., detector_release_digest=...)` 是受信装配端口，不是业务请求接口。

`src/dsh_retrieval/adapters/cleaning/` 已有受控通用调度：每项候选一次授权读取/哈希校验，相同步骤只执行一次，结果绑定原作业的 operation/revision/generation/recipe/input 哈希；返回前再次检查当前授权和版本，发布时仍需业务账本原子栅栏。当前配方仅支持独立步骤、`eq` 硬规则；规格书要求的显式步骤依赖/资源上限/失败处理版本化仍待补齐，不能静默运行依赖链。测试检测器仅提供合成事实，标 SIMULATED。真实 DJ 仍只有旧的宽度规则独立桥接，不能将本框架标作多规则真实 DJ 联测。

本地串联入口现在要求服务端注入 `ReleasedDetectorRegistry`。取得当前批准后、读取媒体或发布尚未完成的预览前，先要求作业保存的 `detector_release_digest` 与当前 `registry.release_digest` 完全一致；旧批准、换能力目录、换实现或模型制品清单均以 `DETECTOR_NOT_RELEASED` 失败关闭，已保存但未形成预览的结果也不能绕过。摘要一致后仍将配方的能力目录摘要与当前目录逐项比对，再核对每条硬规则的已验证能力、谓词/媒体/操作符/值类型、编译后步骤绑定及实际检测器元数据，不能用摘要比较替代完整复核。目录变更、人工/未发布能力、缺失或替换的后端均失败关闭；已原子发布预览的历史读取不重新执行检测器或改写其发布身份，仍按业务账本重新鉴权和校验当前任务栅栏。服务端还须注入 `DetectorArtifactManifest`：它在固定、非符号链接的部署根目录下，将每个 backend_ref 绑定到实现文件及可选模型文件的相对路径与 SHA-256，并要求运行时检测器声明同一绑定摘要。每次未完成执行/预览重试均复核根目录身份、文件类型、路径边界、符号链接、内容摘要及检测器元数据；缺失、替换、篡改或目录漂移在任何候选媒体读取前失败关闭。路径、摘要和清单只来自受信部署配置，业务请求、配方和普通用户不能提供或覆盖。

制品摘要验证只证明本地发布文件与已批准清单一致，不证明模型效果、许可证、资源策略、在线性能或质量门槛。真实发布仍需规格书 7.8、15.6 和 17.4 的登记、评测与环境验收；当前仓库不登记真实模型或生产实现制品。

服务启动装配使用 `detector_release_config.load_released_detector_registry` 读取由服务端显式选择的 JSON 发布文件。配置只含 schema 版本、逻辑 backend/validator/evidence 引用及实现/模型制品的相对路径和摘要；部署根目录作为独立受信设置传入，不允许配置文件或业务请求改变。加载器拒绝未知/重复字段、错误 schema、重复后端或制品、绝对/越界路径、非法摘要、非普通/符号链接配置文件及超过 1 MiB 的输入；它不动态导入 Python、安装依赖或下载制品。

加载完成即对配置后端、运行时检测器和已发布逻辑绑定做全集一致性检查，并校验每个检测器的绑定摘要、调用入口和全部实现/模型文件。任一缺失、多余、元数据错配或制品漂移均使启动预检失败；成功启动不替代每个未完成作业/预览续发前的再次复核。当前入口是内部装配函数，不新增 HTTP/CLI 请求字段，也不把配置可读性当作模型质量验收。

`DetectorArtifactManifest.manifest_digest` 是与部署绝对根目录无关的规范化发布身份，覆盖排序后的 backend/validator/evidence 元数据及每个实现/模型制品的角色、相对路径和 SHA-256；配置列表顺序不改变摘要，任一绑定或制品变化必须改变摘要。`ReleasedDetectorRegistry.release_digest` 再将能力目录摘要与制品清单摘要组合，作为后续批准记录/审计绑定的候选版本身份；当前切片尚未修改批准账本 schema，不能仅凭该摘要授权执行。

`preflight_evidence()` 每次先重新执行完整启动预检，再返回固定的小型视图：schema、组合发布摘要、两个组成摘要及检测器/制品数量。视图不返回部署路径、单文件摘要或运行时对象；缺失、篡改、绑定或目录漂移时不产生成功证据。该视图用于启动记录和后续审计衔接，不是授权凭据、签名、模型质量报告或健康状态的长期保证。

`CleaningJobResult` 是唯一共享的逐素材多规则输出契约。它保留完整 `CleaningBinding`（含已批准的检测器发布摘要）、候选身份、整体三态及每条硬规则的三态/原因/证据引用。`require_complete_cleaning_result` 要求绑定与已批准作业完全相同，候选和规则的数量、身份及顺序完全匹配；缺失、多余、换序、伪造绑定、换发布或错误总结均拒绝。带发布摘要的结果使用 v2 `result_digest`，因此同一事实输出在不同检测器发布下具有不同身份。摘要不是授权凭据；该数据类不做当前权限检查、不持久化、不计算有效数量，受信业务账本必须在同一发布事务中重新校验 task/revision/generation/operation/权限及输入清单。

### 跨批精确结果血缘（2026-10-31）

`ExactResultSetPreview` 的新发布记录直接父结果 ID/摘要和有序的全部来源 cleaning operation。首批使用单一来源；增量批次只能在同 task/revision/generation、同目标和当前结果指针上追加。发布与重启读取必须递归重建父链，重新校验每批 manifest 的当前授权、确认规则、完整结果及摘要；父链循环、缺失、换序、摘要漂移或旧 generation 均失败关闭。

累计合并只把所有硬规则 pass 的候选纳入可选集，按 content digest 跨批精确去重，并以 `(candidate_id, asset_version)` 最小的稳定代表保证重试/重启一致。批内与跨批重复数、fail 数、unknown 数累加；fail/unknown 不进入有效数。合并后重新切分 accepted/reserve，再以累计 accepted 重算 gap 和补数停止原因。当前结果的受控素材查找可跨全部血缘 operation，因此旧批入选项不会因最新 operation 改变而不可打包或预览。

旧快照缺少血缘字段时按单一 operation 的 v1 摘要兼容读取，不补写或改变原摘要；新快照将血缘纳入 `exact-result-preview@2` 摘要。这一血缘只解决同一正式任务的增量清洗结果，不代替近重复策略、跨任务历史去重或分组配额。
